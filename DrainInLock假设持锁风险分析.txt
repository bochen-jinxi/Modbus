DrainInLock 假设持锁风险分析与修复
====================================

一、问题（一段总览）
用户指出：DrainInLock 假设"调用者已持 gate 锁，内部不再加锁"是隐式契约，若未来新增调用者忘记 lock(gate) 就直接调 DrainInLock，buf 会被无锁访问——OnData 的 AddRange 和 DrainInLock 的 RemoveRange 交错，buf 内容不可预测（丢字节/重复/IndexOutOfRange），且这种数据竞争在 Release 构建下静默发生不抛异常，极难排查。根因是"假设"靠人记，没有运行时强制。修复方案：在 DrainInLock 入口用 Monitor.IsEntered(gate) 做运行时检查，未持锁立即抛 InvalidOperationException，把"隐式契约"变成"强制契约"，调用者忘加锁第一时间暴露而非静默烂数据。

二、风险详析（问题先列）

【风险本质】隐式契约无强制 = 数据竞争静默发生
  DrainInLock 当前签名：static List<byte[]> DrainInLock()
  契约（仅靠注释）：调用者必须已持有 lock(gate)
  违约后果：
    假设新代码这样写（忘记加锁）：
        var frames = DrainInLock();   // 没加 lock(gate)!
    此时 OnData 可能同时 lock(gate){ buf.AddRange(tmp); }
    → DrainInLock 的 buf.Count / buf.CopyTo / buf.RemoveRange 与 OnData 的 AddRange 交错
    → List<byte> 内部 _size 和 _items 数组被两个线程交叉改写
    → 丢字节 / 重复字节 / IndexOutOfRange / 内容错乱
    → Release 构建：不抛异常，静默烂数据，温湿度读数错误且无任何报错
    → Debug 构建：可能偶发抛异常但难复现

【为什么 Debug.Assert 不够】
  Debug.Assert(Monitor.IsEntered(gate)) 只在 DEBUG 构建生效。
  生产环境通常 Release 构建（dotnet build -c Release），Assert 被编译器移除，
  忘加锁的调用者静默通过，数据竞争照样发生。
  并发 bug 本就难复现，靠 Debug 构建抓不住的，等于没保护。

【为什么不能让 DrainInLock 自己 lock(gate)】
  若 DrainInLock 内部自己 lock(gate)：
    - Drain() 调它：一次加锁，OK
    - OnFrameGap() 里 lock(gate) 后调它：C# lock 可重入，立即成功，OK
    但 OnFrameGap 的目的是"切完整帧 + 取残帧"原子。
    若 DrainInLock 内部自己加锁，则：切帧时加锁→切完释放→取残帧再加锁，
    中间又有窗口，OnFrameGap 竞态（第三十四章修的问题）回来了！
  所以 DrainInLock 不能自己加锁，必须依赖调用者已持锁——这正是"假设"的由来。

三、4种修复方案对比

方案 | 做法                                    | 原子性 | 无假设 | Release保护 | 开销
-----|----------------------------------------|--------|--------|-------------|-----
A    | Debug.Assert(Monitor.IsEntered)        | ✓      | ✗      | ✗           | 无
B    | throw if !Monitor.IsEntered            | ✓      | ✓      | ✓           | 微秒级
C    | 切帧逻辑内联到OnFrameGap的lock内        | ✓      | ✓      | ✓           | 无(代码重复)
D    | 纯函数化(不碰共享buf)                   | ✓      | ✓      | ✓           | 改动大

选方案B：运行时 throw + 注释。
  - 原子性：调用者仍在外层 lock(gate) 内，切帧+取残帧原子
  - 无假设：运行时强制检查，忘加锁立即抛异常
  - Release保护：Monitor.IsEntered 在 Release 也生效
  - 开销：Monitor.IsEntered 是微秒级，切帧本就是微秒级，可忽略
  - 代码不重复，改动最小

四、修复代码

DrainInLock 入口加运行时检查：
    static List<byte[]> DrainInLock()
    {
        if (!Monitor.IsEntered(gate))

        var frames = new List<byte[]>();
        ...原切帧逻辑...
    }

调用者不变（Drain 和 OnFrameGap 都已在 lock(gate) 内调），契约从"注释假设"升级为"运行时强制"。

五、诚实补充（所有我知道的信息）

1. Monitor.IsEntered(obj) 是 .NET 4.5+ API，.NET 8 肯定有。
   它检查"当前线程是否持有 obj 的锁"，可重入锁也返回 true。
   开销：微秒级（查 CLR 内部锁状态），切帧循环每秒最多几百次，总开销可忽略。

2. 方案C（内联）也完全正确，代价是切帧 while 循环约15行在 OnFrameGap 重复一次。
   选方案B 是为了避免重复——DRY 原则，且运行时检查还能防未来其他调用者犯错。

3. 方案D（纯函数化）最彻底：SplitFrames(List<byte> src) 不碰共享 buf，返回(帧列表, 残帧)。
   调用者 lock(gate){ var (frames, rest) = SplitFrames(buf); buf.Clear(); }
   但要改 FrameLength 签名、buf 更新逻辑，改动大，收益边际，本次不采用。

4. 这个风险的本质是"锁的契约靠注释不靠代码"。业界更彻底的做法是：
   - 用 Roslyn Analyzer 静态扫描"调 DrainInLock 必须在 lock(gate) 内"（编译期抓）
   - 或用 Rust 那样的所有权系统（编译期保证）
   C# 没有这些，运行时检查是性价比最高的防护。

5. 当前两个调用者（Drain:245 和 OnFrameGap:187）都在 lock(gate) 内，无违约。
   加检查是防未来新增调用者犯错，不是修当前 bug——这是防御性编程。

六、记忆口诀

「隐式锁契约靠注释不靠谱，运行时 Monitor.IsEntered 强制检查；
 Debug.Assert 只在 Debug 生效，Release 静默烂数据；
 DrainInLock 不能自己加锁（否则 OnFrameGap 原子性破），
 靠调用者持锁 + 入口 throw 兜底，契约从假设变强制」
