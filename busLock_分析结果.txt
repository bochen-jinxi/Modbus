问题：SendLoop 里的 busLock 锁，为什么不能死等？
文件：F:\chenbo\Program.cs
分析时间：2026-11-03
==================================================

一、结论（先说答案）
--------------------------------------------------
SendLoop 里对 busLock 用的是 Monitor.TryEnter(busLock, 0)（非阻塞、
零超时试锁），而不是 lock(busLock) 或 Monitor.Enter 死等。

根本原因：SendLoop 是"读轮询线程"，写命令（WriteLoop）具有更高优先级，
读操作必须让位于写操作。如果 SendLoop 死等 busLock，会引发"写饿死"
和"实时性丧失"两类严重问题。

二、busLock 的设计意图（事务级互斥）
--------------------------------------------------
busLock 是"总线事务锁"，保护的是 RS485 半双工总线的"整个事务"：
  - 读事务：SendLoop 发请求 → 等应答（frameReceived.WaitOne(TimeoutMs)）
  - 写事务：WriteLoop → ExecuteWrite 发命令 → 等回显（wr.Ack.WaitOne）

同一时刻只允许一个事务独占总线，否则会：
  1) 电气冲突：RS485 半双工，主站同时发两帧会撞车；
  2) 应答错配：两个事务都在等应答，从站回的一帧不知道归谁。

三、为什么 SendLoop 不能死等——逐条分析
--------------------------------------------------

【原因1：写优先，读必须让步】
  写命令（开关 on/off）是用户操作，要求"一定能执行成功"。
  读轮询是后台周期任务，丢一轮没影响（下一轮还会再来）。
  → 优先级：写 > 读。
  → WriteLoop 用 lock(busLock) 死等，保证写一定能拿到总线；
    SendLoop 用 TryEnter，拿不到就跳过本轮，把总线让给写。
  → 如果 SendLoop 也死等，两个线程平等竞争，写命令可能被
    无限推迟（读线程一轮接一轮占着不放），写"饿死"。

【原因2：死等会破坏读轮询的"周期性让步"语义】
  SendLoop 是 while(running) 的死循环，每轮：
    TryEnter → 拿到就发一帧读请求 → 等应答 → 释放 → Sleep(15)
  如果改成死等：
    Monitor.Enter(busLock) 会阻塞，直到写事务释放。
    看似"等到就能继续"，但问题在于：
    - 写事务内部 ExecuteWrite 要等回显 TimeoutMs(50ms) + 重试最多3次
      + 间隔，一次写事务可能占 busLock 长达 200ms+。
    - 这期间 SendLoop 卡死，无法响应 running=false（退出信号），
      程序退出延迟，Ctrl+C 不灵敏。
    - 更糟：如果多个写命令排队（writeQueue 有多条），WriteLoop 会
      连续多次占 busLock，SendLoop 可能长时间得不到执行，
      读轮询"假死"。

【原因3：死等会引入死锁风险（虽然本代码锁顺序一致，但语义上仍危险）】
  SendLoop 拿到 busLock 后，内部还要 lock(io) 写串口、
  frameReceived.WaitOne 等应答。
  如果 SendLoop 在 busLock 上死等，而此时：
    - WriteLoop 持有 busLock，正在 ExecuteWrite 里 lock(io) 写串口；
    - 串口驱动因某种原因卡住（虽然 WriteTimeout=1000 兜底）；
  SendLoop 会一直挂在 busLock 上，整个读通道停摆。
  TryEnter + 跳过 的策略让读通道始终保持"活力"，哪怕本轮跳过，
  下一轮还能再试，不会因一次写事务的卡顿而彻底停读。

【原因4：TryEnter(0) + Sleep(15) 是"让权轮询"模式】
  拿不到锁 → Sleep(15) → continue，本质是"主动让出 CPU + 稍后重试"。
  这比死等的好处：
    - 不持有任何锁就睡眠，不阻塞别人；
    - 睡醒后重新试，写事务一旦释放立刻能拿到；
    - 15ms 的让步对 9600bps 的 18ms 交互周期来说"无感"
      （注释里也写了"读轮询间隔本身 15ms，让步 15.6ms 无感"）。
  死等则是"被动挂起"，调度器何时唤醒不可控，且挂起期间无法
  响应任何其他信号（如退出）。

【原因5：读轮询"跳过一轮"是安全的，死等反而有害】
  读是周期轮询多从站（Slaves = {0x01, 0x02}），丢一轮顶多晚 15ms
  再读，温湿度数据晚一点显示，无功能性损失。
  而写是用户触发的离散事件，必须尽快执行。
  → 让读"可跳过"、写"必执行"是正确的优先级分配。
  → 死等把读变成"必执行"，与写平起平坐，违背了"写优先"的设计。

四、对比 WriteLoop 为什么可以死等
--------------------------------------------------
WriteLoop 用 lock(busLock)（即 Monitor.Enter，死等）：
  - 写命令是用户操作，"必须执行"，不能因为读在轮询就放弃。
  - 读事务持有 busLock 的时间短（发一帧 + 等 50ms 超时），
    且读事务用 TryEnter 拿不到就跳过，不会长时间霸占。
  - 所以 WriteLoop 死等 busLock 不会等太久（最多等读一轮 ~65ms），
    不会饿死，保证写命令最终一定执行。
  这正是"写死等、读试锁"的非对称设计：优先级高的死等，
  优先级低的试锁+让步。

五、锁顺序与死锁预防（补充）
--------------------------------------------------
代码注释声明锁顺序：busLock → io → gate
  - SendLoop：busLock(TryEnter) → io(写串口) → [gate 在超时清理时]
  - WriteLoop：busLock(Enter) → io(写串口) → [gate 在清缓冲时]
  - OnData：io(读串口) → gate(切帧)
  统一顺序保证不会交叉等待而死锁。TryEnter 进一步让读事务
  "拿不到就退"，连"等待"这个动作都不存在，从根本上杜绝了
  读侧参与死锁链的可能。

六、一句话总结
--------------------------------------------------
SendLoop 用 TryEnter(0) 而不死等 busLock，是为了：
  1) 让写命令优先执行（写死等、读让步）；
  2) 保持读轮询的周期性与退出响应能力（不卡死）；
  3) 避免读在写事务长占用期间假死；
  4) 从根本上消除读侧参与死锁链的可能。
死等会让读与写平等竞争总线，违背"写优先"设计，并可能导致
写饿死、读假死、退出延迟等问题。
