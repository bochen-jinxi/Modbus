一、当前 Program.cs 功能设计全面分析
================================================================================

1.1 整体定位
--------------------------------------------------------------------------------
这是一个基于 C# 的 Modbus RTU 串口通讯程序，运行于工控现场，通过 RS485 总线
与多个 Modbus 从站设备通讯。核心能力：
  - 周期性轮询读取从站寄存器（功能码 0x03 读保持寄存器）
  - 支持写单个线圈（功能码 0x05），实现"开到位/关到位"控制
  - 多从站轮询（默认从站 0x01、0x02）
  - 多按钮/多命令并发投递，串行执行，保证 RS485 半双工总线一次一帧
  - 帧定界采用 Modbus 规范的 3.5 字符时间，高精度 Stopwatch 判定
  - 完整的 CRC16 校验、错位重对齐、超时重试、异常响应处理


1.2 关键常量与参数
--------------------------------------------------------------------------------
  - BaudRate = 9600              波特率
  - RegCount = 2                 每次读 2 个寄存器（温湿度场景）
  - TimeoutMs = 50               同步等应答超时 50ms（实测 30ms 偏紧、50ms 稳）
  - IntervalMs = 15              两次请求间隔 15ms
  - WriteRetry = 3               写命令失败重试 3 次
  - Slaves = { 0x01, 0x02 }      轮询从站列表
  - FrameGapMs = 3.5*10/9600*1000 ≈ 3.65ms   3.5 字符帧超时
  - PollMs = FrameGapMs/2 ≈ 1.83ms           帧超时检测轮询间隔
  - Verbose = false              详细日志开关


1.3 线程模型（共 5 个线程 + 主线程）
--------------------------------------------------------------------------------
  ① SendLoop        发送线程：周期轮询各从站，发 0x03 读请求，等应答
  ② FrameGapLoop    帧超时检测线程：高精度判定 3.5 字符静默，触发切帧
  ③ WriteLoop       写线程：串行消费 writeQueue，执行写线圈 + 等回显 + 重试
  ④ CmdLoop         命令线程：解析控制台输入 on/off，提交写请求
  ⑤ OnData          串口数据接收回调（由 SerialPort.DataReceived 触发）
  主线程             等待 Ctrl+C 退出


1.4 同步与锁机制（锁顺序：busLock → io → gate，统一不死锁）
--------------------------------------------------------------------------------
  - busLock  总线事务锁：RS485 半双工要求"发+等应答"独占总线
             SendLoop 用 Monitor.TryEnter 非阻塞试，拿不到跳过本轮（写优先）
             WriteLoop 用 lock 阻塞等，保证写命令一定能执行
  - io       串口读写锁：保护 sp.Write / sp.Read 互斥
  - gate     接收缓冲区 buf 锁：保护 buf 的 AddRange / Clear / Drain
  - frameReceived (AutoResetEvent)  读应答同步信号，收到一帧有效应答时 Set
  - activeWrite (volatile)          当前写线程正在等回显的请求（同一时刻只有一个）
  - curSlave (volatile)             当前正在等哪个从站的应答，用于校验防错配


1.5 写请求模型 WriteRequest
--------------------------------------------------------------------------------
  - Slave/Addr/On/Frame  请求参数 + 完整发送帧（含 CRC）
  - Ack (AutoResetEvent)  收到 0x05 回显时 Set，ExecuteWrite 等它
  - AckOk                 一次回显结果
  - Completed (ManualResetEventSlim)  整个请求（含重试）完成后 Set
  - Result                最终结果
  写队列 writeQueue (ConcurrentQueue) 线程安全，多线程并发 Enqueue 不互相阻塞


1.6 帧处理流程
--------------------------------------------------------------------------------
  ① OnData：串口收到数据 → 追加到 buf → DrainInLock 切出完整帧 → Handle 处理
  ② FrameGapLoop：高精度轮询，距最后收数据超 3.65ms → OnFrameGap → 切帧 → Handle
  ③ DrainInLock：按 FrameLength 算帧长 → CRC 校验通过取走 → 失败滑动 1 字节重对齐
  ④ Handle：
       - 校验帧长、CRC
       - 多从站校验：写用 activeWrite.Slave，读用 curSlave，防迟到应答错配
       - 异常响应（func & 0x80）：通知 activeWrite 或 frameReceived
       - 0x05 写线圈应答：整帧比对发送帧，过滤旧请求迟到应答 → Set Ack
       - 0x03/0x04 读寄存器应答：解析 N 个寄存器，当前硬编码按温湿度解析（t=frame[3..4], h=frame[5..6]）


1.7 当前已实现的能力
--------------------------------------------------------------------------------
  ✅ 多从站轮询读寄存器（0x03）
  ✅ 写单个线圈开到位/关到位（0x05），含重试
  ✅ 多按钮/多命令并发投递，串行执行
  ✅ 参数模式：dotnet run on 1 0 → 执行一次写命令后退出
  ✅ 交互模式：on/off/sync/quit，支持 ; 分隔多命令
  ✅ 帧定界、CRC 校验、错位重对齐、超时清状态
  ✅ 写优先于读（busLock TryEnter vs lock）


1.8 当前的局限与未实现的能力
--------------------------------------------------------------------------------
  ❌ 读寄存器解析硬编码为温湿度（t/h），无法通用解析转速/电压/电流等
  ❌ 没有"写后立即读"的联动机制：开到位成功后，不会自动去读设备应答数据
  ❌ 读操作只在 SendLoop 周期轮询，无法按事件触发（如"开到位成功"事件）
  ❌ 没有寄存器映射表/设备模型：不知道哪个寄存器是转速/电压/电流
  ❌ 读请求地址固定 0x0000、个数固定 RegCount=2，无法按需指定
  ❌ 没有读请求队列（只有写请求队列 writeQueue）


二、新增需求分析：开到位后采集设备应答数据
================================================================================

2.1 需求描述
--------------------------------------------------------------------------------
工控现场按下开关开到位后，需要采集"开到位后设备的应答数据"。
典型场景：
  - 电机启动开关开到位后 → 采集转速、电压、电流
  - 阀门开启开到位后     → 采集开度、流量、压力
  - 加热器启动开到位后   → 采集温度、功率

本质：写线圈(0x05)成功后，触发一次或多次读寄存器(0x03/0x04)，
      把"控制动作"与"状态采集"联动起来。


2.2 技术难点与约束
--------------------------------------------------------------------------------
  ① RS485 半双工：开到位写事务独占总线，写完才能读，不能并发
  ② 设备应答有延迟：开到位成功 ≠ 设备数据立即就绪
     - 电机刚启动时转速还在上升，立即读到的转速可能为 0 或很小
     - 需要等设备稳定后再读，或周期性读一段时间
  ③ 数据可能跨多个寄存器：转速、电压、电流可能在不同寄存器地址
  ④ 不同设备寄存器映射不同：需要可配置的"读任务"描述
  ⑤ 总线占用：开到位后的读任务会占用总线，影响 SendLoop 周期轮询
     - 需要权衡：事件触发的读 vs 周期轮询的读
  ⑥ 当前 SendLoop 是连续轮询，没有"插入一次特定读"的机制
  ⑦ 读请求目前没有队列化（只有写请求队列）


2.3 当前代码与需求的差距
--------------------------------------------------------------------------------
  - WriteSingleCoil / ExecuteWrite 只做写，写完就结束，没有"写后读"钩子
  - SendLoop 只会按 Slaves[] 顺序轮询固定地址 0x0000 读 RegCount 个寄存器
  - Handle 对 0x03 应答的解析硬编码为温湿度，无法输出转速/电压/电流
  - 没有设备模型/寄存器映射表


三、扩展方案分析（多种方案对比）
================================================================================

方案 A：写后同步立即读（最简单）
--------------------------------------------------------------------------------
  思路：ExecuteWrite 成功后，在同一个 busLock 事务内，立即发一个 0x03 读请求
  优点：实现最简单，复用现有 busLock/io/gate 机制
  缺点：
    - 设备数据可能还没就绪（电机刚启动转速还没上来）
    - 同步阻塞写线程，延迟下一个写命令的执行
    - 只读一次，无法观察"启动过程曲线"
  适用：设备应答几乎瞬时就绪的场景（如读开关状态位）


方案 B：写后投递读任务到读队列（推荐）
--------------------------------------------------------------------------------
  思路：
    1. 新增 ReadRequest 模型（类似 WriteRequest）：从站、起始地址、寄存器个数、
       解析方式、完成信号
    2. 新增 readQueue (ConcurrentQueue<ReadRequest>)
    3. SendLoop 改造：优先消费 readQueue 中的事件读任务，没有才做周期轮询
    4. ExecuteWrite 成功后，按配置构造 1 个或多个 ReadRequest 投递到 readQueue
    5. Handle 对 0x03 应答按 ReadRequest 的解析方式输出（转速/电压/电流）
  优点：
    - 不阻塞写线程，读任务排队执行
    - 支持写后延迟读（投递时带 delay，到点才执行）
    - 支持写后周期读（投递多个带递增 delay 的读任务，观察启动曲线）
    - 复用 busLock 机制，读任务与周期轮询互斥
  缺点：
    - 改动较大：新增 ReadRequest、readQueue、SendLoop 改造、Handle 解析改造
    - 需要设计寄存器映射配置
  适用：通用工控场景，最灵活


方案 C：写后启动临时读线程（不推荐）
--------------------------------------------------------------------------------
  思路：ExecuteWrite 成功后，new Thread 周期读一段时间
  缺点：
    - 多个线程抢总线，与 SendLoop/WriteLoop 竞争 busLock，调度复杂
    - 线程数不可控，频繁启停线程开销大
  不推荐


方案 D：事件订阅 + 读任务调度器（最完整）
--------------------------------------------------------------------------------
  思路：
    1. 定义设备模型：DeviceConfig { Slave, WriteCoilAddr, ReadProfiles[] }
       ReadProfile { Name(转速/电压/电流), StartAddr, Count, Scale, Unit, DelayMs, IntervalMs, DurationMs }
    2. 写成功后触发 OnSwitchOn 事件
    3. 读任务调度器订阅事件，按 ReadProfile 生成读任务投递到 readQueue
    4. SendLoop 消费 readQueue
    5. Handle 按 ReadProfile.Name 输出带工程量换算的结果
  优点：最完整、可配置、可扩展
  缺点：改动最大，接近重构


四、推荐方案：方案 B（写后投递读任务到读队列）
================================================================================

4.1 推荐理由
--------------------------------------------------------------------------------
  - 复用现有 busLock/io/gate/frameReceived 机制，不引入新锁
  - 读任务排队执行，不阻塞写线程，不与周期轮询冲突
  - 支持写后延迟读、周期读，覆盖电机启动曲线采集需求
  - 改动可控，不需要重构整个程序


4.2 需要新增的数据结构
--------------------------------------------------------------------------------
  // 读请求（类似 WriteRequest）
  class ReadRequest
  {
      public byte Slave;
      public ushort StartAddr;
      public ushort RegCount;
      public string Tag;              // 用途标识："转速"/"电压"/"电流"
      public double Scale;           // 工程量换算系数（如 0.1 表示除以10）
      public string Unit;            // 单位："RPM"/"V"/"A"
      public byte[] Frame;           // 完整发送帧（含CRC）
      public readonly AutoResetEvent Ack = new AutoResetEvent(false);
      public bool AckOk;
      public ushort[] Values;        // 读到的寄存器值
      public readonly ManualResetEventSlim Completed = new ManualResetEventSlim(false);
      public bool Result;
  }

  // 当前活跃读请求（类似 activeWrite）
  static volatile ReadRequest activeRead;

  // 读请求队列
  static readonly ConcurrentQueue<ReadRequest> readQueue = new ConcurrentQueue<ReadRequest>();

  // 设备配置：写线圈地址 → 开到位后要读哪些数据
  // 例如：电机启动线圈 0 → 读 转速@0x0100 + 电压@0x0102 + 电流@0x0104
  static readonly Dictionary<(byte slave, ushort coilAddr), ReadProfile[]> ReadProfiles = ...;


4.3 需要改造的方法
--------------------------------------------------------------------------------
  ① SendLoop 改造：
     - 每轮先检查 readQueue，有读任务则优先执行（发 0x03 + 等应答）
     - 没有读任务才做原来的周期轮询
     - 读任务也用 busLock 事务锁

  ② ExecuteWrite 改造：
     - 写成功后，查 ReadProfiles，若该 (slave, addr) 有配置，
       则构造 ReadRequest 投递到 readQueue（可带 delay）
     - 写事务本身不变，写完即返回，读任务异步排队

  ③ Handle 改造（0x03/0x04 分支）：
     - 若 activeRead != null，按 activeRead.Tag/Scale/Unit 输出工程量
     - 否则按原逻辑（温湿度）解析
     - Set activeRead.Ack 而非 frameReceived（或两者都 Set）

  ④ FrameLength：0x03/0x04 已支持变长，无需改

  ⑤ 新增 ReadLoop 或在 SendLoop 内消费 readQueue（推荐后者，减少线程）


4.4 执行时序示例（电机启动）
--------------------------------------------------------------------------------
  t=0       用户输入：on 1 0
  t=0       CmdLoop 投递 WriteRequest(从站1, 线圈0, ON) 到 writeQueue
  t=5       WriteLoop 取出，lock(busLock)，发 0x05，等回显
  t=23      收到 0x05 回显，开到位成功，释放 busLock
  t=23      ExecuteWrite 查 ReadProfiles[(1,0)]，发现要读 转速/电压/电流
            构造 3 个 ReadRequest 投递到 readQueue（带 delay 500ms 等电机稳定）
  t=523     SendLoop 取出 ReadRequest(转速)，lock(busLock)，发 0x03 @0x0100
  t=541     收到应答，按 Scale/Unit 输出："转速 = 1450.0 RPM"
  t=556     SendLoop 取出 ReadRequest(电压)... 输出 "电压 = 380.2 V"
  t=571     SendLoop 取出 ReadRequest(电流)... 输出 "电流 = 12.5 A"
  t=586     readQueue 空，SendLoop 恢复正常周期轮询


4.5 关键设计决策点（需确认）
--------------------------------------------------------------------------------
  ❓ 读任务与周期轮询的优先级：读任务优先？还是交替？
     建议：读任务优先（事件驱动数据更重要），但限制 readQueue 最大长度防饿死轮询
  ❓ 写后读的延迟：固定 500ms？可配置？
     建议：ReadProfile.DelayMs 可配置，默认 500ms
  ❓ 读一次还是读一段时间（观察启动曲线）？
     建议：ReadProfile 支持 IntervalMs + DurationMs，可周期读一段时间
  ❓ 读任务的应答超时：复用 TimeoutMs=50ms？
     建议：复用，一致性
  ❓ 寄存器映射如何配置：硬编码？配置文件？
     建议：先用 Dictionary 硬编码（简单），后续可扩展 JSON 配置
  ❓ 多个寄存器连续读还是合并读？
     建议：若转速/电压/电流地址连续，可一次读多个；不连续则分多次读


五、风险与注意事项
================================================================================
  1. 总线占用冲突：读任务会占用总线，期间 SendLoop 周期轮询被暂停，
     可能导致温湿度采集有间隙。需评估是否可接受。
  2. 设备响应延迟：开到位成功后设备数据未必就绪，延迟读必要。
  3. 读任务堆积：频繁开关会堆积读任务，需限制队列长度或丢弃旧任务。
  4. activeRead 与 activeWrite 同时存在时的应答分发：
     - 0x05 回显 → 分发给 activeWrite
     - 0x03 应答 → 分发给 activeRead（若存在）否则按周期轮询处理
     - 需保证同一时刻只有一种事务在等应答（busLock 已保证）
  5. curSlave 校验：读任务执行时 curSlave 应设为 ReadRequest.Slave
  6. 解析逻辑分支：Handle 的 0x03 分支需区分"周期轮询读"和"事件触发读"，
     按 activeRead 是否为 null 判断。


六、总结
================================================================================
当前 Program.cs 是一个成熟的 Modbus RTU 通讯框架，已实现多从站轮询读、
写线圈开到位/关到位、多命令并发串行执行、帧定界与 CRC 校验等核心能力。

要实现"开到位后采集设备应答数据（转速/电压/电流）"，核心是建立"写后读"
联动机制。推荐方案 B：新增 ReadRequest 模型与 readQueue，ExecuteWrite 成功后
投递读任务，SendLoop 优先消费 readQueue，Handle 按读任务配置解析工程量。

该方案复用现有总线锁与帧处理机制，改动可控，支持延迟读与周期读，
能覆盖电机启动后采集转速/电压/电流的典型工控场景。
