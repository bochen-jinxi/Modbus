ProgramTcp.cs DrainInLock 锁位置优化分析
==========================================

一、核心一段（先回答能不能改）
能改，而且应该改。TCP 版没有 OnFrameGap（RTU 版才有），不存在"切帧+取残帧需要原子"的需求。DrainInLock 的"假设调用者持锁"模式是为 RTU 版 OnFrameGap 设计的——OnFrameGap 要在同一个 lock 内调 DrainInLock 切帧 + 取残帧，所以 DrainInLock 不能自己加锁。TCP 版没有这个约束，Drain 唯一调用者是 ReceiveLoop，直接把锁放进 Drain 内部、去掉 DrainInLock，既消除了"假设持锁"风险又简化代码。改法：合并 DrainInLock 到 Drain，Drain 内部 lock(gate) 切帧，出锁后 Handle。

二、RTU 版为什么需要 DrainInLock（回顾）

  RTU 版 OnFrameGap：
    lock (gate) {
        frames = DrainInLock();    // 切完整帧
        rest = buf.ToArray();      // 取残帧
        buf.Clear();
    }
  → 切帧+取残帧必须在同一个 lock 内原子，所以 DrainInLock 不能自己加锁（否则重入释放后取残帧又有窗口）
  → DrainInLock 假设调用者已持锁，靠 Monitor.IsEntered 检查

  TCP 版没有 OnFrameGap，没有"切帧+取残帧"的需求 → 不需要 DrainInLock 模式。

三、TCP 版的 buf 访问点（确认没有原子需求）

  访问点                    | 操作              | 锁
  --------------------------|-------------------|------------------
  ReceiveLoop: AddRange     | buf.AddRange(seg) | lock(gate)
  Drain: 切帧               | buf.CopyTo/Remove | 当前lock(gate)调DrainInLock
  SendLoop超时: Clear       | buf.Clear()       | lock(gate)

  没有任何地方需要"两个buf操作在同一把锁内原子"。
  AddRange 和 Drain 本来就是两次独立加锁（AddRange释放后Drain才加），可接受。
  → 锁可以放进 Drain 内部，不影响正确性。

四、改法（合并 DrainInLock 到 Drain）

【改前】
  static List<byte[]> DrainInLock()
  {
      if (!Monitor.IsEntered(gate)) throw...;
      var frames = new List<byte[]>();
      while (buf.Count >= 6) { ...切帧... }
      return frames;
  }
  static void Drain()
  {
      List<byte[]> frames;
      lock (gate) { frames = DrainInLock(); }
      foreach (var f in frames) Handle(f);
  }

【改后】
  static void Drain()
  {
      var frames = new List<byte[]>();
      lock (gate)
      {
          while (buf.Count >= 6) { ...切帧... }
      }
      foreach (var f in frames) Handle(f);
  }

  去掉 DrainInLock，去掉 Monitor.IsEntered 检查，一个 Drain 搞定。
  锁在内部，没有"假设调用者持锁"的风险。

五、改后的正确性验证

【ReceiveLoop 调 Drain】
  lock(gate){ buf.AddRange(seg); }  // 加数据
  Drain();                          // 内部 lock(gate) 切帧
  → AddRange 和 Drain 两次独立加锁，和改前一样，无变化

【SendLoop 超时 Clear 和 Drain 并发】
  SendLoop: lock(gate){ buf.Clear(); }
  Drain:    lock(gate){ 切帧 }
  → 两者 lock(gate) 互斥，要么先Clear后切（切到空buf）、要么先切后Clear（切完再清），都安全

【没有"假设持锁"风险】
  锁在 Drain 内部，任何调用者直接调 Drain 就行，不用记得先加锁。
  消除了 DrainInLock 的隐式契约。

六、诚实补充（所有我知道的信息）

1. 这次改的本质：TCP 版不需要 DrainInLock 的"调用者持锁"模式，
   因为没有 OnFrameGap。RTU 版需要是因为 OnFrameGap 的原子性需求。
   同一个 DrainInLock 模式，RTU 必需、TCP 不需要——因协议特性而异。

2. 改后 Drain 内部 lock(gate) 切帧，出锁后 foreach Handle：
   Handle 在锁外调用，只读已拷贝的 frame 数组，不碰 buf，安全。
   和改前的"DrainInLock返回frames，出锁后Handle"行为一致。

3. 改后少一个方法（DrainInLock）、少一个 Monitor.IsEntered 检查、少一个隐式契约。
   代码更简洁，风险更低。

4. 如果将来 TCP 版也要加 OnFrameGap（比如要处理"连接 idle 超时清残帧"），
   那时再拆回 DrainInLock 模式。当前不需要，YAGNI 原则。

5. ReceiveLoop 的 AddRange 和 Drain 两次独立加锁的窗口：
   AddRange 释放 gate → Drain 加 gate 前，SendLoop 超时可能 Clear。
   后果：刚 AddRange 的数据被 Clear 清了，Drain 切不到。
   但这是超时的预期行为（清迟到数据），且同时发生概率极低，可接受。
   如果要严格原子，可以把 AddRange+切帧放同一个 lock——但 ReceiveLoop 的 Read 阻塞
   在锁外，不影响。当前两次独立加锁够用。

6. 用户说"你认为不可以改就不改"——我认为可以改且应该改：
   TCP 版没有 OnFrameGap，DrainInLock 是从 RTU 版照搬的过度设计，
   合并到 Drain 更符合 TCP 版的简洁性。

七、记忆口诀

「RTU的DrainInLock为OnFrameGap原子设计，TCP没有OnFrameGap不需要；
 TCP直接锁放Drain内部切帧出锁Handle，去掉DrainInLock消除假设持锁风险；
 AddRange和Drain两次独立加锁可接受，SendLoop Clear和Drain互斥安全；
 简化一个方法一个检查一个契约，YAGNI不需要的不留」
