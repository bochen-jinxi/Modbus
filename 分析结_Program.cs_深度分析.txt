一、整体架构分析
================================================================================

【线程模型】
主线程 - 参数模式执行/交互命令/Ctrl+C退出
SendLoop - 周期轮询读 + 事件触发读（优先消费readQueue）
FrameGapLoop - 帧超时检测（3.5字符时间判定）
WriteLoop - 串行消费writeQueue，执行写命令+等回显+重试
CmdLoop - 用户交互输入on/off命令
OnData - 串口数据接收回调（DataReceived事件）

【核心数据结构】
buf: List<byte> - 接收缓冲区（gate保护）
writeQueue: ConcurrentQueue<WriteRequest> - 写请求队列
readQueue: ConcurrentQueue<ReadRequest> - 读请求队列
activeWrite/activeRead/activeVerify - 当前活跃请求（volatile）
pollAck: AutoResetEvent - 周期轮询应答信号
pollActive: bool - 周期轮询活跃标记

================================================================================
二、线程安全分析（锁顺序与死锁检测）
================================================================================

【锁顺序一致性】✅ 通过
所有锁获取顺序统一为：busLock → io → gate

【锁使用分析】
busLock - WriteLoop: 总线事务（发+等应答）独占
        - SendLoop: TryEnter非阻塞试，写优先
io - OnData: 串口读写（sp.BytesToRead/sp.Read）
   - SendFrame: sp.Write
   - ClearRxState: sp.DiscardInBuffer
gate - OnData: buf.AddRange + DrainInLock原子切帧
     - FrameGapLoop: DrainInLock
     - ClearRxState: buf.Clear

【潜在死锁风险】⚠️ 需关注
1. WriteLoop持有busLock时调用ExecuteWrite → ExecuteWrite内ClearRxState获取io → 安全
2. OnData持有io时调用DrainInLock → DrainInLock内需要gate → 安全（顺序一致）
3. OnData中lock(io)后，在lock(gate)块内调用DrainInLock → DrainInLock检查Monitor.IsEntered(gate) ✅

三、竞态条件分析（线程交错时序穷举）
================================================================================

【场景1：周期轮询超时 + 迟到应答】
T1: SendLoop 发请求，pollActive=true，curSlave=0x01
T2: Handle 收到应答，读curSlave(0x01)，校验通过
T3: SendLoop 超时，pollActive=false，curSlave=0xFF，pollAck.Reset()
T4: Handle 检查pollActive(false) → 不Set pollAck ✅ 安全

【场景2：写命令 + 周期轮询并发】
T1: WriteLoop 持有busLock，ExecuteWrite发0x05
T2: SendLoop TryEnter(busLock,0)失败 → Thread.Sleep(15)跳过 ✅ 写优先
T3: Handle 收到0x05回显，通过activeWrite分发 ✅

【场景3：写命令成功后投递读任务】
T1: ExecuteWrite 成功，EnqueueReadTasks投递读任务
T2: ThreadPool.QueueUserWorkItem延迟DelayMs后Enqueue
T3: SendLoop 优先消费readQueue，执行ExecuteRead ✅

【场景4：ExecuteRead超时 + 迟到应答】
T1: ExecuteRead 发0x03，activeRead=rr，curSlave=slave
T2: Handle 收到0x03，通过activeRead分发 ✅
T3: 超时后curSlave=0xFF，finally activeRead=null
T4: 迟到应答到达，frame[0]!=expect(0xFF) → 忽略 ✅

【场景5：VerifyPhysicalState内嵌在ExecuteWrite中】
T1: ExecuteWrite 持有busLock，写成功
T2: VerifyPhysicalState 发0x02，仍在busLock内
T3: Handle 收到0x02，通过activeVerify分发 ✅
T4: 验证失败 → continue重试写命令（仍在busLock内）✅

【场景6：参数模式退出竞态】⚠️ 需关注
T1: 参数模式执行完成，running=false
T2: 主线程lock(io) sp.Close()
T3: OnData 可能还在执行（DataReceived事件可能已触发但未处理完）
风险：sp.Close()后OnData可能继续访问sp → ObjectDisposedException

四、边界条件分析（溢出、null、死代码）
================================================================================

【边界条件1：int序号溢出】
原代码注释：★ 不用int序号的正负判断（避免int溢出后正变负导致逻辑反转）
当前方案：用bool pollActive替代int序号 ✅ 安全

【边界条件2：缓冲区溢出】
- buf: List<byte> 动态增长，无容量限制
- 风险：长时间运行后内存占用可能增长
- 缓解：ClearRxState定期清理，帧超时后buf.Clear()

【边界条件3：null引用】
activeWrite?.Slave - 条件运算符，null安全 ✅
activeVerify?.Slave - 条件运算符，null安全 ✅
activeRead != null - 显式null检查 ✅
aw?.Frame - 条件运算符，但Frame在构造函数中初始化 ✅
vr.Frame - VerifyRequest构造函数中初始化 ✅

【边界条件4：死代码检测】
第264行 while(running) - 参数模式会return，主循环正常 ✅
第500行 Drain()方法 - 未被调用 ⚠️ 死代码
第691行 else分支 - "[提示] 非预期的帧" - 可能触发 ✅
第772行 Thread.Sleep(5) - 队列空时等待 ✅
第847行 Thread.Sleep(15) - 重试间隔 ✅

【边界条件5：CRC计算边界】
Crc16(data, len): len=0时返回0xFFFF ✅
Crc16(data, data.Length): 正常 ✅
CrcOk(frame): frame.Length<2时，frame.Length-2为负数 → 数组越界 ⚠️
修复建议：在CrcOk开头添加 if(frame.Length < 2) return false;

【边界条件6：帧长度计算边界】
FrameLength(b, start): b.Count-start<3时返回-1 ✅
func==0x05时返回8 ✅
func==0x02/0x03/0x04时，b[start+2]可能越界 ⚠️
修复建议：在读取b[start+2]前检查b.Count > start+2

================================================================================
五、"改了A是否影响B"分析
================================================================================

【问题1：改了WaitOne是否影响Set？】
WaitOne(TimeoutMs) 在多个位置调用：
- SendLoop: pollAck.WaitOne(TimeoutMs)
- ExecuteWrite: wr.Ack.WaitOne(TimeoutMs)
- ExecuteRead: rr.Ack.WaitOne(TimeoutMs)
- VerifyPhysicalState: vr.Ack.WaitOne(TimeoutMs)

Set位置：
- Handle 0x05回显: aw.Ack.Set()
- Handle 0x02回显: av.Ack.Set()
- Handle 0x03/0x04回显: ar.Ack.Set() 或 pollAck.Set()
- 异常响应: aw.Ack.Set() / av.Ack.Set() / ar.Ack.Set() / pollAck.Set()

结论：每个WaitOne对应唯一的Set，改了任何一个都会影响对应的信号 ✅

【问题2：改了pollActive是否影响pollAck？】
pollActive=true: 发请求前标记活跃
pollAck.Reset(): 清上一次残留信号
超时后pollActive=false: 迟到应答不Set pollAck
下一轮发请求前pollActive=true: 不影响正常流程

结论：pollActive是pollAck的"门控"，改了pollActive会影响pollAck的Set行为 ✅

【问题3：改了activeWrite是否影响Handle？】
Handle通过activeWrite?.Slave校验从站号
Handle通过activeWrite?.Frame比对回显帧
ExecuteWrite finally中activeWrite=null防止迟到回显

结论：改了activeWrite会影响Handle的分发逻辑，但有null保护 ✅

【问题4：改了busLock锁顺序是否影响死锁？】
当前顺序：busLock → io → gate
若改为：io → busLock → 可能死锁（OnData持有io时，WriteLoop持有busLock等待io）

结论：锁顺序是死锁防护的核心，改动需谨慎 ✅

六、潜在Bug与改进建议
================================================================================

【Bug 1：CrcOk数组越界】
位置：第698-703行
问题：frame.Length<2时，frame.Length-2为负数，导致数组越界
修复代码：
static bool CrcOk(byte[] frame)
{
    if (frame.Length < 2) return false;
    ushort calc = Crc16(frame, frame.Length - 2);
    ushort recv = (ushort)(frame[frame.Length - 2] | (frame[frame.Length - 1] << 8));
    return calc == recv;
}

【Bug 2：FrameLength潜在越界】
位置：第452-468行
问题：读取b[start+2]前未检查b.Count > start+2
修复代码：
if (b.Count - start < 3) return -1;
byte func = b[start + 1];
if (func == 0x02 || func == 0x03 || func == 0x04)
{
    if (b.Count <= start + 2) return -1;  // 新增检查
    int byteCount = b[start + 2];
    return 3 + byteCount + 2;
}

【Bug 3：参数模式退出竞态】
位置：第232-234行
问题：sp.Close()后OnData可能继续访问sp
修复代码：
running = false;
lock (io) { 
    if (sp.IsOpen) sp.Close(); 
}
Thread.Sleep(100);  // 等待OnData完成

【Bug 4：EnqueueReadTasks延迟投递竞态】
位置：第957-962行
问题：ThreadPool.QueueUserWorkItem中Thread.Sleep(delay)后Enqueue，
      若running=false，读任务可能入队但SendLoop已退出
修复代码：
ThreadPool.QueueUserWorkItem(_ =>
{
    Thread.Sleep(delay);
    if (running) readQueue.Enqueue(rr);
});

【Bug 5：VerifyPhysicalState内嵌在busLock内】
位置：第830行
问题：验证过程持有busLock，若验证失败重试写命令，会长时间阻塞SendLoop
分析：这是设计选择，确保验证和写命令的原子性，但可能影响实时性
建议：保持现状，因为验证是强闭环的关键

【Bug 6：activeWrite/activeRead/activeVerify的volatile语义】
位置：第55、98、90行
问题：volatile保证可见性，但不保证原子性（读写复合操作）
分析：当前代码中这些变量只在单线程写（ExecuteWrite/ExecuteRead/VerifyPhysicalState），
      多线程读（Handle），volatile足够 ✅
