TID 事务标识溢出分析
====================

一、核心一段（先直接回答）
会溢出，但安全。TID 是 ushort（2字节），范围 0~65535，每次请求 ++nextTid，到 65535 再 +1 回绕到 0（C# 默认 unchecked 上下文，ushort 溢出自然回绕不抛异常）。回绕是预期行为，不需要特殊处理。回绕后 TID=0 可能与 65536 次请求前的旧 TID=0 撞上，但误配对概率极低：TCP 可靠传输，迟到响应最多在 TimeoutMs=1000ms 内到达，而 65536 次请求要跑 65536×(100ms间隔+交互)≈2 小时，2 小时前的响应不可能还在路上。且 TID 匹配只是辅助校验，还有 curSlave 兜底。所以自然回绕够用，不需要改代码，加注释说明即可。

二、ushort 溢出机制（C# 原理）

【ushort 范围】0 ~ 65535（2^16-1），共 65536 个值

【++nextTid 的编译行为】
  nextTid 是 ushort
  ++nextTid 编译为：nextTid = (ushort)(nextTid + 1)
  过程：nextTid 提升为 int → +1 → 转回 ushort

  nextTid=65534 → +1=65535 → (ushort)65535=65535 ✓
  nextTid=65535 → +1=65536 → (ushort)65536=0（回绕）✓

【checked vs unchecked】
  unchecked 上下文（默认）：65536 转 ushort 截断高位 = 0，回绕，不抛异常
  checked 上下文：抛 OverflowException
  .NET 8 console 默认 unchecked，所以 ++nextTid 安全回绕

【会不会抛异常】不会。默认 unchecked，自然回绕。
  除非项目级设了 <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow> 或用了 checked 块。
  本项目没设，安全。

三、回绕后会不会误配对（关键风险评估）

【误配对条件】
  TID 回绕到 0 后，如果有迟到的旧响应也带 TID=0，Handle 里 tid==curTid 会误判匹配。
  需要同时满足：
  1.当前请求 TID=0（回绕后）
  2.有 65536 次前的旧请求 TID=0 的响应还在路上没处理
  3.旧响应恰好在新请求发出后到达

【概率分析】
  65536 次请求耗时：
    每轮 = 2站 × (IntervalMs=100ms + 交互≈10ms) ≈ 220ms
    65536 次 = 65536 / 2 × 220ms ≈ 7,209 秒 ≈ 2 小时
  
  旧响应要"还在路上"：
    TCP 可靠传输，响应要么在 TimeoutMs=1000ms 内到达，要么超时丢弃
    2 小时前的响应不可能还在路上（早超时了）
  
  结论：误配对概率 ≈ 0。要 2 小时前的响应拖 2 小时才到，TCP 早就重传/断开了。

【即使误配对的后果】
  TID 匹配只是第一道校验，后面还有：
  1.curSlave 校验：旧响应的 UnitID 要等于当前 curSlave
  2.功能码校验、数据解析
  3.最坏情况：解析出错误的温湿度（一次），下一轮就正常
  不是致命问题，且概率极低。

四、各语言/协议的 TID 处理对比

方式              | 做法                        | 溢出处理
------------------|----------------------------|------------------
本程序（ushort++）| ++nextTid 自然回绕          | 0→65535→0，不抛异常
显式取模          | nextTid = (ushort)(nextTid+1)| 同上，更明确
用 int 不回绕     | int nextTid; 发送时(ushort)(nextTid++ & 0xFFFF) | int 不溢出（2^31次够跑68年），取低16位回绕
Modbus 规范       | TID 由客户端任意，规范不规定溢出行为 | 多数实现自然回绕

本程序用 ushort++ 自然回绕，符合常见做法，不需要改。

五、要不要改代码

【不需要改】理由：
  1.ushort++ 默认 unchecked 回绕，行为正确
  2.回绕后误配对概率≈0（2小时前的响应不可能还在）
  3.有 curSlave 兜底，即使误配对也不致命
  4.加注释说明回绕即可，不改逻辑

【如果要更保险（可选，不改）】
  方案A：用 int 存 nextTid，发送时取低16位：
    int nextTid;
    ushort tid = (ushort)(++nextTid & 0xFFFF);
    int 不会溢出（2^31次≈68年），取低16位自然回绕，意图更明确

  方案B：显式取模：
    nextTid = (ushort)((nextTid + 1) % 65536);
    多一次取模运算，意义不大（ushort++已经回绕）

  本程序不采用——ushort++ 回绕已经是标准做法，加注释够。

六、诚实补充（所有我知道的信息）

1. C# 的 ++ 运算符对整数类型的溢出行为：
  在 unchecked 上下文回绕，checked 上下文抛异常。
  默认是 unchecked（项目级 CheckForOverflowUnderflow 默认 false）。
  所以 ++nextTid 在 65535 时安全回绕到 0，不会崩。

2. ushort 的 ++ 为什么不抛异常：
  C# 语言规范：++ 和 -- 等价于 x = (T)(x + 1) / x = (T)(x - 1)，
  转换 (T) 在 unchecked 时截断高位，不检查溢出。
  ushort 是 16 位，65536 = 0x10000，截断高 16 位 = 0x0000 = 0。

3. Modbus TCP 规范对 TID 的规定：
  "Transaction Identifier: Identification of a Modbus Request/Response transaction.
   It is used for transaction pairing by the client."
  规范没说溢出怎么办，由实现决定。自然回绕是业界通用做法。

4. 实际工业场景 TID 溢出几乎遇不到：
  - 温湿度监控每秒几次请求，65536 次要几小时
  - 程序通常不会连续跑那么久不重启
  - 即使跑了 2 小时回绕，误配对概率仍≈0

5. 如果是高频场景（每秒上千次请求），65536 次几十秒就回绕：
  - 仍安全，因为 TCP 响应在毫秒级到达，不会拖几十秒
  - 真正的风险是"回绕后 TID 恰好等于一个未处理的在途请求的 TID"
  - 但在途请求最多几个（等于从站数），TID 空间 65536，撞中概率 = 几个/65536 ≈ 0

6. curTid 和 nextTid 没有 volatile/Interlocked 保护：
  SendLoop 是唯一写者（++nextTid, curTid=tid），SendLoop 单线程不会自己跟自己竞态。
  Handle 在 ReceiveLoop 线程读 curTid，跨线程读 ushort 是原子的（16位对齐读写原子），
  但可见性不保证——不过这里 curTid 读到旧值最多误忽略一帧，不致命。
  如果要严格可见性可加 volatile，但 ushort 不能加 volatile（C# volatile 只支持部分类型），
  可改用 int 或 Interlocked。本程序没做，因为误忽略一帧可接受。

七、记忆口诀

「ushort TID 0~65535，++到顶回绕到0不抛异常（默认unchecked）；
 回绕误配对要2小时前响应还在，TCP早超时了概率≈0；
 TID匹配是辅助校验，curSlave兜底即使误配也不致命；
 自然回绕是业界标准，加注释说明够，不用改代码」
