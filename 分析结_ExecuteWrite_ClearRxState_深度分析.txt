一、ClearRxState功能解析
================================================================================

【代码位置】第348-352行
static void ClearRxState()
{
    lock (io) { if (sp.IsOpen) sp.DiscardInBuffer(); }
    lock (gate) { buf.Clear(); }
}

【功能分解】
┌───────────────────────────────────────────────────────────────────────────┐
│ 操作                        │ 作用                                          │
├─────────────────────────────┼───────────────────────────────────────────────┤
│ sp.DiscardInBuffer()        │ 清空串口驱动的接收缓冲区                      │
│                             │ 丢弃驱动层已收到但未读取的数据                │
├─────────────────────────────┼───────────────────────────────────────────────┤
│ buf.Clear()                 │ 清空应用程序的接收残帧                        │
│                             │ 丢弃已从驱动读出但未切帧的字节                │
└───────────────────────────────────────────────────────────────────────────┘

【锁顺序】io → gate（与OnData一致，不会死锁）

================================================================================
二、为什么每次重试前都要清理？
================================================================================

【核心原因】防止上一轮的迟到应答/残帧干扰本轮判定

【问题场景】
如果不清理，上一轮的迟到应答可能在下一轮WaitOne之前被Handle处理，
导致误判为"本轮应答已收到"，从而跳过重试。

================================================================================
三、反例构造（不清理的后果）
================================================================================

【反例1：迟到应答导致误判】
时序：
  T1: 第1次尝试发送0x05帧（请求1）
  T2: 从站收到请求1，但处理慢，应答延迟
  T3: WaitOne(50ms)超时，第1次失败
  T4: 第2次尝试发送0x05帧（请求2）
  T5: 请求2的应答还没到，但请求1的迟到应答到了
  T6: OnData触发，读取数据，buf.AddRange，DrainInLock
  T7: Handle(0x05回显) → activeWrite校验通过
  T8: Ack.Set() → WaitOne返回true
  T9: AckOk=true → 第2次尝试"成功"（实际是请求1的迟到应答）

结果：第2次尝试"成功"，但实际上是从站对请求1的应答，不是请求2的应答。
      请求2可能根本没被从站收到，或者从站正在处理。

【修复方案】
在T4（第2次尝试前）调用ClearRxState()：
  - sp.DiscardInBuffer() → 丢弃驱动缓冲里的请求1的迟到应答
  - buf.Clear() → 丢弃已读出的请求1的残帧

这样T5时，请求1的迟到应答被丢弃，T6时OnData不会收到旧数据，
T8时WaitOne会继续等待，直到请求2的真正应答或超时。

================================================================================

【反例2：残帧导致帧解析混乱】
时序：
  T1: 第1次尝试发送0x05帧
  T2: 从站应答，但只发了前4字节（被干扰，帧不完整）
  T3: OnData触发，读取4字节，buf.AddRange
  T4: DrainInLock → FrameLength返回-1（数据不够），不切帧
  T5: WaitOne(50ms)超时，第1次失败
  T6: 第2次尝试发送0x05帧
  T7: 从站应答完整8字节
  T8: OnData触发，读取8字节，buf.AddRange（现在buf里有4+8=12字节）
  T9: DrainInLock → FrameLength检查前3字节，发现func=0x05，len=8
  T10: buf.CopyTo(0, frame, 0, 8) → 取的是前4字节（残帧）+ 后4字节（新帧的前半）
  T11: CrcOk(frame) → CRC失败，滑动1字节
  T12: 继续滑动... 最终可能取到新帧，也可能取不到

结果：残帧混入新帧，导致帧解析失败，可能需要多次滑动，增加延迟。

【修复方案】
在T6（第2次尝试前）调用ClearRxState()：
  - buf.Clear() → 丢弃4字节残帧
这样T8时，buf里只有新帧的8字节，T9时FrameLength返回8，T10时取到完整新帧。

================================================================================

【反例3：多请求并发时的错配】
时序：
  T1: WriteLoop持有busLock，第1次尝试写从站1
  T2: 从站1迟到应答到达，OnData读取，buf.AddRange
  T3: WriteLoop第1次超时，第2次尝试写从站1
  T4: 此时SendLoop TryEnter(busLock)成功，开始周期轮询从站2
  T5: 从站2应答到达，OnData读取，buf.AddRange（现在buf里有从站1残帧+从站2完整帧）
  T6: WriteLoop重新获取busLock，第2次尝试写从站1
  T7: 从站1应答到达，OnData读取，buf.AddRange（现在buf里有3帧数据）
  T8: Handle处理从站2的帧（curSlave=0x02），校验通过，pollAck.Set()
  T9: 但这是从站2的帧，不是从站1的帧

结果：从站2的帧被误判为从站1的帧（如果curSlave没被正确设置）。

【修复方案】
每次发请求前ClearRxState()，确保buf里只有当前请求的应答。

四、边界条件分析
================================================================================

【边界条件1：串口已关闭】
ClearRxState()中：if (sp.IsOpen) sp.DiscardInBuffer();
如果串口已关闭，sp.DiscardInBuffer()不会执行，不会抛异常 ✅

【边界条件2：buf为空】
buf.Clear()在buf为空时是空操作，不会抛异常 ✅

【边界条件3：并发调用】
ClearRxState()被多个线程调用：
- SendLoop超时分支（第324行）
- ExecuteWrite每次重试前（第800行）
- ExecuteRead每次重试前（第978行）

这些调用都在busLock内（SendLoop是TryEnter成功，WriteLoop是lock(busLock)），
所以同一时刻只有一个线程在执行ClearRxState() ✅

【边界条件4：锁顺序】
ClearRxState()的锁顺序：io → gate
OnData的锁顺序：io → gate（先lock(io)读数据，再lock(gate)AddRange+DrainInLock）
锁顺序一致，不会死锁 ✅

五、"改了A是否影响B"分析
================================================================================

【问题1：改了ClearRxState是否影响Ack？】
分析：
- ClearRxState()不含Ack.Reset()，调用方各自Reset自己的Ack
- ExecuteWrite在第800行调用ClearRxState()，第801行Reset wr.Ack
- 如果ClearRxState()也Reset wr.Ack，会导致：
  T1: ClearRxState() → wr.Ack.Reset()
  T2: 从站应答到达，Handle() → wr.Ack.Set()
  T3: WaitOne(50ms) → 立即返回（因为Ack已被Set）
  T4: 但这是上一轮的迟到应答，不是本轮的应答

结论：ClearRxState()不含Ack.Reset()是正确的，改了会影响Ack的语义 ✅

【问题2：改了ClearRxState是否影响activeWrite？】
分析：
- ClearRxState()不操作activeWrite
- activeWrite在ExecuteWrite的finally中清零
- 如果ClearRxState()也清零activeWrite，会导致：
  T1: 第1次尝试，activeWrite = wr
  T2: ClearRxState() → activeWrite = null
  T3: 迟到应答到达，Handle() → activeWrite == null，忽略
  T4: 但这是本轮的应答，不是迟到应答

结论：ClearRxState()不操作activeWrite是正确的，改了会影响activeWrite的语义 ✅

【问题3：改了ClearRxState的锁顺序是否影响死锁？】
分析：
- 当前顺序：io → gate
- 若改为：gate → io，可能与OnData死锁：
  T1: ClearRxState() lock(gate)
  T2: OnData lock(io) → 等待gate
  T3: ClearRxState() 等待io → 死锁

结论：锁顺序是死锁防护的核心，改动需谨慎 ✅

六、线程交错时序穷举（ClearRxState的作用）
================================================================================

【场景1：正常重试】
时序：
  T1: ExecuteWrite 第1次尝试
  T2: ClearRxState() → 清空buf和驱动缓冲
  T3: activeWrite = wr
  T4: SendFrame() → 发送0x05
  T5: WaitOne(50ms) → 超时
  T6: ClearRxState() → 清空buf和驱动缓冲（防止迟到应答）
  T7: activeWrite = wr（同一请求）
  T8: SendFrame() → 重发0x05
  T9: 从站应答到达，OnData读取，Handle分发
  T10: Ack.Set() → WaitOne返回true
  T11: AckOk=true → 成功

【场景2：迟到应答被清理】
时序：
  T1: ExecuteWrite 第1次尝试
  T2: ClearRxState() → 清空
  T3: SendFrame() → 发送0x05
  T4: WaitOne(50ms) → 超时
  T5: ClearRxState() → 清空（此时第1次应答刚到达，被丢弃）
  T6: activeWrite = wr
  T7: SendFrame() → 重发0x05
  T8: 从站应答到达，OnData读取，Handle分发
  T9: Ack.Set() → WaitOne返回true

【场景3：不清理的后果（反例重现）】
时序：
  T1: ExecuteWrite 第1次尝试
  T2: 不调用ClearRxState()
  T3: SendFrame() → 发送0x05
  T4: WaitOne(50ms) → 超时
  T5: activeWrite = wr
  T6: SendFrame() → 重发0x05
  T7: 第1次应答到达，OnData读取，Handle分发
  T8: Ack.Set() → WaitOne返回true（误判）
  T9: AckOk=true → 第2次尝试"成功"（实际是第1次的应答）

================================================================================
七、总结
================================================================================

【ClearRxState的作用】
1. 清空串口驱动缓冲：丢弃驱动层已收到但未读取的数据
2. 清空应用程序残帧：丢弃已从驱动读出但未切帧的字节
3. 防止迟到应答干扰本轮判定
4. 防止残帧导致帧解析混乱
5. 防止多请求并发时的错配

【为什么每次重试前都要清理】
1. 重试意味着上一轮失败，上一轮的应答是"迟到应答"
2. 迟到应答如果在下一轮WaitOne之前到达，会被误判为本轮应答
3. 清理后，本轮WaitOne只等待本轮的应答

【设计选择】
1. ClearRxState()不含Ack.Reset()：调用方各自Reset自己的Ack
2. ClearRxState()不操作activeWrite：防止迟到应答拿旧wr比对
3. 锁顺序io→gate：与OnData一致，不会死锁

【结论】
ClearRxState()在每次重试前调用是必要的，是防止迟到应答干扰的关键设计。
如果不清理，会导致误判、帧解析混乱、多请求错配等问题。
