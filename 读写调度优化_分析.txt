【1. 当前程序是否需要这个优化】
================================================================================

  现状1：SendLoop 被注释了（第141行 `// tx.Start();`）
    → 交互模式下读轮询根本没启动，WriteLoop 独占总线，不存在读写冲突。
    → 优化无对象。

  现状2：参数模式下 SendLoop 也不启动（第116-120行只启动 FrameGapLoop 和 WriteLoop）
    → 参数模式只做一次写，也不存在冲突。

  现状3：即使取消注释让 SendLoop 启动，当前靠什么防冲突？
    → 靠 lock(io) 串行化所有 sp.Write。
    → SendLoop 第176行 lock(io){sp.Write} 和 ExecuteWrite 第552行 lock(io){sp.Write}
      互斥，同一时刻只有一个能拿到 io 锁，物理上不会两帧同时上总线。
    → 但这只是"发送瞬间互斥"，不是"整个事务互斥"——
      SendLoop 发完释放 io 锁，ExecuteWrite 抢到 io 锁发写帧，
      此时从站可能还在回 SendLoop 的读应答，总线撞车。

  ★ 结论：当前程序如果取消 SendLoop 注释，确实存在"读事务未完成时被写事务打断"的风险。
    用户提出的"写时暂停读"需求是合理的。但实现方式需要斟酌。

================================================================================
【2. 简单 bool 标志位为什么不行】
================================================================================

  假设用户设想的实现：
    static volatile bool writing = false;

    WriteLoop:
      writing = true;
      ExecuteWrite(wr);
      writing = false;

    SendLoop:
      while (running) {
        if (writing) { Thread.Sleep(1); continue; }   // 写时跳过
        ...发读请求...
      }

  问题1：竞态条件（check-then-act 不是原子的）
    SendLoop 检查 writing==false → 决定发 → 此时 WriteLoop 恰好 writing=true
    → SendLoop 已经过了检查点，照样发读帧，写帧也发，总线撞车。
    时间窗口：检查 writing 和 sp.Write 之间有 gap，WriteLoop 可在这个 gap 里置位。
    ★ volatile 只保证可见性，不保证"检查+动作"的原子性。

  问题2：反向竞态（WriteLoop 等 SendLoop 让出，但 SendLoop 正在等应答）
    SendLoop 发完读请求 → frameReceived.WaitOne(50ms) 阻塞等应答
    → 此时 writing=true，SendLoop 在等应答，没在"发"，但事务没结束
    → WriteLoop 看到"SendLoop 没在发"（其实它在等），发写帧，总线撞车
    ★ 标志位只保护"发送瞬间"，不保护"整个事务（发+等应答）"。

  问题3：SendLoop 让出后，WriteLoop 发完，SendLoop 恢复，但旧读应答还在路上
    SendLoop 发读 → 让出 → WriteLoop 发写+等写回显 → WriteLoop 完成 → SendLoop 恢复
    → 此时从站的读应答才姗姗来迟，被 Handle 当成写回显的噪声丢弃
    → SendLoop 的读请求永远超时，数据丢失
    ★ 暂停-恢复的边界清状态没做，旧应答污染。

  ★ 简单 bool 标志位的 3 个问题都源于"标志位只表达瞬时状态，不表达事务边界"。

【3. 正确的做法是什么】
================================================================================

  要正确实现"写时暂停读"，需要表达"整个写事务"的边界，而非瞬时标志。

  ── 方案A：用 lock 把整个写事务包起来（最简单正确）──

    static readonly object busLock = new object();   // 总线事务锁

    WriteLoop:
      lock (busLock) { ExecuteWrite(wr); }            // 整个写事务持锁

    SendLoop:
      while (running) {
        if (!Monitor.TryEnter(busLock, 0)) { Thread.Sleep(1); continue; }
        try { ...发读请求+等应答... }
        finally { Monitor.Exit(busLock); }
      }

    特点：
      - 写事务持 busLock 期间，读事务 TryEnter 失败跳过，不会发读帧
      - 读事务持 busLock 期间（含等应答 50ms），写事务 lock(busLock) 阻塞等
      - 事务边界完整，无竞态
    缺点：
      - 写事务可能等读事务释放（最多 50ms+发送时间），写延迟增加
      - 读事务 TryEnter 失败就跳过，该轮读丢失（可接受，下一轮补）

  ── 方案B：用 ReaderWriterLockSlim（读多写少场景标准做法）──

    static readonly ReaderWriterLockSlim busLock = new ReaderWriterLockSlim();

    WriteLoop:
      busLock.EnterWriteLock();
      try { ExecuteWrite(wr); } finally { busLock.ExitWriteLock(); }

    SendLoop:
      if (!busLock.TryEnterReadLock(0)) { Thread.Sleep(1); continue; }
      try { ...发读请求+等应答... } finally { busLock.ExitReadLock(); }

    特点：
      - 写锁独占，读锁共享（但本程序读也是单线程，共享没意义）
      - 比 lock 更明确表达"写优先"
    缺点：
      - 对本程序读单线程的场景，ReaderWriterLockSlim 比 lock 更重，无收益
      - 不如方案A简单

  ── 方案C：用 AutoResetEvent 信号（写优先，读让步）──

    static readonly AutoResetEvent busFree = new AutoResetEvent(true);

    WriteLoop:
      busFree.WaitOne();          // 等总线空
      ExecuteWrite(wr);
      busFree.Set();              // 释放总线

    SendLoop:
      if (!busFree.WaitOne(0)) { Thread.Sleep(1); continue; }  // 非阻塞试
      ...发读请求+等应答...
      busFree.Set();

    特点：
      - 信号量表达"总线占用/空闲"，比 bool 标志位原子
      - WaitOne(0) 非阻塞试，拿不到就跳过
    缺点：
      - 和方案A本质相同，但 AutoResetEvent 语义不如 lock 直观
      - 容易忘记 Set 导致死锁

  ★ 推荐方案A（lock + TryEnter）：最简单、最正确、最易理解。
    简单 bool 标志位不行（第2节的 3 个问题）。

【4. 做了之后能带来什么收益】
================================================================================

  收益1：写命令不被读轮询打断
    现状（如果 SendLoop 启动）：写命令发帧时，SendLoop 可能也在发读帧，
    两帧在总线上叠加，从站无法解析。
    优化后：写事务期间读让步，总线独占给写，写完成再恢复读。

  收益2：写命令的应答不会被读轮询的应答混淆
    现状：写命令等 0x05 回显时，从站可能回的是上一轮读的 0x03 应答，
    Handle 靠功能码区分能挡住，但增加了处理负担。
    优化后：写事务期间没有读请求发出，不会有读应答混淆。

  收益3：写命令延迟更稳定
    现状：写命令可能和读请求竞争 io 锁，发送时机不确定。
    优化后：读让步，写立即拿到总线，延迟可预测。

  ★ 收益大小取决于"读轮询频率"和"写命令频率"。
    本程序读间隔 15ms，写命令用户手动触发（频率远低于读），
    冲突概率本就不高，收益有限。

================================================================================
【5. 做了之后会引入什么风险】
================================================================================

  风险1：写事务期间读数据中断
    写事务含 3 次重试，每次 50ms 超时 + 15ms 间隔 = 195ms
    最坏情况：写命令卡住 3 次重试都超时 = 195ms 读中断
    → 温湿度采样出现近 200ms 空洞。
    → 对慢变量（温湿度）可接受，对快变量可能丢数据。

  风险2：写命令可能被读事务阻塞
    读事务持 busLock 期间（发+等应答 ≈ 18ms+50ms = 68ms），写命令 lock(busLock) 阻塞等。
    → 用户感觉写命令"卡顿"。
    → 可接受（68ms 人感知不到），但需知道。

  风险3：死锁风险（如果锁顺序不一致）
    busLock 和 io/gate 的获取顺序必须统一。
    WriteLoop: busLock → io → gate
    SendLoop:  busLock → io → gate
    OnData:    io → gate（不涉及 busLock）
    → 只要 busLock 永远在最外层，不会死锁。
    → 但如果某处忘了先 busLock 再 io，可能死锁。需要约定。

  风险4：SendLoop 让步后恢复时，旧读应答污染
    SendLoop 发读 → 让步给写 → 写完成 → SendLoop 恢复发新读
    → 上一轮读的迟到应答可能在新读请求后才到
    → 现状已有 frameReceived.Reset() 防这个，但优化后让步-恢复边界要额外清状态
    → 复杂度增加。

  风险5：本程序 SendLoop 被注释，优化无对象
    → 如果不打算取消注释，这个优化是"为不存在的代码做优化"，无意义。
    → 如果打算取消注释让读写并存，才需要这个优化。

【6. 决策建议】
================================================================================

  情况1：保持 SendLoop 注释（只做写命令）
    → 不需要这个优化。WriteLoop 独占总线，无冲突。
    → 做了是死代码。

  情况2：取消 SendLoop 注释（读写并存）
    → 需要这个优化，但不用简单 bool 标志位，用方案A（lock + TryEnter）。
    → 同时要处理让步-恢复边界的清状态。
    → 收益：写命令不被读打断，应答不混淆。
    → 代价：读有近 200ms 空洞，写有近 68ms 延迟，可接受。

  情况3：未来要支持高频读+并发写
    → 用方案B（ReaderWriterLockSlim）+ 写优先策略（TryEnterWriteLock 优先）。
    → 当前场景过度设计，不推荐。

  ★ 当前建议：不做。
    理由：SendLoop 被注释，优化无对象。如果未来取消注释，再用方案A。

【7. 如果要做，方案A的伪代码】
================================================================================

  static readonly object busLock = new object();

  static void SendLoop() {
      int idx = 0;
      while (running) {
          if (!Monitor.TryEnter(busLock, 0)) { Thread.Sleep(1); continue; }
          try {
              byte id = Slaves[idx];
              byte[] frame = ...;
              curSlave = id;
              if (!SendFrame(frame)) break;
              if (!frameReceived.WaitOne(TimeoutMs)) {
                  ClearRxState();
                  frameReceived.Reset();
              }
              idx = (idx + 1) % Slaves.Length;
          }
          finally { Monitor.Exit(busLock); }
          Thread.Sleep(IntervalMs);
      }
  }

  static void WriteLoop() {
      while (running) {
          if (!writeQueue.TryDequeue(out var wr)) { Thread.Sleep(5); continue; }
          lock (busLock) {                    // ★ 写事务独占总线
              wr.Result = ExecuteWrite(wr);
          }
          wr.Completed.Set();
      }
  }

  关键点：
    - SendLoop 用 TryEnter 非阻塞试，拿不到就跳过（写优先）
    - WriteLoop 用 lock 阻塞等，保证写命令一定能执行
    - busLock 在 io/gate 外层，锁顺序统一
    - ExecuteWrite 内部的 lock(io)/lock(gate) 不变

【8. 总结】
================================================================================

  Q: 能用全局标志位让 SendLoop 在写时暂停吗？
  A: 需求合理（RS485 半双工要求），但简单 bool 标志位不行：
     - 竞态条件（check-then-act 不原子）
     - 只保护发送瞬间，不保护整个事务（发+等应答）
     - 暂停-恢复边界清状态没做，旧应答污染

  正确做法：用 lock + TryEnter 表达事务边界（方案A）。
  但当前程序 SendLoop 被注释，优化无对象，不建议做。
  如果未来取消注释让读写并存，再用方案A，同时处理让步-恢复清状态。

  一句话：需求对，实现方式（简单 bool）不对，当前不需要（SendLoop没启动）。
