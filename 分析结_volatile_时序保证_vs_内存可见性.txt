一、问题核心：时序保证 ≠ 内存可见性
================================================================================

【用户的疑问】
既然时序上已经保证了"接收线程收到回显时，activeWrite早已指向当前wr"，
为什么还需要volatile？

【核心回答】
"时序保证"和"内存可见性"是两个完全不同的维度：

┌───────────────────────────────────────────────────────────────────────────┐
│ 维度        │ 含义                                                         │
├─────────────┼─────────────────────────────────────────────────────────────┤
│ 时序保证    │ 逻辑上"先赋值后读取"的顺序关系                                │
│             │ 程序员推理：T1先执行activeWrite=wr，T2后执行Handle读取       │
│             │ 所以T2一定能看到T1的赋值                                     │
├─────────────┼─────────────────────────────────────────────────────────────┤
│ 内存可见性  │ 物理上"赋值后的值是否对其他线程立即可见"                     │
│             │ CPU缓存、寄存器、JIT优化可能导致：                            │
│             │ 写线程已执行赋值，但读线程看到的是旧值                        │
└───────────────────────────────────────────────────────────────────────────┘

【类比】
时序保证 = "你先写了信，我后读信"（逻辑顺序正确）
内存可见性 = "信是否已经从你的桌上送到我的桌上"（物理传递是否完成）

没有volatile时，可能出现：
- 你已经写了信（赋值已完成）
- 但信还在你的抽屉里（CPU缓存/寄存器）
- 我去读信，看到的是上一封信（旧值）

================================================================================
二、没有volatile时可能出什么问题？
================================================================================

【场景：CPU缓存导致读线程看到旧值】

线程A（WriteLoop/ExecuteWrite）：
  activeWrite = wr;           // 写入：将wr的引用写入activeWrite
  SendFrame(frame);           // 发送帧
  wr.Ack.WaitOne(TimeoutMs);  // 等待应答

线程B（OnData/Handle）：
  var aw = activeWrite;       // 读取：读取activeWrite的当前值
  if (aw == null) return;     // 如果为null，忽略
  // ... 使用aw处理回显

【没有volatile时的问题】

1. JIT编译器优化：
   JIT可能将activeWrite的读取优化为"只读一次，缓存在寄存器中"
   如果Handle方法被内联或循环调用，JIT可能将activeWrite的读取提升到循环外
   导致Handle始终看到循环开始时的旧值（null或上一个wr）

2. CPU缓存一致性：
   线程A在CPU核心1上执行，将activeWrite=wr写入核心1的L1缓存
   线程B在CPU核心2上执行，从核心2的L1缓存读取activeWrite
   如果核心1的缓存还没刷新到主内存，核心2读到的是旧值

3. 编译器重排序：
   C#编译器或JIT可能重排序指令：
   原始顺序：activeWrite = wr → SendFrame → WaitOne
   重排序后：SendFrame → activeWrite = wr → WaitOne
   如果SendFrame触发了串口发送，从站应答很快返回，
   Handle在activeWrite赋值之前就执行了，读到null或旧值

三、反例构造（没有volatile的具体后果）
================================================================================

【反例1：JIT寄存器缓存】
时序：
  T1: ExecuteWrite执行 activeWrite = wr（写入CPU核心1的L1缓存）
  T2: SendFrame发送0x05帧
  T3: 从站快速应答，OnData在CPU核心2上触发
  T4: Handle读取activeWrite → CPU核心2的L1缓存还是旧值（null）
  T5: aw == null → 忽略回显
  T6: WaitOne超时 → 重试

结果：从站已经应答，但因为Handle读到null，回显被忽略，导致不必要的重试。

【反例2：编译器重排序】
时序：
  T1: JIT将 activeWrite = wr 和 SendFrame 重排序
  T2: SendFrame先执行 → 发送0x05帧
  T3: 从站快速应答 → OnData触发 → Handle读取activeWrite
  T4: activeWrite还是旧值（null或上一个wr）
  T5: 如果是null → 忽略；如果是旧wr → 比对失败（整帧比对会拒绝）

结果：回显被忽略或拒绝，导致不必要的重试。

【反例3：循环中的读取优化】
假设Handle被某种方式循环调用（虽然当前代码不是这样）：
  while (true) {
      var aw = activeWrite;  // JIT可能将此读取优化为"只读一次"
      if (aw != null) ProcessWrite(aw);
  }

JIT优化后：
  var aw = activeWrite;  // 只在循环外读一次
  while (true) {
      if (aw != null) ProcessWrite(aw);
  }

结果：aw永远是循环开始时的值，后续的activeWrite赋值永远看不到。

四、volatile关键字的作用
================================================================================

【volatile的精确语义（C#）】

1. 读语义：volatile读保证读到的是"最新写入的值"
   - 不使用寄存器缓存
   - 从主内存（或确保缓存一致的层级）读取
   - 编译器不能将volatile读优化掉或重排序到前面

2. 写语义：volatile写保证"立即对其他线程可见"
   - 不停留在CPU缓存中
   - 刷新到主内存（或发出缓存一致性信号）
   - 编译器不能将volatile写重排序到后面

【volatile对activeWrite的作用】

写线程（ExecuteWrite）：
  activeWrite = wr;  // volatile写：确保wr的引用立即对其他线程可见

读线程（Handle）：
  var aw = activeWrite;  // volatile读：确保读到的是最新值，不是缓存旧值

【为什么时序保证不够？】

时序保证的是"逻辑顺序"：先赋值后读取。
但时序保证不了"物理可见性"：赋值后的值何时对其他线程可见。

volatile补充的正是时序保证不了的"物理可见性"：
- 确保赋值后的值立即对其他线程可见
- 确保读取时拿到的是最新值
- 防止编译器/CPU的重排序优化

================================================================================
五、C#内存模型 vs Java内存模型
================================================================================

【C#内存模型】
- 默认：普通字段不做可见性保证
- volatile：保证可见性（读最新值，写立即可见）
- lock：保证可见性 + 原子性（Monitor.Enter/Exit隐含内存屏障）

【为什么lock不够？】
activeWrite的赋值在ExecuteWrite中，不在lock块内：
  activeWrite = wr;           // 不在lock内
  SendFrame(frame);           // SendFrame内部有lock(io)，但activeWrite不在其中
  wr.Ack.WaitOne(TimeoutMs);  // 不在lock内

Handle的读取也不在lock块内：
  var aw = activeWrite;       // 不在lock内
  if (aw == null) return;

如果activeWrite的读写都在lock块内，lock的内存屏障会保证可见性，不需要volatile。
但当前代码中activeWrite的读写不在同一个lock块内，所以需要volatile。

【替代方案】
1. 用lock保护activeWrite的读写 → 可行但增加锁开销
2. 用volatile → 轻量级，只保证可见性，不保证原子性
3. 用Interlocked.Exchange/Read → 保证可见性 + 原子性

当前代码选择volatile，因为：
- activeWrite是引用类型（指针），读写本身是原子的（32位平台上指针读写原子）
- 只需要可见性保证，不需要复合操作的原子性
- volatile是最轻量的方案

六、线程交错时序穷举（volatile的作用）
================================================================================

【场景1：有volatile - 正常流程】
T1: ExecuteWrite: activeWrite = wr（volatile写，立即刷新到主内存）
T2: ExecuteWrite: SendFrame(frame)（发送0x05帧）
T3: 从站应答，OnData触发
T4: Handle: var aw = activeWrite（volatile读，从主内存读最新值=wr）
T5: aw != null，校验通过，Ack.Set()
T6: WaitOne返回true，成功 ✅

【场景2：无volatile - JIT缓存导致旧值】
T1: ExecuteWrite: activeWrite = wr（写入CPU核心1的L1缓存，未刷新到主内存）
T2: ExecuteWrite: SendFrame(frame)
T3: 从站应答，OnData在CPU核心2上触发
T4: Handle: var aw = activeWrite（从CPU核心2的L1缓存读，得到旧值=null）
T5: aw == null，忽略回显
T6: WaitOne超时，重试 ❌

【场景3：无volatile - 编译器重排序】
T1: JIT重排序：SendFrame先执行
T2: SendFrame(frame) → 发送0x05帧
T3: 从站快速应答，OnData触发
T4: Handle: var aw = activeWrite（activeWrite还没赋值，读到null）
T5: aw == null，忽略回显
T6: activeWrite = wr（赋值终于执行了，但回显已经被忽略了）
T7: WaitOne超时，重试 ❌

【场景4：有volatile - 防止重排序】
T1: volatile写 activeWrite = wr（禁止重排序到后面）
T2: SendFrame(frame)（不能重排序到volatile写前面）
T3: 从站应答，OnData触发
T4: Handle: volatile读 activeWrite（确保读到最新值=wr）
T5: aw != null，校验通过 ✅

================================================================================
七、总结
================================================================================

【核心结论】
时序保证 ≠ 内存可见性。
时序保证的是"逻辑顺序"，volatile保证的是"物理可见性"。

【为什么需要volatile】
1. 防止JIT编译器将读取优化为寄存器缓存
2. 防止CPU缓存导致读线程看到旧值
3. 防止编译器/CPU重排序导致赋值顺序被打乱

【volatile的精确作用】
1. volatile写：立即刷新到主内存，禁止重排序到后面
2. volatile读：从主内存读最新值，禁止重排序到前面

【为什么不用lock】
activeWrite的读写不在同一个lock块内，lock的内存屏障不覆盖。
volatile是最轻量的可见性保证方案。

【为什么不用Interlocked】
activeWrite是引用类型，读写本身已是原子的。
只需要可见性保证，不需要复合操作的原子性。
volatile足够且更轻量。
