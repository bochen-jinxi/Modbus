============================================================
DiscardInBuffer + buf.Clear 不合理清理的情况分析
============================================================
分析时间: 2026-11-03
问题: 前次分析说清理都是合理的，哪种情况是不合理的清理?
============================================================

【一、直接回答】
------------------------------------------------------------
存在两类不合理清理 (都是真实风险):

类1: ExecuteWrite 清掉了"当前写帧回显的前半截"
  场景: 从站回显分两次到达 (拆包)，第一次到一半时
        ExecuteWrite 下一轮重试清缓冲，清掉了前半截
  后果: 完整回显被拆成两段，后半截变成残帧，CRC 失败
  严重性: 中 (导致重试，但最终能成功; 极端下重试耗尽失败)

类2: SendLoop 超时清缓冲清掉了"刚好到达的有效应答"
  场景: SendLoop 等 50ms 超时，在执行 DiscardInBuffer 的
        瞬间应答刚好到达驱动缓冲，被清掉
  后果: 本该成功的读轮次变超时，温湿度少刷新一次
  严重性: 低 (下一轮轮询会重新读，数据短暂缺失)

类3 (理论存在但当前代码已规避):
  OnData 已 Read 出数据到 tmp，但还没 lock(gate) AddRange，
  此时 ExecuteWrite 的 buf.Clear 执行 → tmp 数据不受影响
  (buf.Clear 只清 buf，不清 tmp)，AddRange 照常加入
  → 不是问题，代码注释 243 行已说明此竞态被 lock(gate) 规避

下面逐一详述。

【二、类1: ExecuteWrite 清掉回显前半截 (真实风险)】
------------------------------------------------------------
时序:

  t=0:   ExecuteWrite attempt=1
         sp.Write(写帧)                    // 发出 8 字节写帧
  t=18:  从站开始回显 8 字节 (0x05 应答)
         但串口驱动可能分两次投递:
  t=18:  OnData 第1次: 收到前 4 字节 → buf=[4字节]
         (不足 8 字节，DrainInLock 不切帧，buf 保留)
  t=20:  ExecuteWrite attempt=1 的 Ack.WaitOne(50ms) 超时
         (因为回显还没完整到达，Handle 没被调用，Ack 没 Set)
  t=20:  ExecuteWrite attempt=2 开始
         lock(io) sp.DiscardInBuffer()    // ★ 驱动里可能还有后4字节!
         lock(gate) buf.Clear()           // ★ buf 里的前4字节被清!
  t=21:  OnData 第2次: 收到后 4 字节 → buf=[4字节]
         (但前4字节已被清，这4字节是残帧)
  t=25:  FrameGapLoop 判定帧结束 → Handle(后4字节)
         → CRC 失败 (只有半截) → 丢弃

  ★ 不合理之处:
    attempt=1 的回显正在到达 (前4字节已在 buf)，
    attempt=2 的清缓冲把它清了，导致:
    - attempt=1 本可在 t=22 成功 (等后4字节到齐)
    - 被清后，attempt=2 要重发，浪费总线时间
    - 后4字节变残帧，CRC 失败

  根因: ExecuteWrite 超时后立即清缓冲，没考虑
        "回显可能正在途中，只是还没到齐"。

  为什么说"合理中带不合理":
    - 合理: attempt=1 已超时放弃，清掉它的残留防止干扰 attempt=2
    - 不合理: 回显正在到达，清掉前半截制造了残帧

  实际影响:
    - 9600bps 下 8 字节回显 = 8.3ms，OnData 通常一次收齐
    - 拆包概率低 (除非系统繁忙/线程调度延迟)
    - 即使拆包，attempt=2 重发能成功
    - 最坏: 3次都撞上拆包 → 写失败 (概率极低)

【三、类2: SendLoop 清掉刚好到达的应答 (真实风险)】
------------------------------------------------------------
时序:

  t=0:   SendLoop 拿到 busLock
         sp.Write(读请求帧)               // 发出读请求
  t=49:  从站应答正在途中 (假设 49ms 才到，接近超时边界)
  t=50:  SendLoop frameReceived.WaitOne(50ms) 超时
         (应答还没被 Handle 处理，frameReceived 没 Set)
  t=50:  SendLoop 执行清缓冲:
         lock(io) sp.DiscardInBuffer()    // ★ 应答字节在驱动缓冲里!
         lock(gate) buf.Clear()           // buf 可能空 (应答还没到 OnData)
  t=51:  应答字节已被 DiscardInBuffer 清掉，永远不会触发 OnData

  ★ 不合理之处:
    应答在 t=49 已到达串口驱动缓冲，只是 OnData 还没被调度执行
    (OnData 是事件回调，依赖 .NET 串口事件线程池调度，有延迟)
    SendLoop 在 t=50 超时清缓冲，把"已到达但还没被 OnData 处理"的
    应答清掉了。

  根因: 超时判定 (frameReceived.WaitOne) 与数据到达 (驱动缓冲)
        之间有"事件调度延迟"缝隙。frameReceived 没 Set 不代表
        数据没到，只代表 Handle 没执行完。数据可能已在驱动缓冲。

  实际影响:
    - 一次温湿度读轮次丢失 (下一轮 15ms 后重读)
    - 不会累积 (清缓冲后状态干净)
    - 用户几乎无感 (除非 Verbose 模式看到超时日志)

  对比 ExecuteWrite 的同类问题:
    ExecuteWrite 也有这个风险 (Ack 超时但回显在驱动缓冲)，
    但 ExecuteWrite 有重试 (最多3次)，且重试前清缓冲是"故意"的
    (要清掉上一轮残留)。SendLoop 没重试，清了就清了。

【四、类3: OnData 与 buf.Clear 的竞态 (已规避)】
------------------------------------------------------------
时序:

  t=0: OnData 触发，lock(io) sp.Read → tmp=[数据]
  t=1: OnData 准备 lock(gate) AddRange(tmp)
       但此时 ExecuteWrite 正持有 lock(gate) 执行 buf.Clear
  t=2: ExecuteWrite buf.Clear 完成，释放 lock(gate)
  t=3: OnData 拿到 lock(gate)，AddRange(tmp) → buf=[数据]

  ★ 数据没丢! 因为:
    - DiscardInBuffer 清的是"驱动缓冲"，tmp 已 Read 出来，不受影响
    - buf.Clear 清的是"buf 列表"，发生在 OnData 的 AddRange 之前
      (OnData 还在等 lock(gate))，清的是旧数据，不是 tmp
    - AddRange 在 Clear 之后，新数据正常加入

  代码注释 243 行明确说了这个竞态:
    "AddRange 和 DrainInLock 合并到同一个 lock(gate) 块，原子切帧。
     否则 buf.Clear 可在 AddRange 后、Drain 前插入，
     导致数据加了还没切帧就被清掉。"

  → 此情况已被 lock(gate) 规避，不是问题。

  但有一个更细的竞态 (代码没处理):
    t=0: OnData lock(io) sp.Read → tmp (读出 N 字节)
    t=1: ExecuteWrite lock(io) sp.DiscardInBuffer()
         → 此时驱动缓冲里可能还有 M 字节 (OnData 只读了 N)
         → M 字节被清!
    t=2: OnData lock(gate) AddRange(tmp) → buf 只有 N 字节
         → 丢失了 M 字节

  ★ 这个竞态存在! lock(io) 保证了 Read 和 DiscardInBuffer 互斥，
    但不保证"Read 完之后 DiscardInBuffer 之前没有新数据到达"。
    实际上 sp.Read 读的是"当前 BytesToRead"，读完瞬间新数据
    可能又到。DiscardInBuffer 清的就是"Read 之后到达的新数据"。

  严重性: 低。丢失的是"刚好在 Read 和 DiscardInBuffer 之间
    到达的几个字节"，通常是某帧的尾部，下一帧的头部。
    - 如果是当前回显的尾部: 帧不完整，CRC 失败，超时重试
    - 如果是下一帧的头部: 下一帧残缺，但 FrameGapLoop 会处理残帧

【五、总结: 三类不合理清理】
------------------------------------------------------------
类1: ExecuteWrite 清掉回显前半截 (拆包场景)
  不合理点: 回显正在到达，清掉前半截制造残帧
  触发条件: 从站回显被分两次投递 + 第一次不足8字节就超时
  概率: 低 (9600bps 8字节 8.3ms，通常一次收齐)
  后果: 多一次重试，极端下写失败
  修复: 超时后不立即清，等一个帧间隔再清 (确认没有后续字节)

类2: SendLoop 清掉刚好到达的应答 (事件调度延迟)
  不合理点: 应答已到驱动缓冲，只是 OnData 没被调度执行
  触发条件: 应答在超时阈值附近到达 + OnData 调度延迟
  概率: 中 (50ms 超时偏紧，实测有3次超时)
  后果: 一次读丢失，下一轮重读
  修复: 加大超时阈值 (50→80ms)，或超时后不立即清，等2ms再清

类3: OnData Read 与 DiscardInBuffer 之间的新数据丢失
  不合理点: Read 之后到达的字节被 DiscardInBuffer 清
  触发条件: 数据在 Read 和 DiscardInBuffer 之间到达 (微秒级窗口)
  概率: 极低
  后果: 帧不完整，CRC 失败，重试
  修复: 难以完全规避 (除非加全局锁停止接收)，当前可接受

【六、诚实补充: "合理"与"不合理"的边界】
------------------------------------------------------------
前次分析说"清理都是合理的"，这次说"有不合理"，矛盾吗?

不矛盾。区别在视角:

  前次分析视角: busLock 互斥保证不会误清"正在等的应答"
    → 宏观层面正确: SendLoop 没在等，WriteLoop 当前帧没发
    → "不会误清有效应答" 成立

  本次分析视角: 微观时序上，"正在到达途中的应答字节"可能被清
    → busLock 管不到驱动缓冲 (OnData 不加 busLock)
    → 超时与到达的边界有缝隙

  统一表述:
    - 不会误清"已被 Handle 处理的有效应答" (busLock 保证)
    - 可能误清"正在到达途中的应答字节" (时序缝隙)
    - 后者概率低、有重试兜底、不累积，实际可接受

  所以前次说"合理"是指"设计意图合理" (清孤儿数据防干扰)，
  本次说"不合理"是指"边界情况下会清掉正在到达的有效数据"。
  两者都成立，是不同层面的分析。

【七、哪种最值得修?】
------------------------------------------------------------
类2 (SendLoop 清掉刚好到达的应答) 最值得修:
  - 概率最高 (50ms 超时偏紧，实测有超时)
  - 修复最简单 (超时阈值 50→80ms，或超时后 sleep 2ms 再清)
  - 收益最明显 (减少无谓超时，温湿度刷新更稳定)

类1 次之:
  - 概率低，重试兜底
  - 修复稍复杂 (要判断 buf 里是否有"可能正在到达的半截帧")

类3 可不修:
  - 概率极低，微秒级窗口
  - 修复代价大 (全局接收锁)，收益小
