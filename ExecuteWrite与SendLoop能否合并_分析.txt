专题分析：ExecuteWrite 和 SendLoop 能否合并/优化？
文件：F:\chenbo\Program.cs
分析时间：2026-11-02
================================================================================

【用户问题原文】
  "你优化下ExecuteWrite，和SendLoop，功能都差不多能优化不，不能给出理由"

================================================================================
【0. 直接回答】
================================================================================

  ★ 不能合并。能做局部小优化，但"合并成一个通用方法"不可行。

  理由一句话：它们表面相似（都是"发帧→等应答→超时清状态"），
  但在 6 个关键维度上本质不同，强行合并会引入 4 类新 bug，得不偿失。

  下面逐项对比，把"为什么不能"说透。

================================================================================
【1. 两个方法的逐行对比】
================================================================================

  维度                SendLoop（读轮询）              ExecuteWrite（写命令）
  ─────────────────────────────────────────────────────────────────────
  触发方式            定时循环（while+Sleep）          事件驱动（从队列取）
  从站来源            Slaves[] 轮询，idx 循环          wr.Slave 固定一个
  功能码              0x03（读保持寄存器）             0x05（写单个线圈）
  帧构造              每轮现构造                       入队前构造好，wr.Frame 复用
  应答信号            frameReceived（全局唯一）        wr.Ack（每对象独立）
  应答者标识          curSlave（volatile byte）        activeWrite（volatile 引用）
  重试                无（超时就轮下一个从站）         有（WriteRetry=3 次）
  发送异常处理        无 try-catch                     有 try-catch（发送失败也重试）
  超时后动作          清状态 + 轮下一个从站            清状态 + 重发同一帧
  成功后动作          frameReceived 已被 Handle Set    return true 退出重试循环
  异常响应处理        Handle 里 Set frameReceived      Handle 里 Set wr.Ack + AckOk=false
  返回值              void                             bool
  间隔                每次循环 Sleep(IntervalMs)       重试间隔 Sleep(IntervalMs)
  清状态时机          仅超时后清                       每次发前都清（含第1次）

================================================================================
【2. 为什么不能合并 —— 6 个本质差异】
================================================================================

  ── 差异1：应答信号的"作用域"完全不同 ──
    SendLoop 用全局唯一的 frameReceived：因为同一时刻只有一个读请求在等，
    且读请求没有"对象身份"概念（没 new ReadRequest）。
    ExecuteWrite 用 wr.Ack：因为多个写请求可能排队，每个需要独立信号灯隔离。

    如果合并：读操作也要 new 一个 ReadRequest 对象包起来，否则没法用 wr.Ack。
    → 改动波及 SendLoop 的整个数据流，引入复杂度，没收益。

  ── 差异2：应答者标识的"校验方式"完全不同 ──
    SendLoop 用 curSlave（byte）：只需比对从站号。
    ExecuteWrite 用 activeWrite（引用）：除了从站号，还要整帧比对过滤旧应答。

    如果合并：读操作也要走整帧比对，但读请求帧和读应答帧格式不同
    （请求是[slave,03,addrH,addrL,nH,nL,CRC]，应答是[slave,03,byteCount,data,CRC]），
    根本没法"整帧比对"。读操作只能比对从站号。
    → 合并后这个分支差异还是得用 if 区分，没省到代码。

  ── 差异3：重试语义完全不同 ──
    SendLoop 不重试：超时就轮下一个从站，下次轮回来自然重试。
    ExecuteWrite 重试 3 次：对同一从站同一帧连续重发，因为写命令是用户触发的，
    要给用户明确成功/失败结果，不能"轮下一个"。

    如果合并：要么读也重试（破坏轮询节奏，一个从站卡住会拖慢所有从站），
    要么写也不重试（用户写命令一次失败就放弃，体验差）。
    → 两种语义没法统一。

  ── 差异4：清状态时机不同 ──
    SendLoop 只在超时后清：正常收到应答不需要清（buf 已被 DrainInLock 取走）。
    ExecuteWrite 每次发前都清：因为重试时要确保上一轮的迟到应答不污染本轮。

    如果合并：读操作每次发前也清，会清掉"上一轮还没处理的迟到应答"——
    但读轮询的迟到应答恰恰可能是有效的（从站慢了一点，应答在下一轮才到）。
    → 读操作清状态会丢数据。

  ── 差异5：发送异常处理策略不同 ──
    SendLoop 无 try-catch：发送异常会终止线程（后台线程静默退出）。
    ExecuteWrite 有 try-catch：发送失败算一次重试，继续重发。

    如果合并：读操作也要 try-catch + 重试，但读轮询不该重试（见差异3）。
    → 矛盾。

  ── 差异6：从站选择逻辑不同 ──
    SendLoop：idx = (idx+1) % Slaves.Length，循环轮询多从站
    ExecuteWrite：slave 固定来自 wr.Slave，不轮询

    如果合并：要加参数控制"轮询 vs 固定"，加分支，没简化。

【3. 如果强行合并会怎样（反证）】
================================================================================

  假设提取一个通用方法：
    bool SendAndWait(byte[] frame, byte slave, Event ack, Action onSuccess,
                     bool retry, int maxRetry, ...)

  问题1：参数列表爆炸
    要区分读/写、重试/不重试、清状态时机、异常处理策略、从站选择...
    参数超过 8 个，比两个独立方法更难懂。

  问题2：内部分支没减少
    重试逻辑、清状态时机、应答校验方式还是得 if (isWrite) 区分，
    合并后的方法体比任一原方法都长。

  问题3：读操作的迟到应答会被误清
    ExecuteWrite 的"每次发前清"套到读操作上，会清掉有效的迟到应答。

  问题4：读操作的重试会破坏轮询节奏
    一个从站卡住，重试 3 次 = 150ms+，其他从站轮询延迟暴增。

  ★ 结论：合并后代码更长、更难懂、还引入 2 个新 bug。不合并是对的。

================================================================================
【4. 能做的局部小优化（不合并的前提下）】
================================================================================

  虽然不能合并，但两个方法各自有小优化空间：

  ── SendLoop 可优化点 ──

  (S1) 帧构造提到循环外
    现状：每轮都 new req + Crc(req)，但帧内容固定（从站号变化时才不同）。
    优化：预构造 Slaves.Length 个帧，循环里直接用。
    收益：省每轮的数组分配 + CRC 计算。
    注意：如果未来从站列表动态变化，这个优化就不合适。当前 Slaves 是 const，可以。

  (S2) 加 try-catch 包 sp.Write
    现状：第176-181行 sp.Write 无 try-catch，异常会终止线程。
    优化：仿照 ExecuteWrite 加 try-catch，打印日志后 continue 轮下一个。
    收益：避免线程静默退出（可观测性缺口修复）。

  (S3) 超时后 frameReceived.Reset() 是冗余的
    现状：第192行 frameReceived.Reset()
    分析：AutoResetEvent 在 WaitOne 返回 true 时自动 Reset；
          WaitOne 返回 false 时信号没被消费，灯本来就是灭的。
          唯一风险是"WaitOne 返回 false 后、Reset 前瞬间被 Set"，
          但这个 Set 会被下一次 WaitOne 消费——而下次 WaitOne 前会重新发送，
          如果旧应答和新的碰巧都到，新的 Set 也能唤醒（AutoReset 只能 Set 一次，
          两次 Set 之间没有 WaitOne 的话第二次 Set 无效）。
    结论：Reset 多余但无害，可删可留。留着更防御性。

  ── ExecuteWrite 可优化点 ──

  (E1) 提取"清状态"为小方法
    现状：第541-543行三行清状态在 ExecuteWrite 里，SendLoop 超时分支也有类似。
    优化：void ClearRxState() { lock(io){sp.DiscardInBuffer();} lock(gate){buf.Clear();} }
    收益：两处复用，意图更清晰。
    注意：wr.Ack.Reset() 不能放进去，因为 SendLoop 没有 wr.Ack。

  (E2) 提取"发送一帧"为小方法
    现状：SendLoop 第176-181行和 ExecuteWrite 第552-556行都是 lock(io){sp.Write}
    优化：bool SendFrame(byte[] frame) { lock(io){ if(!sp.IsOpen) return false; sp.Write(...); } return true; }
    收益：复用 + 统一 IsOpen 检查。
    注意：ExecuteWrite 的 try-catch 还是要留在外层（SendFrame 不抛异常返回 false）。

  (E3) 第524行 var xxx=wr.GetHashCode() 调试残留，删除
  (E4) 第532-535行 slave/addr/on/frame 四个局部变量只是别名，可直接用 wr.Slave 等
       但留着可读性更好，不必改。

  ── 两个方法共同的可优化点 ──

  (C1) 提取清状态方法 ClearRxState()（见 E1）
  (C2) 提取发送方法 SendFrame()（见 E2）
  (C3) 两个方法都缺顶层 try-catch，应补上（可观测性修复）

【5. 推荐的具体优化方案（保守版，不合并）】
================================================================================

  只做 3 个低风险高收益改动：

  改动1：提取 ClearRxState() 小方法
    private static void ClearRxState()
    {
        lock (io) { if (sp.IsOpen) sp.DiscardInBuffer(); }
        lock (gate) { buf.Clear(); }
    }
    SendLoop 超时分支和 ExecuteWrite 每轮开头都调用它。
    收益：消除重复，意图清晰，锁顺序集中维护。

  改动2：提取 SendFrame() 小方法
    private static bool SendFrame(byte[] frame)
    {
        try
        {
            lock (io)
            {
                if (!sp.IsOpen) return false;
                sp.Write(frame, 0, frame.Length);
            }
            return true;
        }
        catch (Exception ex)
        {
            Console.WriteLine($"[发送异常] {ex.Message}");
            return false;
        }
    }
    SendLoop 和 ExecuteWrite 都调用它。
    收益：SendLoop 也有了发送异常保护（修复可观测性缺口），统一 IsOpen 检查。

  改动3：SendLoop 帧预构造
    在 SendLoop 开头预构造 Slaves.Length 个帧：
      byte[][] readFrames = new byte[Slaves.Length][];
      for (int i=0; i<Slaves.Length; i++)
          readFrames[i] = Crc(new byte[]{ Slaves[i],0x03,0x00,0x00,(byte)(RegCount>>8),(byte)(RegCount&0xFF) });
    循环里直接用 readFrames[idx]。
    收益：省每轮的数组分配 + CRC 计算（9600bps 下收益微小，但干净）。

  ★ 不做的改动：
    - 不合并两个方法（理由见第2、3节）
    - 不删 frameReceived.Reset()（防御性，留着无害）
    - 不给读操作加重试（破坏轮询节奏）

================================================================================
【6. 总结】
================================================================================

  Q: ExecuteWrite 和 SendLoop 功能都差不多，能优化（合并）不？
  A: 不能合并。表面相似（发帧→等应答→超时清状态），但 6 个维度本质不同：
     应答信号作用域、应答校验方式、重试语义、清状态时机、异常处理、从站选择。
     强行合并会参数爆炸、分支没减少、还引入"读迟到应答被误清"和"读重试破坏轮询"2 个新 bug。

  能做的优化（不合并前提下）：
    1. 提取 ClearRxState() 小方法（两处复用）
    2. 提取 SendFrame() 小方法（两处复用 + 修复 SendLoop 无 try-catch 缺口）
    3. SendLoop 帧预构造（省每轮分配）

  这 3 个是低风险高收益，不改变逻辑，只消除重复 + 补防御。
  合并是高风险零收益，不做。
