【用户问题原文】
  "把 SendLoop 的'读请求'也封装成任务，和'写请求'一起丢进一个带优先级的队列
  （PriorityQueue）。由一个唯一的 BusWorker 线程统一从队列拿任务发。
  这个能优化不，不能给出理由"

================================================================================
【0. 直接回答】
================================================================================

  ★ 能优化，且是正确的架构方向。但当前规模不值得做，属于"过度设计"。

  准确说：
    - 方案本身【正确】：解决了读写互斥、总线独占、优先级问题
    - 对当前程序【不划算】：代码量翻倍，复杂度大增，收益有限
    - 对未来扩展【有价值】：多设备/多协议/优先级调度/QoS 时这是必经之路

  下面分 5 节详细评估：方案描述、收益、代价、当前是否值得、何时值得。

================================================================================
【1. 方案描述（把用户的想法具体化）】
================================================================================

  ── 1.1 统一任务抽象 ──

    abstract class BusTask
    {
        public byte Slave;
        public byte[] Frame;          // 完整发送帧（含CRC）
        public abstract byte ExpectFunc { get; }  // 期望的应答功能码
        public readonly AutoResetEvent Done = new AutoResetEvent(false);
        public bool Ok;
        public abstract void HandleResponse(byte[] resp);  // 子类解析应答
    }

    class ReadTask : BusTask         // 读保持寄存器
    {
        public ushort[] Regs;
        public override byte ExpectFunc => 0x03;
        public override void HandleResponse(byte[] resp) { /* 解析温湿度 */ }
    }

    class WriteTask : BusTask        // 写单个线圈
    {
        public ushort Addr; public bool On;
        public override byte ExpectFunc => 0x05;
        public override void HandleResponse(byte[] resp) { /* 校验回显 */ }
    }

  ── 1.2 优先级队列 ──

    // .NET 6+ 有 PriorityQueue<TElement, TPriority>
    // 低优先级数字先出（0=高优先级写，1=低优先级读）
    static readonly PriorityQueue<BusTask, int> busQueue = new PriorityQueue<BusTask, int>();

    // 写请求投递：高优先级
    busQueue.Enqueue(writeTask, 0);

    // 读请求投递：低优先级
    busQueue.Enqueue(readTask, 1);

  ── 1.3 唯一 BusWorker 线程 ──

    static void BusWorkerLoop()
    {
        while (running)
        {
            if (!busQueue.TryDequeue(out var task, out _))
            {
                // 队列空时自动生成读轮询任务（替代 SendLoop 的定时循环）
                task = MakeNextReadTask();   // 按 Slaves[] 轮询构造
                Thread.Sleep(IntervalMs);
            }

            activeTask = task;               // 唯一活跃任务，Handle 按此分发

            ClearRxState();
            task.Done.Reset();

            if (!SendFrame(task.Frame)) { task.Ok = false; task.Done.Set(); continue; }

            if (task.Done.WaitOne(TimeoutMs))
            {
                if (task.Ok) { /* 成功 */ }
                else { /* 写失败重试 */ }
            }
            else
            {
                /* 超时，写任务重试，读任务跳过 */
            }
        }
    }

  ── 1.4 Handle 简化 ──

    static void Handle(byte[] frame)
    {
        // CRC 校验 ...
        var task = activeTask;
        if (task == null || frame[0] != task.Slave) return;  // 从站校验
        if (frame[1] != task.ExpectFunc) return;             // 功能码校验
        task.HandleResponse(frame);                          // 多态分发
        task.Done.Set();
    }

  ── 1.5 SendLoop 和 WriteLoop 都删除 ──

    SendLoop 的轮询逻辑融入 BusWorkerLoop 的"队列空时自动生成读任务"
    WriteLoop 的消费逻辑融入 BusWorkerLoop 的"从队列取任务"
    CmdLoop 不变（投递 WriteTask 到 busQueue 而非 writeQueue）

【2. 收益（这个方案能带来什么）】
================================================================================

  收益1：总线独占天然保证
    只有一个 BusWorker 线程碰串口，物理上不可能两帧并发发送。
    → 不需要 busLock，不需要 lock(io) 串行化（BusWorker 是唯一写者）
    → 之前分析的"读写并存5个风险"全部消失

  收益2：优先级天然实现
    写任务优先级0，读任务优先级1，队列自动让写先出。
    → 用户写命令不会被读轮询阻塞，写响应更快
    → 不需要 TryEnter/lock 的让步逻辑

  收益3：应答归属简化
    只有一个 activeTask（替代 curSlave + activeWrite 两个变量），
    Handle 靠多态分发（task.HandleResponse），不需要 if (func==0x05) / if (func==0x03) 分支。
    → 代码更清晰，扩展新功能码只需加子类

  收益4：重试逻辑统一
    读任务不重试（超时跳过），写任务重试3次，都在 BusWorkerLoop 一处控制。
    → 不需要 ExecuteWrite 和 SendLoop 各写一套

  收益5：扩展性大幅提升
    加新功能（比如功能码0x06写单个寄存器、0x10写多个寄存器、0x02读离散输入）
    只需 new XxxTask() 投队列，BusWorker 不用改。
    → 开闭原则，对扩展开放对修改关闭

  收益6：可观测性提升
    BusWorker 是唯一发送者，天然适合加统计：发送次数/成功率/延迟/队列深度
    → 之前分析的"无心跳汇总"缺口可补

  ★ 收益真实且显著，特别是"总线独占"和"扩展性"。

【3. 代价（这个方案要付出什么）】
================================================================================

  代价1：代码量翻倍
    新增：BusTask 抽象类 + ReadTask + WriteTask + PriorityQueue 字段 + BusWorkerLoop
    删除：SendLoop + WriteLoop + ExecuteWrite + writeQueue + activeWrite + curSlave + frameReceived
    净增：约 100-150 行（当前程序约 690 行，增 15-20%）
    → 对当前规模不算大，但不是"小优化"

  代价2：PriorityQueue 线程安全要处理
    .NET 6 的 PriorityQueue<TElement,TPriority> 不是线程安全的！
    要么用 lock 包裹（失去无锁优势），要么用 ConcurrentQueue + 两个队列（写队列+读队列）模拟优先级
    → 实际实现比设想复杂

    替代方案：两个 ConcurrentQueue（writeQueue + readQueue），BusWorker 优先取 writeQueue
      if (writeQueue.TryDequeue(out var w)) { 执行 w }
      else if (readQueue.TryDequeue(out var r)) { 执行 r }
      else { 自动生成读任务 }
    → 简单且线程安全，但不是"严格优先级"（writeQueue 空才读，写多时读饿死）

  代价3：读轮询的"定时性"被破坏
    现状 SendLoop 固定 15ms 间隔轮询，温湿度采样率稳定。
    BusWorker 方案：队列空时才生成读任务，如果写命令频繁，读轮询间隔不确定。
    → 对温湿度（慢变量）可接受，对快变量采样率有要求时不接受
    → 要保定时性，得加"距上次读 > 15ms 才生成读任务"的判断，复杂度回来一点

  代价4：写重试和读不重试的分支
    BusWorkerLoop 里还是要 if (task is WriteTask) 重试 else 不重试
    或者用虚方法 task.ShouldRetry() 让子类决定
    → 分支没消除，只是从"两个方法"变成"一个方法里的多态"

  代价5：activeTask 的可见性问题没解决
    volatile BusTask activeTask 和现有 volatile WriteRequest activeWrite 本质相同
    → 之前分析的"内部字段可见性靠时序"问题原样存在
    → 没有改善并发正确性，只是把两个变量合并成一个

  代价6：调试/理解成本增加
    现有代码"两个线程各管各"直观易懂
    BusWorker 方案"一个线程+优先级队列+多态任务"抽象层次更高，新人理解成本大
    → 对单人维护的小项目，简单就是好

  代价7：.NET 版本要求
    PriorityQueue<TElement,TPriority> 是 .NET 6 引入的
    如果项目是 .NET Framework 4.x，没有 PriorityQueue，得自己实现或用 SortedSet
    → 需确认目标框架

  ★ 代价真实，主要是"复杂度增加"和"读定时性破坏"。

【4. 当前程序是否值得做】
================================================================================

  评估维度        现状                BusWorker 方案      判断
  ─────────────────────────────────────────────────────────────
  正确性          有读写并发风险      天然互斥            方案更好
  代码量          690行               +100-150行          现状更轻
  可读性          两个线程直观        抽象层次高          现状更易懂
  扩展性          加功能码要改多处    加子类即可          方案更好
  优先级          无                  天然支持            方案更好
  读定时性        15ms 固定           不确定              现状更好
  维护人数        单人                需要懂多态/队列     现状更友好
  .NET 版本       未知                需 6+               现状更兼容
  测试覆盖        无                  无                  持平

  ── 关键判断 ──

  (1) 当前程序只有 2 个从站、2 种功能码（0x03读 + 0x05写），功能固定不扩展
      → 扩展性收益用不上
      → 方案的"对扩展开放"是"为不存在的未来设计"

  (2) 读写并发风险可以用 busLock 解决（之前分析的方案A，加一个 lock）
      → busLock 方案：+10 行代码，解决 5 个风险
      → BusWorker 方案：+100-150 行代码，解决 5 个风险 + 扩展性
      → 性价比：busLock 完胜

  (3) 读轮询定时性对温湿度采样有意义（稳定间隔便于看趋势）
      → BusWorker 破坏定时性，要保定时还得加判断，复杂度回来
      → 现状 SendLoop 固定 15ms 更适合

  (4) 优先级需求：用户写命令频率远低于读轮询（手动输入 vs 15ms自动）
      → 写命令天然不频繁，"写优先"收益小
      → 真正冲突概率低，busLock 足够

  ★ 结论：当前程序不值得做 BusWorker 方案。
    用 busLock（+10行）解决并发风险，保留 SendLoop/WriteLoop 的简单结构，性价比最高。

【5. 何时值得做（诚实指出适用场景）】
================================================================================

  场景1：功能码种类增多
    如果未来要支持 0x06/0x10/0x02/0x04 等多种功能码，
    每种都有自己的帧格式和应答解析，
    现有"if (func==0x03) / if (func==0x05)"分支会爆炸
    → BusTask 多态分发明显更好

  场景2：多设备/多协议
    如果要支持非 Modbus 协议（如自定义帧格式），
    BusTask 可以抽象到"任意总线任务"
    → 现有结构无法扩展

  场景3：写命令高频
    如果写命令不是用户手动输入，而是程序自动高频触发（如每 100ms 写一次），
    读写冲突频繁，优先级调度有实际意义
    → 现有 busLock 让步策略会导致读饿死

  场景4：QoS/限流/统计
    如果要做"每秒最多发 X 帧"、"写命令超时率告警"、"队列深度监控"等运维功能
    BusWorker 是唯一发送者，天然适合加这些
    → 现有分散结构难加

  场景5：团队维护
    如果多人维护、需要严格架构规范、单元测试覆盖
    BusTask 抽象便于 mock 和测试
    → 现有静态方法难测试

  ★ 当以上任一场景出现，BusWorker 方案从"过度设计"变成"合理设计"。
    当前都不满足，所以不做。

【6. 如果要做，推荐的渐进路径】
================================================================================

  不要一步到位，分 3 步渐进：

  步骤1：先加 busLock 解决并发风险（+10行，必做）
    → 读写安全并存，当前问题解决
    → 不引入新抽象

  步骤2：提取 BusTask 抽象（+50行，可选）
    → 把 ReadRequest/WriteRequest 统一成 BusTask 子类
    → SendLoop 和 WriteLoop 还在，但内部用 BusTask
    → Handle 用多态分发，消除 if(func==) 分支
    → 为步骤3铺路

  步骤3：合并成 BusWorker（+50行，按需）
    → 删除 SendLoop + WriteLoop，统一 BusWorkerLoop
    → 加优先级队列
    → 只在步骤2验证稳定后才做

  ★ 绝不要跳过步骤1直接做步骤3。
    busLock 是 10 行解决真问题，BusWorker 是 100 行解决真问题+假想问题。
    先解决真问题。

【7. 对用户想法的具体评价】
================================================================================

  用户的想法在架构上是正确的：
    - "统一任务抽象" → 对，消除重复
    - "优先级队列" → 对，写优先合理
    - "唯一 BusWorker" → 对，单写者天然互斥

  但在工程决策上需要补充考虑：
    - PriorityQueue 在 .NET 6 才有，且非线程安全，实际要用两个 ConcurrentQueue 模拟
    - 读轮询定时性会被破坏，温湿度采样间隔不稳定
    - 当前规模（2从站2功能码）用不上扩展性
    - busLock（+10行）能解决同样的并发问题，性价比更高

  ★ 想法质量：高（架构直觉好）
    实施时机：早（当前过度设计）
    替代方案：busLock（先做）→ BusTask 抽象（按需）→ BusWorker（扩展时）

【8. 总结】
================================================================================

  Q: 统一 BusWorker + 优先级队列能优化吗？
  A: 方案正确，但当前不值得做。

  能带来的收益（真实）：
    1. 总线独占天然保证（单写者）
    2. 优先级天然实现（写先出）
    3. 应答归属简化（多态分发）
    4. 扩展性提升（加功能码只加子类）
    5. 可观测性提升（统一统计点）

  要付出的代价（真实）：
    1. 代码量 +100-150 行（+15-20%）
    2. PriorityQueue 非线程安全，实际要用双队列模拟
    3. 读轮询定时性被破坏
    4. 理解成本增加（多态+队列+单线程消费者）
    5. .NET 6+ 版本要求

  决策：
    当前程序（2从站2功能码不扩展）→ 不做，用 busLock（+10行）解决并发
    未来扩展（多功能码/多协议/高频写/QoS）→ 做，且按 busLock→BusTask→BusWorker 渐进

  一句话：架构方向对，当前规模过度设计，先用 busLock 解决真问题，
           等扩展需求出现再升级到 BusWorker。
