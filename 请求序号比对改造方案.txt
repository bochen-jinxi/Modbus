请求序号比对改造方案（整帧比对）
================================

一、背景
之前分析场景C：Reset 后 Write 前旧应答到达，被误当新请求成功。
提到"加请求序号 Handle 比对"可消除，但 RTU 无原生字段承载。
本文给出实际改造。


二、RTU 为什么不能加递增序号
Modbus RTU 0x05 帧固定 8 字节：
  [slave][0x05][addrH][addrL][valueH][valueL][CRC_L][CRC_H]
每个字段都有定义，没有空位塞序号。加字节会破坏协议，从站不认。
Modbus TCP 才有 MBAP 头的事务ID(TID)，RTU 没有。


三、利用 0x05 应答是"请求的回显"这一特性
0x05 写线圈的应答帧 = 请求帧（逐字节相同，就是回显）。
所以：Handle 收到 0x05 应答时，和"当前发送的请求帧"逐字节比对：
  一致 → 是当前请求的应答，Set writeDone
  不一致 → 是旧请求的迟到应答，丢弃
不需要改协议，只在本机内存里比对。


四、改造内容
1. 加字段：static volatile byte[] curWriteFrame;
   （引用读写原子，volatile 保证可见）
2. WriteSingleCoil 发送前：curWriteFrame = frame;
   记住这次发送的帧。
3. Handle 的 0x05 分支：先逐字节比对 frame 与 curWriteFrame，
   不一致直接 return（丢弃），一致才 writeOk=true + Set。


五、效果
能过滤：旧请求的迟到应答（帧内容不同，如不同线圈地址/不同值）。
  例：上一轮写线圈0，本轮写线圈1，旧应答(线圈0回显) != curWriteFrame(线圈1) → 丢弃。

不能过滤：相同请求重试的旧应答（帧内容完全相同）。
  例：写线圈0超时，重试还是写线圈0，旧应答(线圈0回显) == curWriteFrame(线圈0) → 通过。
  但这种情况：旧应答内容 = 新应答内容（都是线圈0成功回显），
  拿到旧的等于拿到新的，结果一样，无害。


六、和原来"只比对从站号"的对比
  原来：Handle 只看 frame[0]==writeSlave（从站号），同从站不同线圈的旧应答也会误判。
  现在：逐字节比对整帧，同从站不同线圈的旧应答被过滤，更严格。
  场景C 残留：只剩"完全相同的重试旧应答"，且无害。


七、异常响应 0x85 怎么办
0x85 帧是 [slave][0x85][异常码][CRC]，不是请求回显，无法整帧比对。
保留原来的从站号校验（frame[0]==writeSlave）。
异常响应触发重试，误拿旧的异常响应也只是多一次重试，无害。


八、局限与权衡
  优点：不改协议、改动小、过滤比从站号更严格。
  局限：相同请求重试的旧应答无法区分（无害）。
  彻底方案：需要协议层事务ID，RTU 没有，要改用 TCP 或自定义协议，代价大。
  当前方案在 RTU 约束下已是最优。


九、口诀
RTU 没序号，但零x05回显请求帧；
记住当前发的什么，收到回显逐字节比。
一致才是我的答，不一致是旧的丢；
相同重试分不清，内容一样也无害。


十、涉及代码位置
字段：static volatile byte[] curWriteFrame;
WriteSingleCoil: curWriteFrame = frame;  （发送前）
Handle 0x05 分支：逐字节比对 frame vs curWriteFrame，不一致丢弃。
