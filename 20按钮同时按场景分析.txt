============================================================
1秒内同时按20个按钮的场景分析
============================================================
分析时间: 2026-11-03
场景: 用户在 1 秒内同时按下 20 个按钮
      (即 1 秒内投递 20 个 WriteRequest 到 writeQueue)
============================================================

【一、直接回答】
------------------------------------------------------------
20 个请求全部能成功执行完，不会丢失任何一个，
但最后一个请求要等约 2~4 秒才拿到结果。

具体说:
  - 队列峰值: 20 (瞬间全部入队)
  - 全部消化时间: 2~4 秒 (取决于从站响应质量)
  - 调用方等待: 第1个 ~100ms，第20个 ~2~4秒
  - 超时风险: 有! 超时阈值 695ms，排在后面的请求
              可能等不到结果就被调用方放弃

关键结论: 20 个请求本身没问题(队列装得下、写得完)，
但 695ms 超时阈值太短，排在后面的请求会被调用方
误判为"失败"，尽管 WriteLoop 最终会执行它们。

这是当前代码在这个场景下的真实问题。

【二、精确时序推演】
------------------------------------------------------------
假设 20 个请求在 t=0 同时入队 (最坏情况，瞬间全到)。
WriteLoop 串行消费，每个请求耗时取决于从站响应:

情况A: 从站响应良好 (每次首次回显成功)
  单请求耗时 = 发送1ms + 等回显18ms + busLock让读事务0~65ms
             ≈ 20~85ms，取 50ms
  消费时序:
    请求1:  t=0    → t=50ms   完成
    请求2:  t=50   → t=100ms  完成
    ...
    请求20: t=950  → t=1000ms 完成
  全部完成: 20 * 50ms = 1000ms = 1秒
  队列长度变化: 20→19→18→...→1→0 (每50ms减1)

  调用方等待时间 (Completed.Wait):
    请求1:  50ms   ✓ < 695ms 成功
    请求7:  350ms  ✓ < 695ms 成功
    请求14: 700ms  ✗ > 695ms 超时! 调用方返回false
    请求15~20: 750~1000ms ✗ 全部超时

  ★ 问题: 请求14~20 实际会被 WriteLoop 执行成功，
    但调用方已超时返回 false，用户看到"失败"，
    实际从站已被写入。这是"假失败"。

情况B: 从站响应一般 (偶尔超时，平均1次重试成功)
  单请求耗时 ≈ 100ms (1次超时50 + 间隔15 + 重试成功35)
  全部完成: 20 * 100ms = 2000ms = 2秒
  调用方等待:
    请求1:  100ms  ✓
    请求7:  700ms  ✗ 超时
    请求8~20: 全部超时
  ★ 13 个请求"假失败"

情况C: 从站无响应 (3次全超时)
  单请求耗时 = 3*(50+15) = 198ms
  全部完成: 20 * 198 = 3960ms ≈ 4秒
  调用方等待:
    请求1:  198ms  ✓
    请求4:  792ms  ✗ 超时
    请求5~20: 全部超时
  ★ 16 个请求"假失败" (且从站确实没写成功)

【三、核心问题: 695ms 超时阈值太短】
------------------------------------------------------------
当前超时计算 (Program.cs:531):
  waitMs = WriteRetry * (TimeoutMs + IntervalMs + 50) + 500
         = 3 * (50 + 15 + 50) + 500
         = 3 * 115 + 500
         = 345 + 500
         = 695ms

这个 695ms 的含义是: "单个请求从开始执行到完成的最长时间"
(3次重试 * 115ms + 500ms 余量)。

它假设"请求投递后立即开始执行"，没有考虑排队时间!

在单按钮场景: 投递即执行，695ms 够用。
在20按钮场景: 第N个请求要排队 (N-1)*单请求耗时，
              排队时间 + 执行时间 > 695ms 就超时。

这就是"为单按钮设计的超时，不适用多按钮批量场景"。

【四、假失败的危害】
------------------------------------------------------------
"假失败" = 调用方认为失败，但 WriteLoop 仍会执行且可能成功。

危害1: 用户误判
  用户看到"失败"，实际从站已写入。
  用户可能重试(再按一次)，导致重复写(虽然幂等，但浪费总线)。

危害2: 重复执行
  调用方超时后返回，但 WriteRequest 还在队列里，
  WriteLoop 不知道调用方已放弃，仍会执行。
  → 执行了但结果没人读 (wr.Result 写了但没人看)
  → 浪费总线时间，挤占后续请求

危害3: 资源泄漏 (轻微)
  异步模式的 ThreadPool 回调超时后返回，
  但 wr 对象仍被 writeQueue 引用，直到 WriteLoop 消费完。
  → 临时内存占用，消费完后释放，不严重。

【五、解决方案】
------------------------------------------------------------
方案1 (推荐): 超时考虑排队位置
  思路: 超时 = 排队时间 + 单请求执行时间
  实现: 投递时记录队列位置，超时 = 位置 * 单请求最大耗时 + 695
  问题: 队列位置在投递时可知 (writeQueue.Count)，但消费中
        位置在变，不精确。保守用投递时的 Count:
    int ahead = writeQueue.Count;
    int waitMs = ahead * 200 + 695;  // 每个200ms上限
  优点: 简单，几乎不改结构
  缺点: 保守，实际可能用不了这么久

方案2: 动态超时 (基于队列长度)
  思路: 超时随队列长度自适应
  实现:
    int qlen = writeQueue.Count;
    int perReq = WriteRetry * (TimeoutMs + IntervalMs) + 50;
    int waitMs = qlen * perReq + perReq + 500;
  优点: 精确
  缺点: 投递后队列长度仍变，但比固定值好

方案3: 不超时，纯异步通知
  思路: 调用方不阻塞等，结果通过回调通知
  实现: WriteSingleCoil 改为返回 void，加回调参数
  优点: 彻底解决超时问题
  缺点: 改变 API 语义，调用方需改为异步处理
  注: 异步模式 (ParseAndSubmit) 已是此思路，但仍有695ms超时

方案4: 限制队列长度
  思路: 队列超限直接拒绝
  实现:
    if (writeQueue.Count > 10) return false; // 拒绝
  优点: 防止堆积
  缺点: 20按钮场景下后10个被拒绝，用户要重试

方案5 (最简单): 加大超时
  思路: 把 695ms 改大到能覆盖20按钮
  实现:
    int waitMs = 20 * 200 + 695 = 4695ms; // 或直接 5000
  优点: 一行改动
  缺点: 单按钮场景也要等5秒才超时(虽然成功时100ms就返回)

推荐: 方案1 或 方案2，兼顾简单与精确。
当前场景若不常批量按，方案5 也可接受。

【六、20按钮场景的其他影响】
------------------------------------------------------------
1. 对 RS485 总线: 无影响
   - WriteLoop 串行，一次一帧，物理上安全
   - 20个请求只是排队，不会并发发送

2. 对读操作 (SendLoop): 短期饥饿
   - 20个写请求执行期间 (~2秒)，busLock 被写线程持续占用
   - SendLoop 的 TryEnter 持续失败，读轮询跳过
   - 2秒内温湿度不刷新
   - 2秒后队列消化完，读恢复
   - 影响: 短暂的读停滞，人机界面温湿度2秒不更新
   - 严重性: 低 (2秒人眼可接受)

3. 对内存: 微不足道
   - 20 个 WriteRequest * ~100字节 = 2KB

4. 对 CPU: 微不足道
   - WriteLoop 单线程消费，ThreadPool 20个等待线程
   - 等待线程在 Wait，不占 CPU

5. 对 ThreadPool:
   - 异步模式起 20 个 ThreadPool 线程等 Completed
   - ThreadPool 默认上限 = CPU逻辑核数 (现代机8~16)
   - 20 > 16 可能排队，但 Wait 不占 CPU，影响小

【七、诚实补充: 20按钮是否真实场景?】
------------------------------------------------------------
1. 当前代码的交互方式是 Console.ReadLine 输入命令，
   "同时按20个按钮"对应"一行输入20条 ; 分隔的命令":
     on 1 0; off 1 0; on 1 1; off 1 1; ... (20条)
   这是可能的，但用户极少这么干。

2. 真正的"多按钮"场景在 Scada WPF 子项目 (ChenboScada)，
   那里有按钮 UI。但 Scada 是独立项目，不直接调
   ModbusDemo 的 writeQueue (通过命令行/参数模式交互)。
   所以"20按钮同时按"在当前 ModbusDemo 控制台项目里
   只能通过 ; 分隔命令模拟。

3. 若未来 Scada 集成 ModbusDemo 的写逻辑，
   20按钮同时按是真实场景，需提前用方案1/2优化。

4. 即使不优化，20按钮场景下:
   - 总线安全 (串行)
   - 数据不丢 (队列保底)
   - 唯问题是"假失败"显示，用户体感差
   不会导致系统崩溃或数据损坏。

【八、总结】
------------------------------------------------------------
1. 20个请求全部能执行完，队列装得下，总线安全
2. 全部消化需 1~4 秒 (取决于从站响应)
3. 真正问题: 695ms 超时太短，第7~20个请求"假失败"
   (实际成功但调用方超时返回false)
4. 次要影响: 读操作饥饿 ~2秒 (温湿度暂不刷新)
5. 解决: 超时考虑排队位置 (方案1/2)，或加大超时 (方案5)
6. 不会崩溃、不会数据损坏、不会内存泄漏
