一、核心区别一句话
================================================================================
┌──────────────────┬──────────────────────────────────────────────────┐
│                  │  volatile 引用字段      │  非 volatile 引用字段  │
├──────────────────┼────────────────────────┼────────────────────────┤
│  保证什么        │  引用本身的读写可见性   │  无任何保证            │
│                  │  + 有序性               │  （除非另加锁/屏障）   │
├──────────────────┼────────────────────────┼────────────────────────┤
│  不保证什么      │  引用指向对象内部字段   │  —                     │
│                  │  的可见性               │                        │
└──────────────────┴────────────────────────┴────────────────────────┘


二、用 Program.cs 中的真实字段对比
================================================================================

2.1 volatile 引用字段：curWriteFrame（第 30 行）
────────────────────────────────────────────────────────────────────────────────
  代码：static volatile byte[] curWriteFrame;

  【写线程】WriteSingleCoil 第 457 行：
    curWriteFrame = frame;   // volatile 写：release 屏障

    - 写入后，其他线程立刻能看到新引用
    - 不会因为寄存器缓存/指令重排而读到旧值
    - release 语义：frame 的所有初始化写入（构造数组、填值）
      不会被重排到 volatile 写之后
      → 读线程拿到引用时，数组内容也一定就绪

  【读线程】Handle 第 361 行：
    var cur = curWriteFrame;   // volatile 读：acquire 屏障
    for (int i = 0; i < frame.Length; i++) { if (frame[i] != cur[i]) ... }

    - acquire 语义：之后的读取不会被重排到 volatile 读之前
    - 拿到 cur 后读 cur[i] 一定能读到构造时的值

2.2 非 volatile 引用字段：buf（第 12 行）
────────────────────────────────────────────────────────────────────────────────
  代码：static readonly List<byte> buf = new List<byte>();

  【如果 buf 不加 lock 直接多线程访问会怎样？】

    // 线程A
    buf.AddRange(tmp);        // 写

    // 线程B
    int count = buf.Count;    // 读

    - 线程B 可能读到缓存的旧引用（编译器把 buf 缓存到寄存器）
    - 即使读到新引用，AddRange 的中间状态（Count 已加但元素未就绪）
      可能可见 → 数据损坏
    - List<byte> 内部数组操作非原子，可能读到半完成状态

  【所以 buf 必须用 lock 保护】（Program.cs 正是这么做的）：
    lock (gate) { buf.AddRange(tmp); ... }

    - lock 提供 memory barrier + 互斥
    - Monitor.Enter/Exit 隐含完整内存屏障，比 volatile 更强
    - 既保证可见性，又保证互斥


三、可见性差异的底层机制
================================================================================

3.1 volatile 引用字段（有 acquire/release 屏障）
────────────────────────────────────────────────────────────────────────────────
  ┌─────────────────────────────────────────────────────────┐
  │  线程A (写)                  线程B (读)                 │
  │                                                         │
  │  curWriteFrame = frame;      var cur = curWriteFrame;   │
  │  ┌─────────────┐            ┌─────────────┐            │
  │  │ volatile 写 │            │ volatile 读 │            │
  │  │ release屏障 │            │ acquire屏障 │            │
  │  └─────────────┘            └─────────────┘            │
  │       ↓                          ↓                     │
  │  ① 不重排到写之后            ① 不重排到读之前            │
  │  ② 刷新到主内存              ② 从主内存读取              │
  │                                                         │
  │  → B 一定看到 frame 引用 + frame 内部初始化值           │
  └─────────────────────────────────────────────────────────┘

3.2 非 volatile 引用字段（无屏障）
────────────────────────────────────────────────────────────────────────────────
  ┌─────────────────────────────────────────────────────────┐
  │  线程A (写)                  线程B (读)                 │
  │                                                         │
  │  buf.AddRange(tmp);         int c = buf.Count;          │
  │  ┌─────────────┐            ┌─────────────┐            │
  │  │ 普通写      │            │ 普通读      │            │
  │  │ 无屏障      │            │ 无屏障      │            │
  │  └─────────────┘            └─────────────┘            │
  │       ↓                          ↓                     │
  │  ① 可缓存到寄存器           ① 可读寄存器旧值            │
  │  ② 可重排                    ② 可重排                   │
  │                                                         │
  │  → B 可能读到旧引用 / 半完成状态 / 旧 Count             │
  │  → 必须靠 lock / Interlocked 补救                       │
  └─────────────────────────────────────────────────────────┘


四、关键陷阱：volatile 引用字段"不保护对象内部"
================================================================================

  class Data { public int Value; }
  volatile Data _d;   // volatile 只管 _d 这个引用

  // 线程A
  var obj = new Data { Value = 42 };
  _d = obj;           // volatile 写：引用可见 ✓

  // 线程B
  var r = _d;         // volatile 读：拿到新引用 ✓
  r.Value = 99;       // ★ 但 Value 不是 volatile，多线程改 Value 不可见/非原子！

  对应 Program.cs 中的 curWriteFrame（volatile byte[]）：
    - volatile 保证拿到最新的数组引用 ✓
    - 数组元素 cur[i] 本身没有 volatile 语义 ✗
    - Program.cs 安全的原因：
      frame 构造后不再修改（安全发布模式），所以读元素时不会有竞态

七、Program.cs 中非 volatile 引用字段清单与分析
================================================================================

7.1 static readonly List<byte> buf（第 12 行）★ 引用类型
────────────────────────────────────────────────────────────────────────────────
  用途：接收缓冲区
  保护方式：lock(gate)
  分析：
    - buf 会被多线程修改（OnData 的 AddRange、DrainInLock 的 RemoveRange、
      SendLoop 超时时的 Clear、WriteSingleCoil 的 Clear）
    - 必须用 lock 保证互斥 + 可见性
    - readonly 保证引用本身不被重新赋值
    - 正确

7.2 static SerialPort sp（第 17 行）★ 引用类型
────────────────────────────────────────────────────────────────────────────────
  用途：串口对象
  保护方式：lock(io)
  分析：
    - sp 不会被重新赋值（只在 Main 中赋值一次）
    - 但 sp 的方法（Write/Read/BytesToRead/DiscardInBuffer）非线程安全
    - 用 lock(io) 保证同一时刻只有一个线程操作串口
    - 正确

7.3 static readonly object gate / io（第 13、15 行）
────────────────────────────────────────────────────────────────────────────────
  用途：锁对象
  分析：readonly 保证引用不变，无需 volatile（赋值后不再改变）

九、结论
================================================================================

1. volatile 引用字段：保证引用本身读写可见+有序，不保证对象内部字段。
   适合"一次发布、之后只读"的场景。
   Program.cs 中的 curWriteFrame 是典型正确用法（安全发布模式）。

2. 非 volatile 引用字段：无任何保证，多线程访问必须配合 lock / Interlocked
   / 显式 Volatile.Read/Write。
   Program.cs 中的 buf、sp 用 lock 保护，正确。

3. Program.cs 的多线程同步设计是正确的：
   - volatile 用于轻量可见性（curWriteFrame、curSlave、writeSlave、running、writeOk）
   - lock 用于互斥+可见性（buf、sp）
   - Interlocked 用于 long 跨线程读写（lastDataTicks）
   - AutoResetEvent 用于线程间事件通知（frameReceived、writeDone）
   - 锁顺序统一（io → gate），无死锁风险
