一、改造目标
================================================================================
0x05 写线圈成功（收到回显）只表示"从站收到了命令"，不表示"设备真的启动了"。
增加强闭环验证：写线圈成功后读 0x02 离散输入（传感器信号），确认物理设备真的到位。


二、为什么需要这个逻辑
================================================================================

2.1 0x05 回显的含义
--------------------------------------------------------------------------------
  Modbus 0x05 应答是请求帧的完整回显，只表示：
    - 从站收到了写命令
    - 从站接受了写命令（没返回异常响应 0x85）
    - 从站把线圈状态改了
  不表示：
    - 电机真的转起来了（可能机械故障、电源没接、负载卡死）
    - 阀门真的打开了（可能执行机构故障）
    - 设备真正处于"启动"状态

2.2 工控现场的安全需求
--------------------------------------------------------------------------------
  "开到位"的真正含义是"设备确实启动了"，不只是"PLC 收到了命令"。
  如果只看 0x05 回显就认为启动成功：
    - 电机没转但程序认为转了 → 采集转速读到 0 → 误判"转速正常 0 RPM"
    - 操作员看到"开到位成功"就离开，实际设备没启动 → 安全风险

2.3 0x02 读离散输入的作用
--------------------------------------------------------------------------------
  离散输入（Discrete Input）是"只读位"，对应传感器的开关量状态：
    - "电机运行中"信号
    - "阀门到位"信号
    - "设备就绪"信号
  读 0x02 拿到的是传感器实测的物理状态，不是"命令是否收到"。


三、改造内容
================================================================================

3.1 新增数据结构
--------------------------------------------------------------------------------
  class VerifyRequest          // 0x02 验证请求
  {
      Slave, InputAddr, ExpectOn, Frame, Ack, AckOk, ActualOn
  }
  static volatile VerifyRequest activeVerify   // 当前正在等 0x02 应答的请求

  class VerifyProfile          // 验证配置
  {
      VerifyAddr, VerifyOnValue, VerifyDelayMs
  }
  static Dictionary<(byte,ushort), VerifyProfile> VerifyProfiles  // 验证配置表

3.2 新增 VerifyPhysicalState 方法
--------------------------------------------------------------------------------
  在 ExecuteWrite 内同步执行（已在 busLock 内）：
    1. 查 VerifyProfiles，没配置直接返回 true（向后兼容）
    2. 延迟 VerifyDelayMs 等设备物理响应
    3. 构造 0x02 请求帧，发 + 等应答 + 重试 WriteRetry 次
    4. 应答按位解析：frame[3] 的 bit0 是第1个离散输入的值
    5. 实际值 == 期望值 → 返回 true（到位确认）
    6. 不等或重试耗尽 → 返回 false（未到位）

3.3 改造 ExecuteWrite
--------------------------------------------------------------------------------
  0x05 回显成功后：
    if (on && !VerifyPhysicalState(slave, addr))
        continue;   // 物理状态未到位，重试写命令
    if (on) EnqueueReadTasks(slave, addr);
    return true;    // 真正到位确认

3.4 改造 Handle
--------------------------------------------------------------------------------
  - 多从站校验：0x02/0x82 用 activeVerify.Slave 校验
  - 异常响应：0x82 通知 activeVerify.Ack
  - 0x02 正常应答：按位解析，Set activeVerify.Ack

3.5 改造 FrameLength
--------------------------------------------------------------------------------
  0x02 应答格式与 0x03/0x04 相同（从站+功能码+字节数+数据+CRC），合并判断。

3.6 ExecuteWrite finally 清 activeVerify
--------------------------------------------------------------------------------
  finally { activeWrite = null; activeVerify = null; }


四、验证配置表
================================================================================
  VerifyProfiles = { (0x01, 0) → { VerifyAddr=0x0000, VerifyOnValue=true, VerifyDelayMs=200 } }
  含义：从站1 线圈0 写 ON 成功后，延迟 200ms 读离散输入地址 0x0000，
        期望值为 ON(true) 才算"真正开到位"。


五、执行时序示例
================================================================================
  t=0     用户输入：on 1 0
  t=5     WriteLoop: lock(busLock), ExecuteWrite
  t=5     发 0x05 写线圈 ON
  t=23    收到 0x05 回显，写命令成功
  t=23    调用 VerifyPhysicalState(1, 0)
  t=23    延迟 200ms 等电机物理启动
  t=223   发 0x02 读离散输入@0x0000
  t=241   收到 0x02 应答，bit0=1（电机运行中）
  t=241   打印：[验证结果·从站01] 离散输入0 = ON，期望ON，✓到位确认
  t=241   VerifyPhysicalState 返回 true
  t=241   EnqueueReadTasks 投递转速/电压/电流采集任务
  t=241   ExecuteWrite 返回 true，释放 busLock
  t=741   采集任务执行，读转速/电压/电流


六、回头审视清单（主动检查副作用）
================================================================================

6.1 activeVerify 清理
--------------------------------------------------------------------------------
  VerifyPhysicalState 内每次重试设 activeVerify=vr，方法返回后 ExecuteWrite finally 清。
  ✓ 无残留。

6.2 activeVerify 与 activeWrite 同时非 null
--------------------------------------------------------------------------------
  ExecuteWrite 中 activeWrite 在写成功后仍非 null（finally 才清），VerifyPhysicalState 设 activeVerify。
  Handle 中 0x05 用 activeWrite 校验，0x02 用 activeVerify 校验，功能码不同不会混淆。
  ✓ 安全。

6.3 busLock 持有时间变长
--------------------------------------------------------------------------------
  ExecuteWrite 现在在 busLock 内多做 0x02 验证（含 DelayMs + 重试），
  busLock 持有时间增加 200ms + 3×50ms = 350ms。
  SendLoop 期间 TryEnter 失败跳过，周期轮询暂停更久。
  这是设计代价——强闭环验证优先于周期轮询。
  ✓ 可接受（工控现场"到位确认"比"周期采集"更重要）。

6.4 ClearRxState 清 buf 后迟到 0x05 回显
--------------------------------------------------------------------------------
  VerifyPhysicalState 中 ClearRxState 清了 buf，但 activeWrite 还非 null。
  迟到的 0x05 回显到达 → Handle 整帧比对通过 → Set aw.Ack。
  但 aw.Ack 已被 WaitOne 消费，再 Set 无副作用（ExecuteWrite 已过 WaitOne）。
  ✓ 无副作用。

6.5 0x02 应答不会被 0x03/0x04 分支误处理
--------------------------------------------------------------------------------
  Handle 中 0x02 分支在 0x03/0x04 之前，return 了。
  ✓ 不会落到 0x03/0x04。

6.6 VerifyPhysicalState 返回 false 后 continue
--------------------------------------------------------------------------------
  ExecuteWrite 的 for 循环 continue，重发写命令（重试）。
  activeWrite 还是旧 wr，重发同一帧。
  ✓ 正确（物理未到位 → 重试写命令）。

6.7 没有配置验证的线圈
--------------------------------------------------------------------------------
  VerifyPhysicalState 查不到配置直接返回 true。
  ✓ 向后兼容，不强制所有线圈都验证。

6.8 关到位(OFF)不验证
--------------------------------------------------------------------------------
  ExecuteWrite 中 if(on && !VerifyPhysicalState(...))，只有 on=true 才验证。
  关到位不验证（关了就没"物理到位"可言，或者说"关"本身就是到位）。
  ✓ 设计如此。


七、穷举线程交错时序
================================================================================

7.1 时序 A：验证期间 SendLoop 想读
--------------------------------------------------------------------------------
  ExecuteWrite 持 busLock 做 0x02 验证，SendLoop TryEnter 失败跳过。
  ✓ 安全（busLock 互斥）。

7.2 时序 B：验证期间迟到 0x05 回显到达
--------------------------------------------------------------------------------
  VerifyPhysicalState 中 ClearRxState 清 buf，迟到 0x05 回显到达。
  Handle: func=0x05 → activeWrite 非 null → 整帧比对 → Set aw.Ack（已消费，无副作用）。
  ✓ 安全。

7.3 时序 C：验证超时后迟到 0x02 应答到达
--------------------------------------------------------------------------------
  VerifyPhysicalState 超时，重试。迟到 0x02 应答到达。
  但 ClearRxState 在重试前清了 buf，迟到应答在 ClearRxState 之后才到 → 被收进 buf。
  Handle: func=0x02 → activeVerify 非 null → 处理 → Set vr.Ack。
  但 vr.Ack 已被 WaitOne 消费（超时了），再 Set 无副作用。
  重试时 vr.Ack.Reset() 清掉，新一轮等。
  ✓ 安全。

7.4 时序 D：验证成功后迟到 0x02 应答到达
--------------------------------------------------------------------------------
  VerifyPhysicalState 返回 true，ExecuteWrite finally 清 activeVerify=null。
  迟到 0x02 应答到达 → Handle: func=0x02 → activeVerify==null → return（忽略）。
  ✓ 安全。


八、总结
================================================================================
增加了强闭环验证：0x05 写线圈成功 → 0x02 读离散输入验证物理到位。
只有物理状态确认到位才算"真正开到位"，否则重试写命令。
向后兼容（没配置验证的线圈直接返回 true）。
busLock 持有时间增加约 350ms（验证延迟+重试），周期轮询暂停，可接受。
回头审视 8 项 + 穷举 4 种时序，均安全。
编译通过，零错误。
