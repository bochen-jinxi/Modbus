================================================================================
一、承认错误
================================================================================

【之前的错误分析】
在"只有pollActive=false没有pollAck.Reset()"的场景下，我写道：
  T6: 下一轮：pollActive=true，pollAck.Reset() ← 这里才Reset
  T7: 发新请求
  T8: WaitOne → 立即返回！（因为T2时Set的信号还在）

【错误原因】
T6的pollAck.Reset()（第304行）已经把T2的Set信号清除了，
所以T8的WaitOne不会立即返回。我忽略了T6的Reset效果。

【用户指出的正确逻辑】
pollAck.Reset()调用后，T2的Set信号灯已经灭了，
T8的WaitOne会正常阻塞等待，不会立即返回。

================================================================================
二、重新分析：超时分支的pollAck.Reset()（第330行）是否冗余？
================================================================================

【代码中的两个Reset位置】

位置1：第304行（发请求前）
  curSlave = id;
  pollActive = true;
  pollAck.Reset();           ← 每次发请求前都Reset

位置2：第330行（超时分支）
  pollActive = false;
  curSlave = 0xFF;
  pollAck.Reset();           ← 超时后也Reset

【关键问题】
如果第304行的Reset已经能清除任何残留信号，
那第330行的Reset是否冗余？

【分析：假设移除第330行的Reset】

时序：
  T1: 第1轮：pollActive=true, pollAck.Reset()(第304行), 发请求
  T2: 从站应答到达，Handle处理，pollAck.Set() ← 信号亮了
  T3: WaitOne(50ms) 超时（Set发生在超时窗口之外）
  T4: pollActive=false
  T5: curSlave=0xFF
  T6: （假设没有第330行的Reset）
  T7: idx++, Thread.Sleep(IntervalMs)
  T8: 第2轮：curSlave=新从站, pollActive=true
  T9: pollAck.Reset()(第304行) ← 清除T2的Set信号
  T10: 发新请求
  T11: WaitOne → 正常阻塞等待 ✅

结论：即使没有第330行的Reset，第304行的Reset也能清除残留信号。

【那第330行的Reset有什么额外作用？】

在当前代码逻辑下，第330行的Reset确实是冗余的，因为：
1. 第304行的Reset在下一轮WaitOne之前执行，清除所有残留信号
2. pollActive=false阻止了超时后的迟到应答Set
3. curSlave=0xFF阻止了从站号不匹配的应答

三道防线已经足够，第330行的Reset是第四道"防御性"保险。

【防御性编程的价值】
虽然当前逻辑下冗余，但第330行的Reset有以下防御价值：
1. 如果未来代码修改导致第304行的Reset被移除或延迟，第330行仍能保护
2. 确保超时后信号立即被清除，不依赖下一轮的Reset
3. 使超时分支的语义更清晰：超时后所有状态都被清理干净

三、重新审视：pollActive=false的真正必要性
================================================================================

【既然第304行的Reset能清除残留信号，pollActive=false是否也冗余？】

假设移除pollActive=false（但保留第330行的Reset）：

时序：
  T1: 第1轮：pollActive=true, pollAck.Reset(), 发请求
  T2: WaitOne(50ms) 超时
  T3: ClearRxState()
  T4: curSlave=0xFF
  T5: pollAck.Reset()
  T6: idx++, Thread.Sleep(IntervalMs)
  T7: 第2轮：curSlave=新从站, pollActive=true
  T8: pollAck.Reset()
  T9: 发新请求
  T10: 从站1的迟到应答到达
  T11: Handle检查从站号：frame[0](从站1) != curSlave(新从站) → 忽略 ✅

在这个场景中，curSlave=0xFF（T4）和第2轮的curSlave=新从站（T7）都能防护。
所以pollActive=false似乎是冗余的？

但考虑另一个时序：
  T1: 第1轮：pollActive=true, pollAck.Reset(), 发请求
  T2: WaitOne(50ms) 超时
  T3: ClearRxState()
  T4: curSlave=0xFF
  T5: pollAck.Reset()
  T6: idx++, Thread.Sleep(IntervalMs)
  T7: 第2轮：curSlave=新从站(0x02), pollActive=true
  T8: pollAck.Reset()
  T9: 发新请求（从站2）
  T10: 从站1的迟到应答到达
  T11: Handle检查从站号：frame[0](0x01) != curSlave(0x02) → 忽略 ✅

仍然安全。curSlave防护了。

但再考虑：如果迟到应答在T7(curSlave=新从站)之后、T9(发新请求)之前到达呢？
  T7: curSlave=0x02
  T7.5: 从站1的迟到应答到达
  T8: Handle检查从站号：frame[0](0x01) != curSlave(0x02) → 忽略 ✅

还是安全。因为curSlave已经是新从站了。

那pollActive=false到底防什么？

关键场景：迟到应答在T2(超时)和T7(下一轮curSlave设置)之间到达。

  T2: WaitOne超时
  T3: ClearRxState()
  T4: curSlave=0xFF ← 此时curSlave是0xFF
  T5: pollAck.Reset()
  T6: Thread.Sleep(IntervalMs) ← 15ms的窗口
  T7: curSlave=新从站

在T4到T7之间，curSlave=0xFF，迟到应答的从站号不会等于0xFF，所以被忽略。

那pollActive=false确实似乎是冗余的？

等等，让我再想想。如果从站号恰好是0xFF呢？虽然Modbus从站号范围是1-247，0xFF不太可能，但理论上...

更重要的是，pollActive=false防护的是另一个场景：

在Handle中，0x03/0x04应答的从站号校验逻辑：

```csharp
byte expect;
if (func == 0x05 || func == 0x85)
    expect = activeWrite?.Slave ?? 0;
else if (func == 0x02 || func == 0x82)
    expect = activeVerify?.Slave ?? 0;
else if (activeRead != null)
    expect = activeRead.Slave;
else
    expect = curSlave;
```

如果activeRead != null（ExecuteRead正在执行），expect = activeRead.Slave。
此时迟到应答的从站号可能等于activeRead.Slave（如果两个请求都是同一从站）。

但这个场景中，pollActive不会被检查（因为activeRead != null，走的是activeRead分支，不是周期轮询分支）。

所以pollActive=false主要防护的是：周期轮询场景下，超时后迟到应答在curSlave被更新前到达，且从站号恰好匹配。

虽然概率很低，但pollActive=false作为额外保险是合理的。

================================================================================
四、总结
================================================================================

【纠正】
之前分析中"T8: WaitOne → 立即返回"是错误的。
第304行的pollAck.Reset()已经清除了残留信号，WaitOne会正常阻塞。

【超时分支第330行的pollAck.Reset()是否冗余？】
在当前代码逻辑下，确实是冗余的——第304行的Reset已经足够。
但作为防御性编程，保留它没有坏处。

【pollActive=false是否冗余？】
在curSlave=0xFF的防护下，pollActive=false的大部分场景是冗余的。
但在极端边界条件下（如从站号恰好匹配），pollActive=false提供额外保险。
两者协同构成"纵深防御"。

【核心教训】
分析时必须严格追踪每个操作的效果，不能忽略中间步骤的Reset。
pollAck.Reset()的效果是"立即清除信号"，之后的WaitOne不会看到被清除的信号。
