为什么 PreciseSleepMs 不能直接用单个 SpinWait(20) 替代
======================================================

一、核心一段（先回答）
不能。Thread.SpinWait(20) 只自旋 20 次迭代，约几十纳秒（不是 20ms！），而我们要等 1.83ms = 1,830,000 纳秒——差了 4~5 个数量级。while 循环的作用是用 Stopwatch 精确计时，没到 1.83ms 就继续 SpinWait(20) 再查，到了才退出。SpinWait(20) 只是"等一小会儿再查表"，while 循环才是"精确控制总等 1.83ms"。去掉 while 就只剩几十纳秒，FrameGapLoop 会疯狂空转查 gap，虽然不漏判但 CPU 烧得更狠且毫无意义。

二、SpinWait(20) 到底等多久（关键误解）

【误解】SpinWait(20) 的 20 是 20ms 或 20μs
【实际】20 是"自旋迭代次数"，每次迭代约几个纳秒，SpinWait(20) 总共约 50~200 纳秒

  SpinWait 内部大致逻辑（简化）：
    for (int i = 0; i < iterations; i++) {
        // 空转（某些架构发 PAUSE 指令让超线程兄弟核有机会跑）
    }
  
  20 次迭代 × 每次约几纳秒 = 几十纳秒
  我们要等 1.83ms = 1,830,000 纳秒
  差距：1,830,000 / 100 ≈ 18,000 倍

三、各方案对比（能不能不用 while）

方案 | 代码                          | 实际等待        | 精度   | 可移植 | 评价
-----|------------------------------|----------------|--------|--------|------------------
A    | SpinWait(20)                 | ≈100纳秒       | 不可控  | ✗      | 差1.8万倍，不行
B    | SpinWait(超大数如180000)      | ≈1.83ms(本机)  | 不可控  | ✗      | 换CPU就不对
C    | Thread.Sleep(1)              | ≈15.6ms        | 15.6ms | ✓      | 太长，漏判帧结束
D    | while(Stopwatch没到){}       | =1.83ms        | 微秒级  | ✓      | 纯空转，CPU满载伤兄弟核
E    | while+SpinWait(20)           | =1.83ms        | 微秒级  | ✓      | ★当前方案，精确+轻微让步

四、为什么 SpinWait(大数) 也不行（方案B详解）

  理论上可以算：1.83ms / 每次迭代纳秒 = 迭代次数，比如 1,830,000 / 10 = 183,000
  SpinWait(183000) 在本机可能正好 1.83ms。

  但不可行：
  1.每次迭代时间取决于 CPU 频率/缓存/分支预测，不同机器不同
    i7-12700 @3.6GHz 和 i5-8250U @1.6GHz 差 2 倍多
  2.同一台机器动态调频（省电降频）也会变
  3.没有可靠的"迭代次数→时间"公式，只能实测，实测完换机器又不对
  4.SpinWait 内部对超线程/PAUSE 的处理在不同架构不同

  所以必须用 Stopwatch 计时做"到了没"的判断，不能靠"自旋次数"猜时间。

五、while 循环的真正作用（类比理解）

【闹钟类比】
  SpinWait(20) = 看一眼表（几十纳秒）
  while + Stopwatch + SpinWait(20) = 每隔几十纳秒看一眼表，没到1.83ms继续看，到了才停

  你要"等到1.83ms"，不能"看一眼表就走"（只等了几十纳秒），
  要"反复看表直到时间到"——反复看 = while 循环。

【烧水类比】
  SpinWait(20) = 瞄一眼水壶没开
  while + Stopwatch = 一直守着看，没开继续等，开了才关火
  不用 while = 瞄一眼没开就走了，水烧干都不知道

六、去掉 while 会怎样（具体后果）

  如果 FrameGapLoop 里改成：
    while (running) {
        ...查gap...
        Thread.SpinWait(20);   // 去掉PreciseSleepMs，直接SpinWait(20)
    }

  后果：
  1.PollMs 失效：本意每1.83ms查一次，变成每几十纳秒查一次
  2.查 gap 的频率暴涨：从 550次/秒 变成 1000万次/秒
  3.查 gap 本身要读 Stopwatch + 算术 + 比较，每次几十纳秒
  4.CPU 100% 满载（比当前还狠，当前至少 SpinWait(20) 有轻微让步）
  5.功能上不漏判（查得更频繁反而更不会漏），但：
    - CPU 烧满一个核，影响其他线程调度
    - SpinWait(20) 的"让步"意义丧失（让步是给兄弟核喘息，但查 gap 紧接着又 SpinWait）
    - 笔记本功耗飙升、风扇狂转
  6.本质退化成方案D（纯空转），且比方案D更浪费（多了无意义的 gap 计算）

七、诚实补充（所有我知道的信息）

1. SpinWait 的参数叫 iterations 不是 ms，这是 .NET 命名明确的。
   文档原文："The number of times to spin."
   这是之前 BUG3（Thread.SpinWait(IntervalMs) 把10ms间隔变≈0）的同款陷阱。

2. .NET 还有 Thread.SpinWait(int) 的重载只有这一个，没有"按时间等"的版本。
   要按时间等就得自己 while + Stopwatch，即 PreciseSleepMs 的做法。

3. 方案D（纯空转 while(没到){}）和方案E（while+SpinWait(20)）时间精度一样，
   差别在 CPU 影响：
   - 纯空转：CPU 流水线满载，超线程兄弟核被饿死
   - SpinWait(20)：内部发 PAUSE 指令（x86），给兄弟核让出执行资源
   所以 SpinWait 不是为了"等更久"，是为了"等得更文明"。

4. 更省 CPU 的替代（代码没用）：Monitor.Wait(剩余时间) 挂起，OnData 来字节时 Pulse 唤醒。
   不用忙等，精度不减还不烧核。但改动大，当前选忙等是拿 CPU 换实现简单。

5. 1.83ms 的 while 循环每轮约 100 纳秒（SpinWait20约50 + Stopwatch读取约30 + 比较约10），
   1.83ms / 100ns ≈ 18,300 轮。所以 while 实际跑约 1.8 万次，不是"无限循环"，
   是"有限次精确填充1.83ms"。

八、记忆口诀

「SpinWait(20) 等几十纳秒不是20ms，差1.83ms有1.8万倍；
 while+Stopwatch 才是精确等，SpinWait 只是看一眼表再查；
 靠自旋次数猜时间不可移植，必须 Stopwatch 计时做判断；
 去掉while退化成纯空转，CPU烧更狠且无意义，PollMs节拍全失效」
