expect 局部变量与 curSlave volatile 读取时序分析报告
================================================================================
分析时间：2026-11-04
分析对象：F:\chenbo\Program.cs 的 Handle 方法中 byte expect 与 curSlave 的关系
================================================================================


一、用户问题
================================================================================
byte expect; 这个线程栈的值，expect = curSlave; 这个值是缓存了的，
我在 curSlave = 0xFF; 之前，expect 这个是旧值的嘛，对程序有影响？


二、结论：对程序没有影响
================================================================================
expect 是局部变量（值拷贝），curSlave 是 volatile 字段（强制读主内存）。
expect = curSlave 读到的是"某一时刻 curSlave 的真实值"，不存在 CPU 缓存旧值的问题。
无论读到旧值(1)还是新值(0xFF)，都不会导致错误结果。


三、关键概念澄清
================================================================================

3.1 expect 是局部变量（线程栈）
--------------------------------------------------------------------------------
  byte expect;  // 声明在 Handle 方法内，分配在线程栈
  expect = curSlave;  // 一次性值拷贝：读 curSlave 当前值 → 赋给 expect
  expect 在本次 Handle 调用内不再变化，但每次 Handle 调用都是全新的 expect。

3.2 curSlave 是 volatile 字段（主内存）
--------------------------------------------------------------------------------
  static volatile byte curSlave;
  volatile 的 C# 语义：
    - 读取时：强制从主内存读最新值，不走 CPU 缓存/寄存器优化
    - 写入时：立即刷到主内存，不留在 CPU 写缓冲
  因此 expect = curSlave 读到的一定是"某一时刻 curSlave 的真实值"，
  不存在"缓存了旧值"的问题。

3.3 expect = curSlave 是一次性的原子读
--------------------------------------------------------------------------------
  这一行执行时，读 curSlave 的值赋给 expect，就结束了。
  之后 curSlave 怎么变，都不影响 expect。
  但这次读到的值，要么是 0xFF 写入前的旧值，要么是写入后的新值，二选一。


四、所有可能的时序分析
================================================================================

4.1 场景 A：Handle 读 curSlave 在前，SendLoop 写 0xFF 在后
--------------------------------------------------------------------------------
  t=51    Handle: expect = curSlave → 读到 1（此时 curSlave 还是 1）
  t=51.5  SendLoop 超时分支: curSlave = 0xFF
  t=52    Handle: frame[0](1) == expect(1) → 校验通过 → Set frameReceived

  分析：
  - Handle 处理的是从站1的迟到应答，expect=1 是"正确的期望"（应答确实是给从站1的）
  - Set frameReceived 灯亮
  - 但 SendLoop 超时分支里紧接着执行 frameReceived.Reset() → 灯被关掉
  - ★ 关键：Reset 和 curSlave=0xFF 在 SendLoop 同一线程内连续执行，中间没有 WaitOne
  - 即使 Handle 在 Reset 之后、curSlave=0xFF 之前 Set 了灯，
    curSlave=0xFF 之后 Handle 再读就是 0xFF，不会再 Set
  - 即使 Handle 在 Reset 之前 Set 了灯，Reset 会关掉它
  - 结论：灯最终是灭的，下一轮 WaitOne 正常等 → 无影响

4.2 场景 B：SendLoop 写 0xFF 在前，Handle 读 curSlave 在后
--------------------------------------------------------------------------------
  t=50    SendLoop 超时: frameReceived.Reset()
  t=50    SendLoop 超时: curSlave = 0xFF
  t=51    Handle: expect = curSlave → 读到 0xFF（volatile 强制读主内存）
  t=51    Handle: frame[0](1) != expect(0xFF) → 校验失败 → 走"忽略"分支 → 不 Set

  分析：
  - 这正是修复要达到的效果：迟到应答被忽略，不 Set
  - 结论：完全正确

4.3 场景 C：Handle 读 curSlave 和 SendLoop 写 0xFF 同时发生
--------------------------------------------------------------------------------
  volatile 保证读和写是原子的（byte 是 8 位，原子读写在所有平台上保证）
  要么读到旧值 1（场景 A），要么读到新值 0xFF（场景 B），不会读到中间态
  结论：退化为 A 或 B，无影响


五、为什么场景 A 也不会出问题（关键论证）
================================================================================

5.1 SendLoop 超时分支的执行顺序（同一线程内连续执行）
--------------------------------------------------------------------------------
  if (!frameReceived.WaitOne(TimeoutMs))   // 超时返回 false
  {
      sp.DiscardInBuffer();    // ① 清驱动缓冲
      buf.Clear();             // ② 清残帧
      frameReceived.Reset();   // ③ 关灯
      curSlave = 0xFF;         // ④ 置无效从站（修复新增）
  }
  // ⑤ idx++ 轮下一个
  // ⑥ 下一轮 curSlave = id

  ①②③④ 在同一线程内连续执行，中间没有 WaitOne/Sleep/yield（除了锁操作）。
  Handle 在另一个线程（OnData 回调线程）执行。

5.2 Handle 在超时分支执行期间 Set 灯的所有可能位置
--------------------------------------------------------------------------------
  位置1：在 ① 之前 Set → ③ 的 Reset 会关掉 → 灯灭 → 无影响
  位置2：在 ①② 之间 Set → ③ 的 Reset 会关掉 → 灯灭 → 无影响
  位置3：在 ②③ 之间 Set → ③ 的 Reset 会关掉 → 灯灭 → 无影响
  位置4：在 ③④ 之间 Set → ★ 灯亮了，但 ④ 之后 Handle 读 curSlave=0xFF → 不再 Set
         → 但这次 Set 的灯还亮着！下一轮 WaitOne 会立即返回 true！
  位置5：在 ④ 之后 Set → Handle 读 curSlave=0xFF → 校验失败 → 不会 Set → 无影响

  ★ 位置4 是唯一可能出问题的点！

5.3 位置4 的深入分析
--------------------------------------------------------------------------------
  时序：
    t=50.0  SendLoop: frameReceived.Reset()   // 灯灭
    t=50.1  Handle: expect = curSlave         // 读到 1（curSlave 还没被置 0xFF）
    t=50.2  Handle: frame[0](1) == expect(1)  // 校验通过
    t=50.3  Handle: frameReceived.Set()       // 灯亮！
    t=50.4  SendLoop: curSlave = 0xFF         // 置无效
    t=50.5  SendLoop: 超时分支结束，idx++
    t=50.6  SendLoop: 下一轮 curSlave = 2
    t=50.7  SendLoop: sp.Write(从站2请求)
    t=50.8  SendLoop: frameReceived.WaitOne(50) // ★ 灯是亮的！立即返回 true！
    // 误判从站2应答成功，但实际是从站1的迟到应答

  ★ 位置4 确实有问题！expect 读到旧值 1，校验通过 Set 了灯，
    Reset 已经执行过了关不掉，下一轮 WaitOne 误判成功。

5.4 位置4 问题的本质
--------------------------------------------------------------------------------
  问题不在 expect 缓存旧值（volatile 保证了读到的是真实值），
  问题在于 Reset 和 curSlave=0xFF 之间有窗口：
    Reset 之后灯灭了，但 curSlave 还是旧值，
    Handle 在此窗口内读到旧 curSlave → 校验通过 → Set → 灯又亮了
  这是"Reset 在前、curSlave=0xFF 在后"的顺序问题。

5.5 修复方案：调换顺序，先置 curSlave=0xFF 再 Reset
--------------------------------------------------------------------------------
  把超时分支改为：
    sp.DiscardInBuffer();
    buf.Clear();
    curSlave = 0xFF;         // ★ 先置无效，阻断迟到应答的校验
    frameReceived.Reset();   // 再关灯

  这样位置4 的窗口被消除：
    - curSlave=0xFF 之后，Handle 读到 0xFF → 校验失败 → 不 Set
    - Reset 关灯之后，不会有新的 Set（curSlave 已无效）
    - 灯确定是灭的，下一轮 WaitOne 正常等


六、最终修复
================================================================================
  调换 SendLoop 超时分支中 curSlave=0xFF 和 frameReceived.Reset() 的顺序：
  先 curSlave=0xFF（阻断迟到应答校验），再 frameReceived.Reset()（关灯）。

  ExecuteRead 超时分支同理：先 curSlave=0xFF，再（如果有）Reset。


七、总结
================================================================================
用户的问题非常精准。expect 是局部变量值拷贝，curSlave 是 volatile 强制读主内存，
不存在 CPU 缓存旧值的问题。但分析过程中发现了一个更深层的问题：
Reset 和 curSlave=0xFF 的执行顺序有讲究——
必须先 curSlave=0xFF（阻断校验），再 Reset（关灯），
否则两者之间的窗口内迟到应答仍可能 Set 灯，导致下一轮误判。
