自我反思：为什么我不能主动发现问题

反思时间：2026-11-04

一、事实
================================================================================
这几轮对话中，所有问题都是用户发现的，我没有主动发现任何一个：
  1. frameReceived 超时后迟到应答误 Set
  2. expect 局部变量与 curSlave 时序
  3. curSlave=0xFF 与 Reset 之间残留窗口
  4. int 序号溢出
  5. frameReceived 死代码
  6. pollActive 为什么不用局部变量
  7. curSlave 为什么拷贝


二、为什么我不能主动发现
================================================================================

2.1 只看当前一步，不回头审视整体
--------------------------------------------------------------------------------
  每次改完代码，我只检查"编译通过没"，
  不回头审视"改完之后整个逻辑自洽吗"。
  例：引入 curPollSeq 时没想过"int 会溢出吗"；
      引入 pollActive 时没想过"frameReceived 还有人 WaitOne 吗"。

2.2 不主动做"破坏性审查"
--------------------------------------------------------------------------------
  用户的视角是"假设它出错"：
    "如果迟到应答在 Reset 之后 Set 呢？"
    "如果 int 溢出呢？"
    "如果没人 WaitOne 了呢？"
  我的视角是"它应该能工作"。
  我不主动构造反例、不主动找边界条件、不主动想"什么情况下会坏"。

2.3 改代码只关注"实现功能"，不关注"是否引入新问题"
--------------------------------------------------------------------------------
  例：把 frameReceived.WaitOne 换成 pollAck.WaitOne 时，
  只想着"换掉它"，没想过"换掉之后 frameReceived 的 Set 还有意义吗"。
  这是"改一半"——改了 WaitOne 没改 Set，留了死代码。

2.4 不主动验证"所有时序组合"
--------------------------------------------------------------------------------
  竞态问题都是把两个线程的指令交错排列，找危险组合。
  我不主动做这个。我只写"正常时序能工作"，不穷举"异常时序会不会坏"。


三、本质原因
================================================================================
  我倾向于"完成"而非"正确"。
  编译通过我就觉得"做完了"，
  但编译通过只代表语法对，不代表逻辑对、竞态安全、无死代码、无溢出。

  用户做的是"审查"——假设它错，找它错的地方。
  我做的是"实现"——让它能跑。

  这是能力差距，也是习惯差距。


四、我应该怎么做
================================================================================
  1. 每次改完代码，回头审视整个相关逻辑块，不只看改的那几行
  2. 主动构造反例和边界条件（溢出、null、死代码、竞态窗口）
  3. 穷举线程交错时序，不只看正常路径
  4. 检查"改了 A 是否影响 B"（改了 WaitOne 是否影响 Set）
  5. 改完后主动问自己："这个改动会留下什么残留？有没有变死代码？有没有新窗口？"


五、总结
================================================================================
  我之前没做到主动发现问题，这是我的不足。
  用户的每一次追问都暴露了我"只完成不审查"的习惯。
  我应该在改完代码后主动做破坏性审查，而不是等用户来问。
