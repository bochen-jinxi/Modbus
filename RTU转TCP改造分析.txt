Modbus RTU → TCP 改造分析（Program.cs → ProgramTcp.cs）
=======================================================

一、改造核心一段
参考 Program.cs（Modbus RTU 串口版）的运行逻辑，写 ProgramTcp.cs（Modbus TCP 版）。截图配置：127.0.0.1:502、Ignore Unit ID 勾选。RTU→TCP 的本质变化：传输层从串口换 TCP（可靠传输）、帧格式从"地址+CRC"换"MBAP头7字节+PDU"、定界从"3.65ms静默"换"MBAP长度字段"、多从站从"总线地址"换"Unit ID（同一TCP连接）"。去掉的：CRC16（TCP有校验）、FrameGapLoop+PreciseSleepMs（TCP靠长度定界不靠静默）、io锁（TCP全双工读写不冲突）、Stopwatch/lastDataTicks（不需要高精度计时）。保留的：多从站轮询、SendLoop发→等→收→解→醒、frameReceived握手、buf攒帧+Drain按长度切、curSlave校验防迟到应答错配。新增的：MBAP头（TID事务标识+Protocol+Length+UnitID）、TID自增配对请求响应、TcpClient连接、ReceiveLoop接收线程（TCP无DataReceived事件要自己循环Read）。

二、RTU vs TCP 逐项对比

方面            | RTU (Program.cs)              | TCP (ProgramTcp.cs)
----------------|------------------------------|----------------------------------
传输层          | SerialPort COM4 @9600        | TcpClient 127.0.0.1:502
帧格式          | [地址][FC][数据][CRC16]      | [MBAP头7字节][PDU]
定界方式        | 3.65ms静默 + 长度字段双保险  | MBAP Length字段（纯长度定界）
校验            | CRC16（每帧2字节）           | 无（TCP底层有校验）
多从站          | RS485总线地址 0x01/0x02      | Unit ID 0x01/0x02（同一连接）
半双工/全双工   | 半双工（收发互斥，要io锁）   | 全双工（收发并行，不要io锁）
帧超时检测      | FrameGapLoop独立线程忙等     | 不需要（长度定界，读够字节即可）
高精度计时      | Stopwatch+SpinWait           | 不需要（无静默判定）
CRC计算         | Crc16/Crc/CrcOk              | 不需要
接收触发        | SerialPort.DataReceived事件  | 自己开ReceiveLoop线程循环Read
事务标识        | 无（靠curSlave匹配）         | TID自增（请求响应配对）+ curSlave
超时            | 50ms（串口18ms交互）         | 1000ms（网络延迟不确定）
间隔            | 15ms（半双工要等总线空闲）   | 100ms（全双工，不急）

三、MBAP头格式（TCP帧结构）

  偏移  长度  字段            | 说明
  ---------------------------|----------------------------------
  0     2     Transaction ID | 事务标识，请求响应配对（自增）
  2     2     Protocol ID    | 0x0000（Modbus协议固定）
  4     2     Length          | 后续字节数 = UnitID(1) + PDU
  6     1     Unit ID         | 从站地址（对应RTU的帧[0]）
  7     1     Function Code   | 功能码（03读保持寄存器）
  8+    变    Data            | 数据区

  请求（读2个寄存器）：TID(2)+0x0000+Length=6(2)+UnitID+03+起始(2)+数量(2) = 12字节
  响应：TID(2)+0x0000+Length(2)+UnitID+03+byteCount(1)+数据(4) = 12字节

  定界：读MBAP头6字节 → 取Length → 总长=6+Length → 读够即一帧
  粘包：buf里多帧 → 按Length切走第一帧，剩余继续切
  拆包：buf不够6+Length → 等下次Read凑够

四、去掉的RTU机制及原因

【去掉CRC16】TCP底层有校验和重传，应用层不需要CRC。
  RTU串口是裸传输，可能位翻转，必须CRC16兜底。
  TCP是可靠传输，数据到应用层一定是完整的，不需要二次校验。

【去掉FrameGapLoop+PreciseSleepMs】TCP靠MBAP Length字段定界，不靠静默。
  RTU没有帧起始符，靠3.65ms静默判帧结束，要独立线程忙等。
  TCP每帧有明确长度，读够字节就是一帧，不需要静默判定。
  → 不需要Stopwatch、lastDataTicks、FrameGapMs、PollMs、SpinWait

【去掉io锁】TCP全双工，读写不冲突。
  RTU半双工RS485，同一时刻只能收或发，要lock(io)互斥。
  TCP全双工，SendLoop写和ReceiveLoop读并行安全，NetworkStream读写线程安全。

【去掉OnFrameGap】没有静默判定就没有"帧超时"概念。
  RTU的OnFrameGap处理"长度判不出但静默说帧结束"的残帧。
  TCP每帧有Length，不存在"判不出长度"的情况（除非连接断开/数据损坏）。

五、保留的RTU机制及原因

【多从站轮询】TCP版仍轮询Unit ID 0x01/0x02。
  截图"Ignore Unit ID"勾选意味着服务器不校验Unit ID，
  但客户端仍按Unit ID区分逻辑从站，curSlave校验防响应错配。

【frameReceived握手】请求-响应同步不变。
  SendLoop发请求→WaitOne等→Handle里Set唤醒→轮下一站。

【buf攒帧+Drain切】TCP流式也可能粘包拆包。
  一次Read可能读到多个帧（粘）或不够一个帧（拆），
  仍需buf攒+按Length切。但比RTU简单：只按Length切，不需要CRC校验、不需要静默兜底。

【curSlave校验】防迟到应答错配下一轮。
  TCP虽然可靠，但应答可能迟到（网络延迟），轮到下一站时上一站应答才到，
  仍需curSlave/TID校验。TID是TCP新增的，比curSlave更精确（每次请求唯一标识）。

六、新增的TCP机制

【TID事务标识】每次请求TID自增，响应带回相同TID。
  RTU没有TID，靠curSlave匹配。TCP有TID，请求响应按TID配对更精确。
  Handle里校验tid==curTid，不匹配说明是迟到/错配的响应，忽略。

【TcpClient连接】TCP要先建立连接。
  RTU打开串口即可收发。TCP要先Connect，连接断开要处理（ReceiveLoop Read返回0）。

【ReceiveLoop接收线程】TCP无DataReceived事件。
  SerialPort有DataReceived事件（池线程回调），TcpClient没有，
  要自己开线程循环stream.Read。Read返回0=连接断开，设running=false。

八、线程模型对比

RTU (4个执行流)              | TCP (3个执行流)
-----------------------------|--------------------------
Main等Ctrl+C                 | Main等Ctrl+C
SendLoop发送                 | SendLoop发送
OnData(串口事件池线程)       | ReceiveLoop(自己开的接收线程)
FrameGapLoop(静默检测)       | 无（不需要）

TCP少一个线程，少一把锁(io)，少一套高精度计时——简洁很多。

九、诚实补充（所有我知道的信息）

1. Modbus TCP 标准端口 502（IANA注册）。
   本地测试用127.0.0.1，实际设备用设备IP。
   多设备可以多个TcpClient连不同IP，或一个连接用不同Unit ID（取决于设备支持）。

2. "Ignore Unit ID"勾选是服务器端行为（不校验Unit ID，任何Unit ID都响应）。
   客户端仍需发送Unit ID（MBAP头必须有），只是服务器不区分。
   本程序仍按Unit ID轮询0x01/0x02，如果服务器Ignore，两个Unit ID可能返回相同数据。

3. TCP的"粘包拆包"和RTU不同：
   RTU：物理层可能一次收多帧/一帧分多次（串口缓冲区行为）
   TCP：TCP是流式协议，Nagle算法可能合并小包、拆大包
   但应用层处理一样：buf攒+按Length切。

4. TCP不需要超时清buf吗？需要。
   超时后buf里可能有迟到数据，Clear防止错配下一轮——和RTU一样。
   但TCP"迟到"概率比RTU低（TCP保证顺序，不丢不重）。

5. TCP版没有DrainInLock的竞态问题：
   RTU的OnFrameGap两次加锁竞态在TCP不存在（没有OnFrameGap）。
   TCP的Drain只有一次lock(gate)切帧，天然原子。
   但仍用DrainInLock模式+Monitor.IsEntered检查（防御性编程，保持一致风格）。

6. NetworkStream.ReadTimeout 可以设读超时，但本程序用frameReceived.WaitOne(TimeoutMs)控制，
   ReceiveLoop的Read阻塞等数据。连接断开时Read返回0或抛异常，ReceiveLoop退出。

十、记忆口诀

「RTU换TCP：去CRC去静默去io锁去FrameGap，留轮询留握手留buf切留curSlave；
 MBAP头7字节TID+Proto+Length+UnitID，长度字段定界不靠静默；
 TCP全双工读写并行不要io锁，3线程够（Main+Send+Receive）；
 TID自增配对请求响应，比curSlave更精确防错配」
