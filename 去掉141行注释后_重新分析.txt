【1. 新的线程全景】
================================================================================

  现在同时运行的线程：
    1. 主线程 Main：while(running) Sleep(200)
    2. SendLoop（读轮询）：每 15ms 对 Slaves[] 轮询发 0x03 读请求
    3. FrameGapLoop（帧超时检测）：1.83ms 轮询判定 3.5 字符静默
    4. WriteLoop（写消费者）：从 writeQueue 取请求执行
    5. CmdLoop（命令输入）：Console.ReadLine 阻塞
    6. OnData（串口回调）：DataReceived 事件触发
    7. ThreadPool 工作线程：异步命令结果打印

  ★ 核心冲突：SendLoop 和 WriteLoop 都会 sp.Write，且都会等应答，
    两者并发运行，总线时序会相互干扰。

【2. 读写并存后的 5 个新风险（按严重度排序）】
================================================================================

  ── 风险1（严重）：读事务进行中被打断，写帧插入，总线撞车 ──

    时序：
      t0: SendLoop 发读请求帧 A → 释放 io 锁 → frameReceived.WaitOne(50ms)
      t1: WriteLoop 抢到 io 锁 → 发写请求帧 B → 释放 io 锁 → wr.Ack.WaitOne(50ms)
      t2: 从站收到 A，回读应答 A'
      t3: 从站收到 B，回写回显 B'

    问题：
      (a) A 和 B 在总线上时间太近（< 3.5 字符时间），从站可能把 AB 当成一帧解析失败
      (b) A' 和 B' 在总线上时间太近，Handle 收到混叠数据，CRC 失败
      (c) 即使 A' 和 B' 分开到达，Handle 靠功能码区分：
          - A' 是 0x03 → 走读分支 → frameReceived.Set → SendLoop 醒了
          - B' 是 0x05 → 走写分支 → 比对 activeWrite.Frame → wr.Ack.Set → WriteLoop 醒了
          但 curSlave 和 activeWrite 可能指向不同从站，应答归属判定会混乱

    ★ 这是 RS485 半双工的核心矛盾：物理上同一时刻只能有一个帧在总线上，
      但 SendLoop 和 WriteLoop 逻辑上独立，不互相感知。

  ── 风险2（严重）：应答归属错配 ──

    场景：SendLoop 轮到从站1发读，WriteLoop 对从站2发写
      t0: SendLoop 设 curSlave=1，发读请求
      t1: WriteLoop 设 activeWrite=wr(slave=2)，发写请求
      t2: 从站1 回读应答（0x03）
      t3: Handle 收到 0x03 → expect = curSlave = 1 → frame[0]=1 匹配 → frameReceived.Set
      t4: 从站2 回写回显（0x05）
      t5: Handle 收到 0x05 → expect = activeWrite.Slave = 2 → frame[0]=2 匹配 → wr.Ack.Set

    看起来对了？但有个隐患：
      如果 t2 和 t4 之间 < 3.5 字符时间，两帧在 buf 里粘成一坨，
      DrainInLock 切帧时第一帧 CRC 可能失败（错位），滑动1字节，连锁反应。

    更糟的场景：
      t0: SendLoop curSlave=1 发读
      t1: WriteLoop activeWrite=wr(slave=2) 发写
      t2: 从站1 回读应答 0x03
      t3: Handle 收到 0x03 → expect=curSlave=1 → 匹配 → frameReceived.Set
      t4: SendLoop 醒了，curSlave=2（轮下一个），发新读请求
      t5: 从站2 回写回显 0x05 到了
      t6: Handle 收到 0x05 → expect=activeWrite.Slave=2 → 匹配 → wr.Ack.Set
      → 看似没问题

      但如果 t5 的写回显迟到，t4 之前到：
      t4': 写回显 0x05 到 → Handle → expect=activeWrite.Slave=2 → 匹配 → wr.Ack.Set
      → WriteLoop 醒了，activeWrite 变 null（实际没置 null，指向旧 wr）
      → SendLoop 还在等读应答，frameReceived 没 Set → 超时
      → 读数据丢失

    ★ 归属判定靠 curSlave/activeWrite 的瞬时值，读写并发时这两个值各自变化，
      错配窗口真实存在。

  ── 风险3（中等）：清状态互相干扰 ──

    SendLoop 超时后清状态（第190-192行）：
      lock(io) DiscardInBuffer + lock(gate) buf.Clear + frameReceived.Reset

    ExecuteWrite 每次发前清状态（第541-543行）：
      lock(io) DiscardInBuffer + lock(gate) buf.Clear + wr.Ack.Reset

    场景：
      t0: SendLoop 发读，等应答
      t1: WriteLoop ExecuteWrite 清状态 → buf.Clear
      t2: 此时 OnData 刚把读应答前几字节加进 buf → 被 WriteLoop 清掉
      t3: 读应答剩余字节到达 → buf 里只有半帧 → 永远凑不齐 → SendLoop 超时

    ★ WriteLoop 的清状态会清掉 SendLoop 正在接收的读应答。
      反之亦然。清状态是"全局破坏性的"，不区分"这是谁的应答"。

  ── 风险4（中等）：frameReceived 信号被写应答误触发 ──

    Handle 第383行：异常响应里 `else frameReceived.Set();`
    Handle 第436行：读应答解析完 `frameReceived.Set();`

    场景：WriteLoop 发写，从站回异常响应 0x85
      Handle 第377行：orig=0x05 → 走写分支 → aw.AckOk=false; aw.Ack.Set()
      → 不会 frameReceived.Set，OK

    但如果 orig != 0x05（比如读异常 0x83）：
      Handle 第383行：frameReceived.Set()
      → SendLoop 如果正在等读应答，被错误唤醒
      → 但 SendLoop 等的是它自己发的读请求的应答，不是写异常
      → SendLoop 醒了，认为读成功，实际没收到读数据 → 下一轮 idx++ 跳过该从站

    ★ 这个风险在"只有写"时不存在（SendLoop 没启动），现在出现了。

  ── 风险5（低）：CPU 占用增加 ──

    SendLoop 每 15ms 发一次，FrameGapLoop 每 1.83ms 轮一次，
    两者都持续运行，CPU 占用比"只有写"时高。
    对 9600bps 低频场景影响不大，但需知道。

【3. 现有代码能扛住吗？逐风险评估】
================================================================================

  风险1（总线撞车）：
    现有保护：lock(io) 串行化 sp.Write，发送瞬间不会两帧同时上总线。
    但发送间隔不保证 > 3.5 字符时间（3.65ms）。
    SendLoop 发完释放 io，WriteLoop 立即抢到发，两帧间隔可能 < 3.65ms。
    → 从站可能把两帧当一帧解析失败。
    ★ 现有代码扛不住，需要加事务级互斥。

  风险2（应答错配）：
    现有保护：Handle 用 curSlave/activeWrite 区分读写应答，功能码区分帧类型。
    单线程时正确。读写并发时，curSlave 和 activeWrite 各自变化，有错配窗口。
    但 0x05 有整帧比对兜底，0x03 只比对从站号——如果从站号碰巧相同（比如读从站1和写从站1并发），会错配。
    ★ 现有代码部分扛得住（不同从站时），同从站并发读写会错配。

  风险3（清状态互相干扰）：
    现有保护：lock(gate) 保护 buf，但 Clear 不区分"谁的应答"。
    WriteLoop 清状态会清掉 SendLoop 正在收的读应答。
    ★ 现有代码扛不住。

  风险4（frameReceived 误触发）：
    现有保护：Handle 用功能码区分，写异常走 aw.Ack 不走 frameReceived。
    但读异常（0x83）走 frameReceived.Set——如果 SendLoop 没发读请求却收到读异常，
    frameReceived 被 Set，下次 SendLoop WaitOne 立即返回 true（无应答误判成功）。
    实际：SendLoop 每轮都发读，所以 frameReceived.Set 通常对应真实读请求，
    但时序错位时（上一轮的读异常唤醒下一轮的 WaitOne）会误判。
    ★ 现有代码基本扛得住，边缘场景有风险。

  风险5（CPU）：
    可接受。
    ★ 扛得住。

  ───────────────────────────────────────────────────────────────────
  总评：现有代码在"读写不同从站、应答不粘帧"的幸运情况下能跑，
        但在"读写同从站"或"应答粘帧"或"清状态时序冲突"时会出错。
        不是"一定崩"，而是"偶尔出问题，难复现"。
  ───────────────────────────────────────────────────────────────────

【4. 要安全并存，必须改的 3 处】
================================================================================

  ── 必改1：事务级总线互斥（解决风险1、3）──

    加 busLock，SendLoop 和 WriteLoop 的整个事务（发+等应答）都持锁：
      static readonly object busLock = new object();

      SendLoop:
        if (!Monitor.TryEnter(busLock, 0)) { Thread.Sleep(1); continue; }
        try { 发读 + 等应答 }
        finally { Monitor.Exit(busLock); }

      WriteLoop:
        lock (busLock) { ExecuteWrite(wr); }

    效果：写事务期间读让步，读事务期间写等待，总线事务级独占。
    锁顺序：busLock → io → gate，统一不死锁。
    代价：读有近 200ms 空洞（写3次重试），写有近 68ms 延迟（读等应答）。

  ── 必改2：ExecuteWrite 返回后清 activeWrite（解决风险2残留）──

    现状：ExecuteWrite 返回后 activeWrite 仍指向旧 wr。
    改为：finally { activeWrite = null; }
    效果：写完成后，迟到的写回显不会拿旧 wr 比对，直接走 aw==null 丢弃。

  ── 必改3：SendLoop 超时清状态前确认"清的是自己的应答"──

    现状：SendLoop 超时后无条件 buf.Clear。
    风险：如果 WriteLoop 正在收写回显，被清掉。
    改法1（简单）：有了 busLock 互斥，SendLoop 清状态时 WriteLoop 不会在收（写让步了），安全。
    改法2（更严）：清状态前检查 buf 里是否是读应答（看功能码），是才清。
    → 有 busLock 后改法1 就够，不需要改法2。

  ★ 必改1 是核心，必改2 是兜底，必改3 被 必改1 覆盖。
    做了 必改1 + 必改2，读写安全并存。

  static readonly object busLock = new object();

  static void SendLoop() {
      int idx = 0;
      while (running) {
          // ★ 非阻塞试 busLock，拿不到说明写事务在执行，跳过本轮读
          if (!Monitor.TryEnter(busLock, 0)) { Thread.Sleep(1); continue; }
          try {
              byte id = Slaves[idx];
              byte[] req = { id, 0x03, 0x00, 0x00, (byte)(RegCount>>8), (byte)(RegCount&0xFF) };
              byte[] frame = Crc(req);
              curSlave = id;
              if (!SendFrame(frame)) break;
              if (Verbose) Console.WriteLine($"[发送→从站{id:X2}] {Hex(frame)}");
              if (!frameReceived.WaitOne(TimeoutMs)) {
                  if (Verbose) Console.WriteLine($"[超时] 从站{id:X2}");
                  ClearRxState();
                  frameReceived.Reset();
              }
              idx = (idx + 1) % Slaves.Length;
          }
          finally { Monitor.Exit(busLock); }
          Thread.Sleep(IntervalMs);
      }
  }

  static void WriteLoop() {
      while (running) {
          if (!writeQueue.TryDequeue(out var wr)) { Thread.Sleep(5); continue; }
          lock (busLock) {                    // ★ 写事务独占总线
              wr.Result = ExecuteWrite(wr);
          }
          wr.Completed.Set();
      }
  }

      }
      finally {
          activeWrite = null;                // ★ 必改2：写完清活跃引用
      }

【6. 不改会怎样（诚实评估）】
================================================================================

  如果去掉注释但不加这 3 处改动，实际运行表现：

  乐观情况（从站响应快、读写不同从站、不粘帧）：
    → 大概率能跑，偶尔超时，偶尔 CRC 错，日志有噪声但功能基本正常。
    → 因为 9600bps 下帧间隔 15ms 远大于 3.65ms，撞车概率不高。
    → 用户感觉"好像能用，偶尔有点问题"。

  悲观情况（从站慢、读写同从站、应答粘帧）：
    → 频繁超时、CRC 错、清状态互相干扰、应答错配
    → 温湿度采集中断、写命令偶发失败
    → 用户感觉"不稳定，难复现"

  最坏情况（某从站掉线）：
    → SendLoop 每轮对该从站超时 50ms，期间 WriteLoop 清状态可能打断其他从站的应答
    → 连锁反应，整体通信恶化

  ★ 不改不是"一定崩"，是"概率性出问题"。
    对学习/调试可接受，对生产部署不可接受。

【7. 还有一个被忽视的问题：SendLoop 没有 try-catch】
================================================================================

  SendLoop 第176-181行 sp.Write 无 try-catch。
  之前 SendLoop 没启动，不是问题。现在启动了：
    如果 sp.Write 抛异常（串口突然拔掉），SendLoop 线程静默退出，
    读轮询停止，但 WriteLoop 还在跑，程序"半死不活"。

  ★ 必须加 try-catch，至少打印日志 + continue，不要让线程死。

【8. 总结】
================================================================================

  去掉第141行注释后，从"只有写"变成"读写并存"，质变。

  新增 5 个风险：
    1. 总线撞车（严重）—— lock(io) 只保护发送瞬间，不保护事务间隔
    2. 应答错配（严重）—— curSlave/activeWrite 并发变化，同从站读写会错配
    3. 清状态互相干扰（中等）—— WriteLoop 清掉 SendLoop 正在收的应答
    4. frameReceived 误触发（中等）—— 读异常唤醒错误的 WaitOne
    5. CPU 占用增加（低）—— 可接受

  现有代码能扛住的风险：风险5、风险4边缘
  现有代码扛不住的风险：风险1、风险2同从站、风险3

  必改 3 处：
    1. 加 busLock 事务级互斥（核心，解决风险1、3）
    2. ExecuteWrite 返回后 activeWrite=null（兜底，解决风险2残留）
    3. SendLoop 加 try-catch（修复线程静默退出）

  不改的后果：
    乐观情况大概率能跑但偶尔出问题，悲观情况通信恶化，最坏情况半死不活。
    学习调试可接受，生产部署不可接受。

  一句话：去掉注释是"让读轮询启动"，但要"读写安全并存"还需要加事务级互斥。
           现在的状态是"能跑但不安全"。
