【0. 一句话定性】
这是一个基于 C# SerialPort 的 Modbus RTU 串口通信程序，运行在 Windows COM4 / 9600bps，
挂接多个从站（0x01、0x02），实现：
  - 多从站轮询读保持寄存器（功能码 0x03，读温湿度）
  - 写单个线圈（功能码 0x05，开关"开到位/关到位"）
  - 支持命令行参数模式与交互命令模式
  - 支持多按钮/多命令并发提交、串行执行（适配 RS485 半双工）
  - 高精度 3.5 字符帧定界（Stopwatch + SpinWait）
  - 失败重试、异常响应处理、迟到应答过滤、CRC 错位重新对齐

【2. 线程模型（共 5 类线程）】
================================================================================

2.1 主线程 Main
  - 解析参数模式 / 初始化串口 / 启动后台线程 / while(running) Sleep(200) 等待退出
  - 退出时 lock(io) 关闭串口

2.2 发送线程 SendLoop（注意：交互模式下被注释掉 tx.Start()）
  - 多从站轮询：构造 0x03 读请求 → 设 curSlave → 发送 → 等 frameReceived
  - 超时清空接收状态（DiscardInBuffer + buf.Clear + frameReceived.Reset）
  - 轮询间隔 IntervalMs
  - ★ 重要发现：第 141 行 `// tx.Start();` 被注释，交互模式下读轮询未启动！
    只有参数模式不会走这里；交互模式只做写操作，不做读轮询。

2.3 帧超时检测线程 FrameGapLoop
  - 高精度轮询：读 lastDataTicks → 算 gapMs → 超 3.5 字符则 OnFrameGap
  - 用 PreciseSleepMs(PollMs) 忙等，精度微秒级
  - handled 标记避免同一批 lastDataTicks 重复触发

2.4 写线程 WriteLoop（串行消费者）
  - 从 writeQueue 取请求 → ExecuteWrite → 设 Result → Completed.Set
  - 队列空时 Sleep(5) 避免空转
  - ★ 保证 RS485 半双工总线一次只发一帧的核心

2.5 命令线程 CmdLoop
  - 读控制台输入 → 按 ';' 分隔多条命令 → ParseAndSubmit
  - 支持 sync 前缀（同步等结果）/ 默认异步（投递队列 + ThreadPool 打印结果）

2.6 串口回调线程（SerialPort.DataReceived，由底层线程池触发）
  - OnData：lock(io) 读字节 → lock(gate) AddRange + DrainInLock 原子切帧 → Handle

2.7 ThreadPool 工作线程（异步命令结果打印）
  - ParseAndSubmit 异步分支中 QueueUserWorkItem 等 Completed 并打印

【3. Modbus RTU 协议实现细节】
================================================================================

3.1 帧格式
  - 读保持寄存器请求：[从站][0x03][起始地址H][起始地址L][数量H][数量L][CRC_L][CRC_H]
  - 读保持寄存器应答：[从站][0x03][字节数][数据...][CRC_L][CRC_H]  长度 = 3 + byteCount + 2
  - 写单个线圈请求：  [从站][0x05][线圈地址H][线圈地址L][ON=FF00/OFF=0000][CRC_L][CRC_H]
  - 写单个线圈应答：  8 字节回显（与请求完全一致）
  - 异常响应：        [从站][0x80|原功能码][异常码][CRC_L][CRC_H]  固定 5 字节

3.2 大端/小端
  - 多字节字段（地址、数量、寄存器值）：大端，高字节先
  - CRC：小端，低字节先  ← 这是 Modbus RTU 规范要求，代码注释明确指出

3.3 CRC16
  - 初值 0xFFFF，多项式 0xA001（标准 Modbus CRC16）
  - Crc16 计算前 len 字节；Crc 追加 CRC（低字节先）；CrcOk 校验
  - 实现正确，符合 Modbus 规范

3.4 帧长度判定 FrameLength
  - <3 字节：返回 -1（不够帧头）
  - func & 0x80 != 0：异常响应，固定 5 字节
  - func == 0x05：写线圈应答，固定 8 字节
  - func == 0x03/0x04：读应答，3 + byteCount + 2
  - 其他：-1
  - ★ 这是变长帧解析的核心，逻辑正确

3.5 帧定界（3.5 字符时间）
  - FrameGapMs = 3.5 * 10 / BaudRate * 1000  → 9600 下 3.65ms
  - 判定规则：gap < 3.65ms 继续攒帧；gap >= 3.65ms 判定帧结束
  - 1.5ms~3.65ms 模糊区被自然容忍（仍 < 3.65ms，继续攒）
  - PollMs = FrameGapMs/2，保证检测延迟 < 帧间静默，不漏判

【4. 并发与同步机制】
================================================================================

4.1 锁层次（必须保持一致以避免死锁）
  - io：保护串口读写
  - gate：保护 buf
  - 锁顺序约定：io → gate（OnData / SendLoop超时 / ExecuteWrite 清理 都遵循）
  - ★ 检查：OnData 先 lock(io) 再 lock(gate) ✓；SendLoop 超时先 lock(io) 再 lock(gate) ✓；
    ExecuteWrite 清理先 lock(io) 再 lock(gate) ✓。无死锁风险。

4.2 信号量
  - frameReceived（AutoResetEvent）：读操作应答信号，发送线程等，Handle 中 Set
  - WriteRequest.Ack（AutoResetEvent）：单次写回显信号，ExecuteWrite 等，Handle 中 Set
  - WriteRequest.Completed（ManualResetEventSlim）：整个写请求完成信号，WriteSingleCoil 等

4.3 跨线程可见性
  - running / activeWrite / curSlave 用 volatile
  - lastDataTicks 用 Interlocked.Read/Exchange
  - ★ volatile 在 C# 中保证"不缓存"但不保证原子性（对引用类型只保证引用本身的可见性，
    不保证对象内部字段的可见性）。activeWrite 的 Slave/Frame 等字段可见性靠"写线程先赋值
    后发数据，接收线程收到数据时写线程已赋值完成"的时序保证，实际可行但属隐式假设。

4.4 写请求队列
  - ConcurrentQueue 线程安全，多生产者（CmdLoop / 参数模式 / 多按钮）并发 Enqueue 不互斥
  - 单消费者 WriteLoop 串行 Dequeue

4.5 原子切帧
  - OnData 中 AddRange + DrainInLock 合并在同一个 lock(gate) 内，避免 buf.Clear 插入导致数据丢失
  - DrainInLock 用 Monitor.IsEntered 校验调用者持锁

【5. 错误处理与容错】
================================================================================

5.1 写命令重试（ExecuteWrite）
  - 最多 WriteRetry=3 次
  - 每次发前清干净：DiscardInBuffer + buf.Clear + Ack.Reset
  - 发送异常 / 超时 / 异常响应 都算失败，继续重试
  - 重试间隔 IntervalMs=15ms

5.2 读操作超时（SendLoop）
  - TimeoutMs=50ms 没应答 → DiscardInBuffer + buf.Clear + frameReceived.Reset
  - 防止迟到旧应答错配到下一轮

5.3 CRC 失败 & 帧对齐（DrainInLock）
  - CRC 失败 → 滑动 1 字节重新对齐（buf.RemoveRange(0,1)）
  - 防止总线噪声导致帧错位持续累积

5.4 多从站应答错配防护（Handle）
  - 应答帧第1字节 vs expect（写操作看 activeWrite.Slave，读操作看 curSlave）
  - 不匹配 → 忽略，不 Set 信号
  - 0x05 还做整帧比对（frame vs activeWrite.Frame），过滤旧请求迟到应答

5.5 串口写超时
  - sp.WriteTimeout = 1000，避免驱动层无限阻塞

5.6 Ctrl+C 优雅退出
  - Console.CancelKeyPress → running=false
  - 主线程 while(running) Sleep(200) 退出后关串口

【7. 代码质量与潜在问题（诚实补充）】
================================================================================

7.1 已发现的设计问题
  ─────────────────────────────────────────────────────────────────
  (A) ★ SendLoop 被注释掉（第141行 `// tx.Start();`）
      影响：交互模式下读轮询（温湿度采集）完全不工作！
      只有参数模式（写操作）能用，交互模式只能写不能读。
      若用户期望交互模式同时读温湿度，这是 bug；若只是调试写功能，则是有意为之。
      建议：明确意图。要读就取消注释；不读就删掉 SendLoop 避免误导。

  (B) ★ COM4 硬编码（第110、130行）
      不同机器串口号不同，硬编码 COM4 不便携。
      建议：从 args 或配置读取，或自动枚举可用串口。

  (C) ★ Slaves 硬编码 {0x01, 0x02}
      从站列表写死，扩展需改代码重新编译。
      建议：配置化。

  (D) ★ RegCount=2、起始地址 0x0000 硬编码
      读寄存器的地址和数量写死，只能读温湿度。
      建议：配置化或命令化。

7.2 潜在的并发隐患
  ─────────────────────────────────────────────────────────────────
  (E) activeWrite 用 volatile 但其内部字段（Slave/Frame/AckOk 等）无 volatile/锁保护
      风险：理论上接收线程读 aw.AckOk 时可能读到旧值。
      实际：写线程先 activeWrite=wr 再 sp.Write，接收线程收到回显时写线程早已赋值完成，
            且 Ack.Set/Ack.WaitOne 提供内存屏障，实际不会出问题。但属隐式依赖，不够严谨。
      建议：activeWrite 赋值前加 Thread.MemoryBarrier()，或在 lock 内赋值。

  (F) Handle 中 `var aw = activeWrite;` 读后多次访问 aw 的字段
      风险：若中途 activeWrite 被换（理论上 WriteLoop 串行不会换），aw 仍指向旧对象。
      实际：WriteLoop 串行，ExecuteWrite 返回前 activeWrite 不会变，安全。

  (G) OnFrameGap 中 rest 当残帧直接 Handle
      风险：残帧大概率 CRC 失败被丢弃，但若恰好是完整帧的尾巴且 CRC 碰巧通过，会误解析。
      实际：概率极低，可接受。

  (H) ParseAndSubmit 异步分支中 wr 的 GetHashCode() 调用（第667、675行 var xx2/xx）
      看起来是调试残留，无实际作用，应删除。WriteLoop 第524行 var xxx 同理。

7.3 资源/性能问题
  ─────────────────────────────────────────────────────────────────
  (I) PreciseSleepMs 用 SpinWait 忙等，CPU 占用高
      PollMs=1.83ms 的循环 SpinWait(20)，帧检测线程会持续吃满一个 CPU 核。
      对长时间运行的程序不友好。
      建议：对 >1ms 的睡眠用 Thread.Sleep(1) + SpinWait 补尾，降低 CPU。

  (J) buf 用 List<byte>，RemoveRange(0,n) 是 O(n) 拷贝
      高波特率/大流量下频繁 RemoveRange 性能差。
      建议：用环形缓冲区（byte[] + head/tail）或 Queue<byte>。

  (K) OnData 中 sp.Read 一次性读完 BytesToRead
      若数据量大，一次性 Read 可能阻塞较久。9600 下问题不大，115200+ 需注意。

  (L) ThreadPool.QueueUserWorkItem 每条异步命令起一个工作线程等结果
      若用户疯狂输入，会起很多等待线程。实际场景可接受。

7.4 协议/逻辑细节
  ─────────────────────────────────────────────────────────────────
  (M) 温湿度解析假设 n>=2 且第1个寄存器是温度、第2个是湿度
      与具体设备强绑定，换设备需改代码。

  (N) 写线圈成功判定靠"回显帧与发送帧整帧比对"
      正确且严格，比只比对从站号更可靠，能过滤旧请求迟到应答。设计良好。

  (O) 异常响应处理：0x85（写异常）会触发 AckOk=false + Ack.Set，ExecuteWrite 重试
      合理。但读异常（0x83）只 frameReceived.Set，发送线程当成"收到应答"不再重试，
      会直接轮下一个从站——读异常不重试，可能丢失数据。视需求而定。

  (P) SendLoop 超时后 frameReceived.Reset()
      AutoResetEvent 本就是一次性，WaitOne 返回 false 后信号若迟到会被下次 WaitOne 误收。
      显式 Reset 是对的，但注释说"清掉可能残留的Set信号"——AutoReset 不会残留（Set 一次就消耗），
      除非在 WaitOne 超时返回后、Reset 前恰好被 Set。Reset 多余但无害。

7.5 代码风格
  ─────────────────────────────────────────────────────────────────
  (Q) 注释非常详尽，几乎每行都有，对维护友好。
  (R) 中英文混用注释，风格统一性一般，但可读性好。
  (S) 变量名偏短（buf/gate/io/sw），在静态全局上下文中尚可理解。
  (T) 第524行 var xxx=wr.GetHashCode(); 第667行 var xx2=...; 第675行 var xx=...;
      调试残留代码，应删除。

7.6 异常处理
  ─────────────────────────────────────────────────────────────────
  (U) Main 中参数模式 try-catch，交互模式命令 try-catch，写发送 try-catch
      基本覆盖。但 OnData / Handle / FrameGapLoop 内部部分异常未捕获，
      若抛出会终止该后台线程（后台线程异常不冒泡到主线程，静默退出）。
      建议：每个后台线程顶层 try-catch 记录日志。

  (V) sp.Open() 未 try-catch，COM4 不存在/被占用会直接崩溃。
      建议：try-catch 给友好提示。

【8. 数据流时序图（文字版）】
================================================================================

【读操作（参数模式不触发，交互模式被注释）】
  SendLoop:  构造0x03请求 → curSlave=id → sp.Write → frameReceived.WaitOne(50ms)
                                                              ↑
  串口回调:  数据到 → OnData → buf.AddRange → DrainInLock切帧 → Handle
                                                              ↓
  Handle:    CRC校验 → 从站校验 → 解析温湿度 → frameReceived.Set ─┘

  FrameGapLoop: 持续轮询 lastDataTicks → 超3.65ms → OnFrameGap → 切帧 → Handle

【写操作（参数模式 & 交互模式）】
  CmdLoop:   解析输入 → 构造WriteRequest → writeQueue.Enqueue → (异步立即返回)
                                                              ↓
  WriteLoop: TryDequeue → ExecuteWrite ────────────────────────┘
                ↓
  ExecuteWrite: 清接收 → activeWrite=wr → sp.Write → wr.Ack.WaitOne(50ms)
                                                       ↑
  串口回调:    OnData → Handle → 0x05回显比对 → wr.AckOk=true → wr.Ack.Set ─┘
                ↓
  ExecuteWrite: AckOk=true → return true → WriteLoop设Result → Completed.Set
                                                       ↓
  WriteSingleCoil / ThreadPool: 等 Completed → 打印结果

【9. 总结评价】
================================================================================

优点：
  - Modbus RTU 实现规范，CRC、帧定界、变长帧解析正确
  - 多从站轮询 + 写操作并发提交串行执行，适配 RS485 半双工，设计合理
  - 高精度 Stopwatch 帧定界，9600 下 3.65ms 阈值正确
  - 错误处理层次清晰：重试 / 超时清状态 / CRC错位滑动对齐 / 迟到应答过滤
  - 注释极其详尽，可维护性好
  - 0x05 整帧比对过滤旧应答，比只比对从站号更严格，设计良好

需改进：
  - SendLoop 被注释，交互模式读轮询不工作（最关键，需明确意图）
  - COM4 / Slaves / RegCount 硬编码，不便携不灵活
  - PreciseSleepMs 忙等吃 CPU，长跑不友好
  - List<byte> + RemoveRange 性能差，高波特率需换环形缓冲
  - activeWrite 内部字段可见性靠时序隐式保证，不够严谨
  - 调试残留代码（GetHashCode 三处）应删除
  - sp.Open 未 try-catch，COM4 异常会崩溃
  - 后台线程顶层未 try-catch，异常会静默退出线程

整体：是一个功能完整、注释优秀、协议实现规范的 Modbus RTU 工具程序，
      主要问题集中在硬编码、SendLoop被注释、CPU占用、调试残留这几处，
      �!核心逻辑正确，可作为生产用途前!需修复上述问题。
