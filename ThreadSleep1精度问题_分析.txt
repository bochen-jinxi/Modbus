【0. 直接回答】

  ★ 用户说得对。Thread.Sleep(1) 在 Windows 默认配置下实际睡眠约 15.6ms，不是 1ms。
  我写的 Sleep(1) 意图是"短睡让步"，但实际效果是"睡一整个时钟节拍"。

================================================================================
【1. Windows 时钟节拍（timeBeginPeriod 的真相）】
================================================================================

  1.1 Windows 默认时钟节拍
    - Windows 系统时钟（system timer）默认节拍 = 15.625ms（1/64 秒）
    - Thread.Sleep(n) 的实际睡眠 = ceil(n / 15.625) * 15.625ms（向上取整到节拍边界）
    - 所以：
        Sleep(1)  → 实际约 15.6ms（1 个节拍）
        Sleep(15) → 实际约 15.6ms（1 个节拍）
        Sleep(16) → 实际约 31.2ms（2 个节拍）
        Sleep(0)  → 立即让出 CPU（不睡，特殊值）

  1.2 为什么是 15.625ms
    - 硬件定时器（HPET/Local APIC）精度远高于此（微秒级）
    - 但 Windows 默认把系统定时器节拍设为 15.625ms 以省电
    - 节拍越短，定时器中断越频繁，CPU 唤醒次数越多，耗电越大
    - 15.625ms 是"功耗 vs 精度"的默认折中

  1.3 可以改吗？
    - 调 timeBeginPeriod(1) 可以把节拍改为 1ms（全局生效，影响整个进程）
    - 但 .NET Core 3.0+ / .NET 5+ 不再自动调 timeBeginPeriod
    - 需要手动 P/Invoke 调用，且会增加功耗
    - 本程序没有调 timeBeginPeriod，所以默认 15.6ms 节拍生效

  1.4 .NET 的特殊行为
    - .NET Framework 4.x 及更早：某些版本会自动调 timeBeginPeriod(1)
    - .NET Core 3.0+ / .NET 5+：不再自动调，回归 15.6ms 默认
    - 本程序是 net5.0（从 csproj 看），所以 Sleep(1) ≈ 15.6ms

  ★ 用户判断正确：net5.0 下 Thread.Sleep(1) 实际约 15.6ms。

================================================================================
【2. 这会导致什么问题？】
================================================================================

  改造后的代码意图：
    写事务执行时，SendLoop TryEnter 失败 → Sleep(1) 让步 → 重试 TryEnter

  实际行为：
    TryEnter 失败 → Sleep(15.6ms) → 重试 TryEnter

  影响分析：
    (a) 功能正确性：不影响
        - 写事务期间 SendLoop 每隔 15.6ms 试一次 TryEnter
        - 写事务最多 200ms（3次重试×65ms），试 12-13 次足够
        - 写完成后 SendLoop 下次 TryEnter 成功，恢复读轮询
        - 不会死锁，不会饿死

    (b) 响应延迟：有影响但可接受
        - 写完成后，SendLoop 最多再等 15.6ms 才恢复读
        - 比预期的 1ms 慢 15 倍，但读轮询本身间隔 15ms，多 15.6ms 无感
        - 对温湿度采样（秒级变化）完全无影响

    (c) CPU 占用：反而更好
        - Sleep(1) 如果真的睡 1ms，每秒 1000 次循环，CPU 占用高
        - 实际睡 15.6ms，每秒 64 次循环，CPU 占用低
        - 对"让步"场景，睡长一点反而更省 CPU

  ★ 结论：不会导致功能错误，但"1ms"的意图落空，代码有误导性。

【3. 三种修正方案】
================================================================================

  ── 方案A：改成 Sleep(0)（立即让出 CPU 时间片）──
    Thread.Sleep(0) 的语义：立即让出当前 CPU 时间片，不睡。
    优点：响应最快（下次调度立即试 TryEnter）
    缺点：CPU 占用高（如果写事务长，SendLoop 会忙等）
    适用：让步时间极短（< 1ms）的场景
    本场景：写事务可能 200ms，Sleep(0) 会让 SendLoop 忙等 200ms，CPU 飙高
    → 不适合

  ── 方案B：改成 SpinWait（自旋等）──
    Thread.SpinWait(100) 的语义：CPU 自旋 100 次迭代，不睡。
    优点：响应极快（微秒级）
    缺点：CPU 100% 占用（自旋不释放 CPU）
    适用：等待时间极短（< 100us）且不能睡的场景
    本场景：写事务 200ms，SpinWait 会让 CPU 100% 跑 200ms
    → 不适合

  ── 方案C：显式写 Sleep(15) 并注释说明（推荐）──
    Thread.Sleep(15) 的语义：睡约 15.6ms（1 个时钟节拍）
    优点：
      - 名实相符（写 15 实际 15.6，误差小）
      - CPU 占用低（每秒 64 次）
      - 响应延迟可接受（写完成后最多 15.6ms 恢复读）
    缺点：比"理想 1ms"慢，但本场景不需要 1ms 精度
    适用：让步时间 > 1 个时钟节拍的场景
    本场景：读轮询本身间隔 15ms，让步 15.6ms 完全合理
    → 推荐

  ── 方案D：用 AutoResetEvent 信号通知（最优雅但改动大）──
    写事务完成时 Set 一个信号，SendLoop 等这个信号而非 Sleep
    优点：响应最快（写完成立即通知，SendLoop 立即醒）
    缺点：改动大，要加信号量 + 通知点
    适用：对响应延迟敏感的场景
    本场景：15.6ms 延迟可接受，不值得加复杂度
    → 过度设计

  ★ 推荐方案C：改成 Thread.Sleep(15) + 注释说明 Windows 时钟节拍。

【4. 为什么不调 timeBeginPeriod(1) 把节拍改到 1ms】
================================================================================

  可以调，但不推荐：
    (a) 全局副作用：timeBeginPeriod 影响整个进程的所有定时器，不只 Sleep
    (b) 功耗增加：节拍从 15.6ms 改到 1ms，定时器中断频率 ×15，CPU 耗电增加
    (c) .NET 5+ 不再自动调：微软认为默认 15.6ms 对大多数应用够用
    (d) 本场景不需要 1ms 精度：读轮询间隔 15ms，让步 15.6ms 无感

  ★ 保持默认节拍，用 Sleep(15) 适配它，比改节拍更合理。
