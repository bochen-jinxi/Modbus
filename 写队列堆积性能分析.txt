============================================================
写队列堆积性能分析
============================================================
分析时间: 2026-11-03
问题: 多请求投递到 writeQueue 串行消费，会导致队列
      排队增多，有没有性能问题?
============================================================

【一、直接回答】
------------------------------------------------------------
在当前应用场景下 (人机交互输入 on/off 命令)，没有性能问题。
在极端场景下 (程序化高频投递)，会有队列堆积，但已有
超时保护，不会无限堆积。

结论分场景说:
  - 人机交互 (当前实际场景): 完全没问题，队列几乎永远是 0
  - 多按钮"同时"按下 (模拟场景): 队列短暂堆积几个，秒级消化
  - 程序化高频投递 (非设计场景): 会堆积，但有超时兜底

【二、量化分析: 投递速率 vs 消费速率】
------------------------------------------------------------
消费速率 (WriteLoop 处理一个请求的耗时):

  最佳 (首次回显成功):
    发送 <1ms + 等回显 ~18ms (9600bps 下 8 字节传输)
    ≈ 20ms/请求
    → 消费速率上限: 1000/20 = 50 请求/秒

  最坏 (3次全超时):
    3 * (发送 + 50ms超时 + 15ms间隔) = 3 * 66 = 198ms/请求
    → 消费速率下限: 1000/198 ≈ 5 请求/秒

  典型 (1次成功或1次超时后成功):
    ≈ 50~100ms/请求
    → 消费速率典型: 10~20 请求/秒

  还要加 busLock 等待:
    SendLoop 读事务每轮 ~65ms，写优先 (lock 阻塞)，
    最多让读事务做完当前轮 ≈ +0~65ms

  综合消费速率: 约 5~30 请求/秒，典型 10 请求/秒

投递速率 (各种场景):

  场景A: 人机交互 (CmdLoop + Console.ReadLine)
    人类输入速度: 最快 ~5 次/秒 (熟练打字)
    实际: 1~2 次/秒
    → 投递速率 1~5 请求/秒 << 消费速率 10 请求/秒
    → 队列几乎永远为空，零堆积

  场景B: 多按钮同时按下 (一行 ; 分隔多条命令)
    例: "on 1 0; off 2 0; on 1 1" → 3 个请求同时入队
    → 队列瞬间长度 3，消费时间 3*100ms = 300ms
    → 300ms 内全部消化完，用户无感
    → 不是性能问题

  场景C: 程序化高频投递 (非当前设计场景)
    若外部程序以 100 请求/秒投递
    → 消费速率 10/秒 << 投递速率 100/秒
    → 队列每秒净增 90 个，持续堆积
    → 这是问题，但当前代码不支持此场景 (无外部API)

【三、队列堆积的后果 (即使堆积了会怎样)】
------------------------------------------------------------
假设队列堆积了 N 个请求，后果分两层:

1. 对总线/硬件: 无影响
   - WriteLoop 串行消费，RS485 一次一帧，物理上不会冲突
   - 队列再长，发送速率也被消费速率限制，不会轰炸总线

2. 对调用方: 等待时间变长，但有超时保护
   - WriteSingleCoil (同步模式):
     waitMs = 3*(50+15+50)+500 = 695ms
     若排队时间 + 执行时间 > 695ms → 返回 false
     打印 "排队执行超时，可能写队列拥堵"
     → 调用方不会无限等，有界

   - 异步模式 (ParseAndSubmit 的 ThreadPool 回调):
     同样 waitMs = 695ms 超时
     → 不会无限等

   所以即使队列堆积，调用方最多等 695ms 就超时返回，
   不会线程阻塞累积、不会内存泄漏。

3. 对内存: 每个 WriteRequest 约 100 字节
   - 堆积 1000 个 = 100KB，微不足道
   - 且有超时机制，请求不会无限留存 (超时后调用方放弃，
     WriteLoop 仍会消费完，只是结果没人读)

【四、当前代码已有的保护机制】
------------------------------------------------------------
1. 调用方超时 (WriteSingleCoil 第 531-534 行):
     int waitMs = WriteRetry * (TimeoutMs + IntervalMs + 50) + 500;
     if (!wr.Completed.Wait(waitMs)) {
         Console.WriteLine("排队执行超时...");
         return false;
     }
   → 同步调用方有 695ms 上限，不会无限等

2. 异步回调超时 (ParseAndSubmit 第 714-719 行):
     同样 waitMs 超时
   → 异步调用方也有上限

3. WriteLoop 串行消费 (第 543-559 行):
     一次只处理一个，lock(busLock) 独占总线
   → 物理上保护总线

4. busLock 写优先 (SendLoop TryEnter 失败跳过):
   → 写事务不会被读事务无限阻塞

【五、真正的瓶颈不是队列，是 RS485 物理限制】
------------------------------------------------------------
即使队列无限大、CPU 无限快，发送速率也被限制在:
  - 9600bps: 每帧 8 字节 = 80 位 → 8.3ms/帧
  - 加等回显 ~18ms + 帧间隔 15ms → ~40ms/帧
  → 物理上限 25 请求/秒

这是 RS485 半双工 + 同步等应答模式的固有限制，
与队列设计无关。任何方案都突破不了这个物理上限。

所以"队列堆积"是表象，根因是"投递速率 > 物理发送速率"，
此时队列起到了"削峰填谷"的作用——这正是队列的本职工作。

【六、如果真要优化 (假设高频场景)】
------------------------------------------------------------
当前场景不需要优化。若未来要支持高频写，可选:

方案1: 限制队列长度 (有界队列)
  - 投递时检查 writeQueue.Count，超限直接拒绝
  - 优点: 防止无限堆积，快速失败
  - 缺点: 需要调用方处理"被拒绝"

方案2: 合并相邻同地址写
  - 若队列里有多个对同一 (slave,addr) 的写，只保留最后一个
  - 优点: 减少无意义的中间写 (用户快速点按钮时)
  - 缺点: 改变语义 (中间状态丢失)

方案3: 异步回调替代阻塞等
  - 调用方不阻塞，结果通过回调通知
  - 当前异步模式已是这种方式 (ThreadPool.QueueUserWorkItem)
  - 同步模式 (WriteSingleCoil) 才阻塞，且已有超时

方案4: 提高波特率
  - 115200bps 比 9600bps 快 12 倍
  - 物理上限提到 ~300 请求/秒
  - 但需要从站支持

方案5: 批量写 (功能码 0x10 写多个线圈)
  - 一次写多个地址，减少交互次数
  - 但需要从站支持且语义匹配

再次强调: 当前人机交互场景，以上优化都不需要。

【七、诚实补充: 当前代码的一个小隐患】
------------------------------------------------------------
ParseAndSubmit 异步模式 (第 701-725 行) 每次都
ThreadPool.QueueUserWorkItem 起一个后台线程等结果。

如果用户疯狂输入命令 (比如脚本往控制台灌 1000 行)，
会起 1000 个 ThreadPool 线程，每个等 695ms。
- ThreadPool 有上限 (默认 CPU 逻辑核数)，多余排队
- 不会崩溃，但线程池可能饱和
- 这是"高频投递"场景的问题，人机交互不会触发

严格说这不算队列堆积问题，是"每请求一线程"的问题，
但与"高频投递"相关，一并指出。

【八、总结】
------------------------------------------------------------
1. 当前人机交互场景: 队列几乎为空，零性能问题
2. 多按钮同时按: 队列短暂堆积几个，300ms 内消化，无感
3. 程序化高频投递: 会堆积，但有 695ms 超时保护，不会无限
4. 真正瓶颈是 RS485 物理限制 (25 请求/秒)，非队列设计
5. 队列的"堆积"恰是它的本职: 削峰填谷，保护总线

你的担忧在极端场景下成立，在当前场景下不成立。
代码已有超时保护，不会因队列堆积导致挂死。
