问题：ExecuteWrite 和 SendLoop 功能都差不多，能优化（合并）不？
文件：F:\chenbo\Program.cs
分析时间：2026-11-03
结论：不能合并优化。表面相似，本质不同。
==================================================

一、先承认"看起来像"的部分（用户直觉的来源）
--------------------------------------------------
两者确实有相似的"骨架"：

  SendLoop 一轮：
    1) 占 busLock
    2) 构造帧
    3) lock(io) sp.Write 发送
    4) 等应答（frameReceived.WaitOne(TimeoutMs)）
    5) 超时则清缓冲
    6) 释放 busLock

  ExecuteWrite 一次重试：
    1) （busLock 由外层 WriteLoop 占）
    2) 取出帧
    3) lock(io) sp.Write 发送
    4) 等应答（wr.Ack.WaitOne(TimeoutMs)）
    5) 超时则进入下一轮重试
    6) （busLock 由外层释放）

骨架确实都是"发→等→超时处理"。这是用户觉得"差不多"的根源。
但骨架相同 ≠ 功能相同 ≠ 可合并。下面逐条说差异。

二、本质差异清单（9 条，每条都足以否决合并）
--------------------------------------------------

【差异1：调用者与生命周期不同】
  - SendLoop 是一个独立线程的整个主体（Thread tx = new Thread(SendLoop)），
    while(running) 自驱循环，自己管 busLock 的占与放。
  - ExecuteWrite 是被 WriteLoop 调用的"单次请求执行函数"，
    busLock 由 WriteLoop 在外层 lock(busLock) 占好再调进来，
    ExecuteWrite 自己不碰 busLock。
  → 一个是"线程主循环"，一个是"被调用的子函数"，
    合并意味着要把线程结构和调用栈揉在一起，职责混乱。

【差异2：循环驱动方式不同】
  - SendLoop：while(running) 无限循环，靠 Slaves[idx] 轮转，
    每轮一个从站，idx = (idx+1)%Slaves.Length。
    循环条件是全局退出标志 running。
  - ExecuteWrite：for(attempt=1; attempt<=WriteRetry; attempt++) 有限重试，
    重试次数固定 3 次，重试完就 return。
    不轮转从站，从站是入参 wr.Slave 固定的。
  → 一个是"无限轮询多从站"，一个是"有限重试单从站"，
    循环边界、步进、终止条件全不同。

【差异3：应答信号不同（最关键）】
  - SendLoop 等的是全局 frameReceived（AutoResetEvent），
    Handle 里收到 0x03/0x04 读应答时 frameReceived.Set()。
    这是"广播式"信号：谁在等谁被唤醒，不区分是哪一轮。
  - ExecuteWrite 等的是 wr.Ack（每个 WriteRequest 自带的独立 AutoResetEvent），
    Handle 里收到 0x05 写回显时 aw.Ack.Set()。
    这是"定向"信号：只有那个特定的 wr 被唤醒。
  → 信号机制完全不同：全局广播 vs 实例定向。
    合并就要统一信号模型，但读是"无主"的（没有 WriteRequest 对象），
    写是"有主"的，强行统一会引入不必要的对象分配或虚假的"读请求对象"。

【差异4：应答匹配方式不同】
  - SendLoop：靠 curSlave（volatile byte）告诉接收线程"我在等谁"，
    Handle 里用 frame[0] != curSlave 判定迟到应答。
    匹配依据：从站地址。
  - ExecuteWrite：靠 activeWrite（volatile WriteRequest）+ 整帧逐字节比对，
    Handle 里 for(i=0;i<frame.Length;i++) frame[i]!=cur[i] 判定旧应答。
    匹配依据：整帧内容（更严格）。
  → 读只比对从站号（因为读请求帧除从站外都一样，整帧比对无意义）；
    写比对整帧（因为不同写请求可能同从站但不同线圈/值，必须整帧区分）。
    这套匹配逻辑是 Handle 里 func==0x05 分支专用的，读用不上。

【差异5：超时后的处理策略不同】
  - SendLoop 超时：
      lock(io) sp.DiscardInBuffer() + lock(gate) buf.Clear()
      + frameReceived.Reset()
      然后 idx++ 轮下一个从站（放弃本轮，不等了）。
  - ExecuteWrite 超时：
      不清缓冲（下一轮重试开头才清）
      直接进入下一次 attempt 重试（同一个从站再发）。
  → 读超时=放弃换下一个；写超时=重试同一个。
    策略相反，无法用同一段代码表达。

【差异6：重试 vs 不重试】
  - SendLoop：发一次等一次，超时就过，没有重试。
    （因为读是周期轮询，"重试"等价于"下一轮再来"，天然冗余）
  - ExecuteWrite：发一次失败要重试 WriteRetry=3 次，
    每次重试前清缓冲 + Reset Ack + 重发 + 间隔 Sleep。
  → 写有重试循环，读没有。合并要么给读加无意义重试，
    要么把重试做成可选参数——但读的"重试"语义和写的"重试"语义
    完全不同（读重试=换从站再来，写重试=同从站再发），参数化会扭曲语义。

【差异7：发送前的清理不同】
  - SendLoop：发送前不清缓冲（依赖上一轮超时清理或 FrameGapLoop 切帧）。
  - ExecuteWrite：每次重试前必清（DiscardInBuffer + buf.Clear + Ack.Reset），
    因为写要求"回显必须对应当前这次发送"，不能让上一轮的迟到应答混进来。
  → 写对"接收状态干净度"的要求比读严苛得多。
    读可以容忍缓冲里有残帧（FrameGapLoop 会切），写不能容忍（会错配回显）。

【差异8：退出时对 activeWrite 的维护不同】
  - ExecuteWrite 有 finally { activeWrite = null; }
    防止写完成后迟到回显拿旧 wr 比对。
  - SendLoop 不碰 activeWrite（它根本不是写路径）。
  → 这是写路径专属的"接收分发锚点"清理，读路径没有这个对象，无从清理。

【差异9：失败语义与返回值不同】
  - SendLoop：void，没有"成功/失败"返回，超时只打日志。
  - ExecuteWrite：bool，return true 表示写成功（AckOk），
    return false 表示重试耗尽，结果回传给 WriteLoop → wr.Result → 调用方。
  → 读不需要返回结果（数据在 Handle 里直接解析打印），
    写必须返回结果给调用方（用户要知道开关是否到位）。
    合并就要统一返回值，但读的"结果"是温湿度数据（在 Handle 里处理），
    写的"结果"是布尔成功标志，类型都不一样。

三、如果强行合并会怎样（反证）
--------------------------------------------------
假设抽一个通用方法 DoTransaction(frame, waitSignal, retry, ...)：

  1) 参数列表会爆炸：要传"等哪个信号""重试几次""超时后清不清缓冲"
     "成功条件是什么""要不要维护 activeWrite""要不要轮转从站"……
     每个参数都是"读这样、写那样"的二选一，本质是把两个方法
     的差异用 bool 开关堆进一个方法体——这是典型的"假合并"，
     行数没少，可读性反而更差（每个 if 都要想想读路径还是写路径）。

  2) 信号统一不了：读用全局 frameReceived，写用 wr.Ack。
     要统一就得给读也造一个"读请求对象"——但读没有调用方等结果，
     造对象纯属浪费，且 Handle 里 0x03 分支要改成"找当前读请求"，
     引入和写一样的 activeWrite 机制，复杂度净增。

  3) 应答匹配统一不了：读比对从站号，写比对整帧。
     要统一就得都用整帧比对——但读请求帧除从站外都一样，
     整帧比对等价于比对从站号，多此一举；且读没有"Frame"字段
     （读帧是现场构造的局部变量），要存下来比对就得加字段，
     又是写路径的复杂度倒灌读路径。

  4) 重试语义统一不了：读"重试"=换从站，写"重试"=同从站再发。
     一个 retry 参数表达不了两种语义，要么拆成两个参数
     （retryCount + retryStrategy），要么硬塞同一种语义——
     塞写的语义给读，读就变成"同从站连发3次"，违背轮询初衷；
     塞读的语义给写，写就变成"换从站重试"，但写从站是用户指定的，
     不能换。

  5) 测试和维护变难：现在两个方法各自独立，改读不影响写，反之亦然。
     合并后改一处要同时验证读、写两条路径，回归测试面积翻倍。

四、唯一"看起来能抽"的部分：发送那几行
--------------------------------------------------
  lock(io) { if (!sp.IsOpen) ...; sp.Write(frame, 0, frame.Length); }
  这几行两边确实一样。可以抽成 SendFrame(frame) 辅助方法。
  但这属于"工具函数级"抽取，不是"两个方法合并"，
  节省的只是 3-4 行代码，且要处理"读 break、写 return false"的
  退出差异，抽出来收益甚微，反而多一层调用。
  现状不抽也能接受，属于可有可无的微优化，不影响架构。

五、最终结论
--------------------------------------------------
不能合并优化。理由总结：

  1) 两者只是"发→等→超时"骨架相似，这是所有同步式串口通信的
     通用模式，相似是必然的，但不构成合并依据；
  2) 9 条本质差异（调用者、循环驱动、应答信号、匹配方式、超时策略、
     重试、清理、activeWrite 维护、返回值）每一条都不同，
     且每一条都源于"读 vs 写"的固有语义差异，无法消除；
  3) 强行合并会得到一个参数爆炸、bool 开关堆砌的"假通用方法"，
     行数不减、可读性更差、改一处影响两条路径，是负优化；
  4) 唯一可抽的 SendFrame 3-4 行属于微优化，收益甚微，可不抽。

  根本原因：读和写是 RS485 上两种语义完全不同的事务——
  读是"无主、广播、周期、可放弃、不重试、比对从站、结果在 Handle 内消化"；
  写是"有主、定向、触发、必成功、要重试、比对整帧、结果要回传调用方"。
  语义对立的方法，骨架再像也不该合并。
