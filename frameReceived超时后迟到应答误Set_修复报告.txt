一、用户问题描述
================================================================================
SendLoop 方法中，frameReceived 超时后执行了 Reset 关闭了灯，
接收线程又把迟到的应答字符收到后，调用了 Set 方法后，
全局的 frameReceived 灯是否又再次开启了？
如果又再次开启了，那后续轮询的从站数据就会是上次的信号？


二、结论：问题确实存在，是真实的竞态 bug
================================================================================
用户的判断完全正确。在修复前的代码中，存在以下竞态窗口：
  超时 Reset 后 → 迟到应答到达 → Handle 校验通过 → Set → 灯又亮了
  → 下一轮 WaitOne 立即返回 true → 误判成功（拿的是上一轮的旧信号）

  t=35    SendLoop 轮询从站2，curSlave=2，frameReceived 已被 WaitOne 消费（灯灭）

四、根本原因分析
================================================================================

4.1 frameReceived 是全局共享信号
--------------------------------------------------------------------------------
  frameReceived 是一个全局 AutoResetEvent，不区分"哪个请求的应答"。
  任何 0x03/0x04 应答（只要从站校验通过）都会 Set 它。
  SendLoop 用它等"当前轮询从站"的应答，但 Set 的可能是"上一轮迟到应答"。

4.2 超时后的 Reset 和迟到应答的 Set 之间有竞态窗口
--------------------------------------------------------------------------------
  超时分支执行顺序：
    DiscardInBuffer → buf.Clear → frameReceived.Reset → (idx++) → 下一轮
  在 Reset 之后、下一轮 curSlave 赋值之前，有一个时间窗口。
  此窗口内迟到应答到达，Handle 会 Set frameReceived。

4.3 curSlave 更新时机问题
--------------------------------------------------------------------------------
  超时后 curSlave 没有立即失效，仍然是刚超时的从站号。
  迟到应答的从站号 == curSlave → Handle 校验通过 → Set。
  这是竞态能成立的根本原因：校验用的"期望从站"还是旧的。

4.4 DiscardInBuffer 不能清掉"还没到的"数据
--------------------------------------------------------------------------------
  DiscardInBuffer 只清"当前已在驱动缓冲区"的数据。
  迟到应答在 DiscardInBuffer 执行之后才到达，清不掉。
  这是物理事实，无法通过 DiscardInBuffer 解决。


五、修复方案
================================================================================

5.1 核心思路
--------------------------------------------------------------------------------
  超时后立即把 curSlave 置为一个"无效值"（0xFF），
  使迟到应答的从站校验必然失败，Handle 走"忽略"分支 return，不 Set。

5.2 为什么选 0xFF
--------------------------------------------------------------------------------
  Modbus 从站号合法范围是 1~247（0x01~0xF7）。
  0xFF(255) 不在合法范围内，任何真实从站的应答 frame[0] 都不会等于 0xFF。
  因此 curSlave=0xFF 时，frame[0] != curSlave 必然成立 → 校验失败 → 忽略 → 不 Set。

5.3 修复点
--------------------------------------------------------------------------------
  ① SendLoop 超时分支：在 frameReceived.Reset() 之后加 curSlave = 0xFF
  ② ExecuteRead 超时分支：在重试日志之后加 curSlave = 0xFF
     （ExecuteRead 超时后 activeRead 在 finally 置 null，迟到应答会走 curSlave 分支，
      不置无效会污染 SendLoop 下一轮的 frameReceived）

5.4 修复后的时序
--------------------------------------------------------------------------------
  t=0     SendLoop 发从站1请求，curSlave=1
  t=50    超时
  t=50    DiscardInBuffer + buf.Clear + frameReceived.Reset()
  t=50    ★ curSlave = 0xFF（修复新增）
  t=51    从站1迟到应答到达 → Handle
  t=51    Handle 校验：frame[0]==1, curSlave==0xFF → 1 != 0xFF → 校验失败！
  t=51    Handle 走"忽略"分支：打印 [忽略] 从站01的迟到应答 → return → 不 Set
  t=52    SendLoop 下一轮：curSlave=2，sp.Write(从站2请求)
  t=52    frameReceived.WaitOne(50) → 灯是灭的 → 正常等
  t=70    从站2真实应答到达 → Set → WaitOne 返回 true → 正常成功
  ★ 错位不会累积，请求-应答正确配对


六、为什么 ExecuteWrite 超时不需要改 curSlave
================================================================================
  ExecuteWrite 用 wr.Ack（每个写请求独立信号），不是全局 frameReceived。
  超时后 finally 置 activeWrite = null。
  迟到应答到达时：
    - 若是 0x05 回显：Handle 中 activeWrite==null → return 不 Set（不影响任何信号）
    - 若是 0x03 应答：走 activeRead 或 curSlave 分支
      - activeRead != null：Set activeRead.Ack（不影响 wr.Ack）
      - activeRead == null：走 curSlave 分支，可能 Set frameReceived
        但 ExecuteWrite 等的是 wr.Ack 不是 frameReceived，frameReceived 被 Set
        不影响写操作。最坏情况是污染 SendLoop 下一轮，但写操作期间 SendLoop
        拿不到 busLock（TryEnter 失败跳过），不会执行 WaitOne，所以无影响。
  因此 ExecuteWrite 超时不需要改 curSlave。

八、修复的正确性论证
================================================================================

8.1 不影响正常流程
--------------------------------------------------------------------------------
  curSlave = 0xFF 只在超时分支执行，超时本身就是异常情况。
  下一轮发送前 curSlave 会被重新赋值：
    - SendLoop：curSlave = id（第255行）
    - ExecuteRead：curSlave = slave（第795行）
  因此 0xFF 只是"超时到下一轮发送之间"的临时值，不影响正常轮询。

8.2 彻底阻断迟到应答的 Set
--------------------------------------------------------------------------------
  curSlave = 0xFF 后，任何真实从站(1~247)的迟到应答：
    frame[0] ∈ [1, 247], curSlave = 255
    frame[0] != curSlave → Handle 走"忽略"分支 → return → 不 Set
  竞态窗口被彻底关闭。

8.3 不引入新问题
--------------------------------------------------------------------------------
  - 0xFF 不会与任何真实从站冲突（Modbus 从站号上限 247）
  - 不影响 activeRead/activeWrite 的应答分发（它们用各自的 Slave 校验，不用 curSlave）
  - 不影响写操作（写操作不读 curSlave）


九、其他可能的修复方案对比
================================================================================

方案 A：超时后不 Reset，靠 WaitOne 自动消费
  问题：AutoResetEvent.WaitOne 超时返回 false 时不消费信号，
        灯可能还是亮的（如果 Set 发生在 WaitOne 期间但超时了）。
        Reset 是必要的，不能去掉。

方案 B：超时后 Sleep 一小段再继续（等迟到应答自己来）
  问题：不知道要等多久，增加延迟，治标不治本。

方案 C：用"请求序号"匹配应答（最彻底）
  思路：每个请求带递增序号，应答也带序号，序号不匹配则忽略。
  问题：Modbus RTU 应答帧不带请求序号（不像 TCP 版有 TID），
        无法实现。只能靠从站号+功能码+地址近似匹配。

方案 D（本次采用）：超时后置 curSlave 无效
  优点：一行代码，零副作用，彻底阻断校验通过路径。
  缺点：无。


十、总结
================================================================================
用户描述的竞态问题确实存在：frameReceived 超时 Reset 后，迟到应答可能
被 Handle 处理并 Set，导致下一轮 WaitOne 误判成功，请求-应答错位累积。

根本原因是超时后 curSlave 仍指向旧从站，迟到应答校验通过。

修复方案：超时后立即 curSlave = 0xFF（无效从站号），
使迟到应答校验必然失败，走"忽略"分支不 Set。
修复点：SendLoop 超时分支 + ExecuteRead 超时分支。
编译通过，零副作用，不影响正常流程。
