【三、推送过程中的关键诊断与突破】
------------------------------------------------------------
本任务最大难点是网络问题。完整诊断过程如下:

阶段 1: 直接 HTTPS 推送 → 失败
  现象: Failed to connect to github.com port 443
  诊断: ping github.com 可达 (78ms)，但 443 端口连不上。

阶段 2: SSH 各种方式 → 失败
  尝试: git@github.com:22, ssh.github.com:443
  结果: 22 端口不通; 443 端口通但公钥未注册 → 认证失败

阶段 3: 网络根因定位 → 找到真凶
  关键测试:
    - curl https://api.github.com     → HTTP 200 (通!)
    - curl https://codeload.github.com → HTTP 301 (通!)
    - curl https://github.com         → 超时 (不通)
    - nslookup github.com             → 61.139.2.69 (错误 IP!)
  结论: DNS 污染! github.com 被解析到 61.139.2.69
        (四川成都 IP，非 GitHub 真实 IP)，
        导致 443 连接超时。
        而 api.github.com / codeload.github.com 子域名未被污染。

阶段 4: 寻找可用 IP → 成功
  测试多个 GitHub 公开 IP:
    - 20.205.243.166 → 443 不通 (可能也被污染)
    - 140.82.112.3   → 443 通! curl 返回 200/301

阶段 5: 用 IP 绕过 DNS 污染 → 推送成功
  命令:
    git remote set-url origin https://140.82.112.3/bochen-jinxi/Modbus.git
    GIT_SSL_NO_VERIFY=1 git -c http.sslVerify=false \
        -c http.sslBackend=openssl push -u origin main
  结果: git 自动跟随重定向到 github.com，
        推送成功，main -> main 新分支已创建。
  推送后恢复 remote URL 为标准域名:
    git remote set-url origin https://github.com/bochen-jinxi/Modbus.git

【四、根本原因总结】
------------------------------------------------------------
根因: 当前网络环境的 DNS 把 github.com 解析到了错误 IP
      (61.139.2.69，成都某 IP)，这是典型的 DNS 污染/
      劫持现象。GitHub 在国内部分地区经常遭遇此类问题。

绕过方法: 使用 GitHub 真实 IP (140.82.112.3) 直接连接，
          跳过被污染的 DNS 解析。git 跟随 HTTP 301 重定向
          到正确域名完成推送。

说明: 此 IP 可能随时间变化，GitHub 的真实 IP 列表可从
      https://api.github.com/meta 的 "git" 字段获取
      (api.github.com 未被污染，可正常访问)。
