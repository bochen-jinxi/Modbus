============================================================
WriteRequest 三要素实现异步通信 详解
============================================================
日期：2026-11-02
相关代码：F:\chenbo\Program.cs

------------------------------------------------------------
一、结论
------------------------------------------------------------

WriteRequest 类型 + 队列 + 信号量 + 后台线程，三要素缺一不可，
组合起来才能实现"提交方异步提交、执行方串行执行、结果准确回传给提交方"。

------------------------------------------------------------
二、三要素各自的作用
------------------------------------------------============

【要素1：队列 ConcurrentQueue<WriteRequest>】—— 解决"多对一提交"

    多个提交方（按钮A、按钮B、按钮C、控制台...）
            ↓ Enqueue        ↓ Enqueue        ↓ Enqueue
            ┌──────────────────────────────────┐
            │  writeQueue: [wr1, wr2, wr3]      │   ← 队列（线程安全）
            └──────────────────────────────────┘
                            ↓ TryDequeue
                  单个 WriteLoop 写线程（串行消费）

为什么需要：多个按钮可能同一时刻提交。如果没有队列，
多个线程直接调 sp.Write，帧在总线上碰撞。

队列的作用：把"并发的提交"变成"串行的执行"。
提交方 Enqueue 立即返回（非阻塞），执行方按顺序一个一个取。

为什么是 ConcurrentQueue：多线程并发 Enqueue 不需要额外加锁，
无锁实现，性能好且不会死锁。


【要素2：信号量 Ack + Completed】—— 解决"跨线程通知结果"

    执行线程                    提交方线程
       │                          │
       │  发帧 → 等回显            │  提交 wr → 等 wr.Completed
       │  ← Handle 收到回显        │      ↑
       │     wr.Ack.Set() ──────→ │      │ 被唤醒
       │  读 wr.AckOk=true         │
       │  wr.Result=true           │
       │  wr.Completed.Set() ────→│  读 wr.Result=true ✓

两个信号分工：

| 信号    | 谁 Set              | 谁 Wait                  | 作用 |
|---------|--------------------|--------------------------|------|
| Ack     | Handle（收到回显时）| ExecuteWrite（每轮重试） | 通知"这一帧的回显到了"，判断成功/重试 |
| Completed| WriteLoop（执行完）| 提交方（WriteSingleCoil或后台线程）| 通知"请求彻底处理完，可读最终结果" |

为什么需要两个信号：
如果 WriteSingleCoil 和 ExecuteWrite 都 wait 同一个信号，
ExecuteWrite 的 WaitOne 会消费掉信号，WriteSingleCoil 就收不到了。
两个信号分工：Ack 是"单次回显通知"，Completed 是"整个请求完成通知"。

为什么是每个 wr 独立的信号：
如果用全局单例信号，A 的完成会唤醒等 B 的线程（错配）。
每个 wr 自己的 Completed，A 完成只唤醒等 A 的。


【要素3：后台线程 ThreadPool 回调】—— 解决"提交方不等结果继续干活"

    提交方线程                    后台打印线程
       │                            │
       │  Enqueue(wr)                │  (由 ThreadPool 调度)
       │  QueueUserWorkItem(回调) ──→│  捕获 wr
       │  立即返回，继续接收下一条    │  wr.Completed.Wait()
       │                            │  ...阻塞等待...
       │                            │  被唤醒 → 打印 wr.Result

为什么需要：控制台 CmdLoop 提交命令后要立即能接收下一条输入，
不能阻塞等结果。后台线程替它等结果并打印。

为什么用 ThreadPool 而不是 new Thread：
每个回调就是"等信号+打印一行"，是短小任务，线程池复用线程开销小。
new Thread 每次创建销毁几毫秒，浪费。

------------------------------------------------------------
三、三要素缺一不可
------------------------------------------------------------

【缺队列：多按钮提交会帧碰撞】

    按钮A线程: sp.Write(帧A)  ─┐
    按钮B线程: sp.Write(帧B)  ─┤  同时写串口 → 总线上帧A帧B混在一起 → 从站无法解析
    按钮C线程: sp.Write(帧C)  ─┘

【缺信号量：执行完没法通知提交方】

    WriteLoop: ExecuteWrite(wr) → 执行完了，然后呢？
      → 没有 Completed.Set()，提交方永远 Wait 超时
      → 提交方不知道成功还是失败

【缺后台线程：提交方被阻塞】

    CmdLoop: SwitchOn(slave, addr)  ← 阻塞等 Completed
      → 用户输完 "on 1 0" 要等 50ms+ 才能输下一条
      → 无法"同时按多个按钮"（控制台被卡住）

------------------------------------------------------------
四、三要素如何协同（完整时序）
------------------------------------------------------------

用户输入 "on 1 0; off 2 0"

ParseAndSubmit("on 1 0"):
  ① new wr1 { Completed=信号C1 }
  ② writeQueue.Enqueue(wr1)           ← 要素1：队列
  ③ ThreadPool.QueueUserWorkItem(     ← 要素3：后台线程
       _ => wr1.Completed.Wait()      ← 要素2：信号量
            → 打印 wr1.Result)

ParseAndSubmit("off 2 0"):
  ① new wr2 { Completed=信号C2 }
  ② writeQueue.Enqueue(wr2)
  ③ ThreadPool.QueueUserWorkItem(
       _ => wr2.Completed.Wait()
            → 打印 wr2.Result)

WriteLoop (单线程串行):
  TryDequeue → wr1
  ExecuteWrite(wr1):
    activeWrite = wr1
    sp.Write(wr1.Frame)
    wr1.Ack.WaitOne()  ← Handle 收到回显 → wr1.Ack.Set()
    wr1.AckOk=true → return true
  wr1.Result=true
  wr1.Completed.Set()  ← 要素2：唤醒等 wr1 的后台线程

  TryDequeue → wr2
  ExecuteWrite(wr2): ... 同上
  wr2.Completed.Set()  ← 唤醒等 wr2 的后台线程

------------------------------------------------------------
五、WriteRequest 结构回顾
------------------------------------------------------------

    class WriteRequest
    {
        public byte Slave;
        public ushort Addr;
        public bool On;
        public byte[] Frame;                 // 发送帧（含CRC），用于回显比对
        public readonly AutoResetEvent Ack = new AutoResetEvent(false);       // 信号量1：单次回显
        public bool AckOk;                   // 一次回显的结果
        public readonly ManualResetEventSlim Completed = new ManualResetEventSlim(false); // 信号量2：整体完成
        public bool Result;                  // 最终结果
    }

每个 WriteRequest 实例自带：
- 自己的发送帧 Frame（用于回显比对，过滤旧应答）
- 自己的 Ack 信号（Handle → ExecuteWrite 通知单次回显）
- 自己的 Completed 信号（WriteLoop → 提交方通知整体完成）
- 自己的 Result 字段（最终结果）

多个 WriteRequest 互不干扰，靠的就是"每个实例独立信号"。

------------------------------------------------------------
六、为什么这三要素组合能实现"异步通信"
------------------------------------------------------------

"异步通信"的三个要求：
1. 提交方不阻塞 → 靠队列（Enqueue 立即返回）+ 后台线程（替提交方等结果）
2. 执行方串行 → 靠 WriteLoop 单线程 TryDequeue
3. 结果准确回传 → 靠每个 wr 独立的 Completed 信号 + 引用传递

三者关系：
- 队列负责"收集并发请求，交给单线程执行"
- 信号量负责"跨线程通知结果，不轮询不忙等"
- 后台线程负责"替提交方等结果，让提交方继续干活"

缺任何一个，要么阻塞（不异步），要么错配（结果乱），要么碰撞（总线坏）。

------------------------------------------------------------
七、一句话总结
------------------------------------------------------------

队列把"多按钮并发提交"变成"写线程串行执行"（解决总线冲突）；
信号量让"执行完的结果"跨线程准确通知给"提交方"（解决结果回传）；
后台线程替"提交方"等结果，让提交方立即能接收下一条（解决非阻塞）。
三者缺一不可，组合成完整的异步通信链路。
