FrameGapLoop 检测逻辑理解纠偏
==============================

一、你的表述 vs 准确逻辑（先纠偏）

【你的表述】"1.83ms后检测一次，最后帧在3.65ms后有没有数据"
【判定】前半对，后半偏。拆开纠：

  "1.83ms后检测一次" —— ✓对。每 1.83ms（PollMs）查一次。
  "最后帧在3.65ms后有没有数据" —— ✗偏了两处：
    偏1："最后帧"不准。lastDataTicks 是"最后收数据的时刻"，不是"最后帧"。
         收的是字节流，可能半帧、一帧、多帧，lastDataTicks 只记"最后一次有字节进 buf 的时刻"。
    偏2："在3.65ms后有没有数据"像是"等3.65ms后看有没有新数据来"——方向反了。
         实际是"每1.83ms看一次：从最后收数据到现在已经静默多久了？静默≥3.65ms就判帧结束"。

【准确表述】"每1.83ms轮询一次：算距最后一次收字节过了多久（gap），gap≥3.65ms就判定这批数据收完了（帧结束）"

二、准确逻辑逐行（对照代码）

  long last = Interlocked.Read(ref lastDataTicks);   // 读"最后收字节的时刻"
  double gapMs = (now - last) * 1000.0 / Frequency;  // 算"从那以后静默了多久"
  if (gapMs >= FrameGapMs)                           // 静默≥3.65ms
      OnFrameGap();                                  // 判定帧结束，切帧+处理残帧

  核心是算"静默时长" = 当前时刻 - 最后收数据时刻。
  不是"等3.65ms后看有没有数据"，是"现在已经静默多久了？够3.65ms了吗？"

三、轮询 vs 事件驱动（你表述偏差的根源）

【你的表述像事件驱动】"3.65ms后检测有没有数据" —— 像在说"设个3.65ms定时器，到点看有没有新数据来"
【实际是轮询】"每1.83ms主动问一次：现在静默多久了" —— 不设定时器，不停问

  为什么用轮询不用事件驱动：
    事件驱动需要"3.65ms没数据"这个事件能被系统通知 —— 但系统没有这种通知！
    串口只在"有数据来"时触发 DataReceived，"没数据来"永远不触发任何事件。
    "静默"是"没有事件"，你没法等一个"没有事件"的事件。
    所以只能有人主动、持续地去问"距最后收数据过去多久了" —— 主动问=轮询=循环。

  这正是 FrameGapLoop 必须独立线程的原因（分析文档第七章）：
    "没来数据"这件事本身永远不会产生任何回调，只能主动轮询。

四、时序图（一帧收完到判帧结束）

  t=0      最后一字节进buf，OnData里 Interlocked.Exchange(ref lastDataTicks, t0)
  t=1.83   FrameGapLoop查：gap=1.83 < 3.65，不触发，PreciseSleepMs睡1.83ms
  t=3.66   FrameGapLoop查：gap=3.66 ≥ 3.65，触发OnFrameGap ✓
           → DrainInLock切完整帧 + 取残帧 → Handle解析

  关键：t=0 到 t=3.66 这3.66ms里，没有新数据来（静默），
  FrameGapLoop 每1.83ms查一次，第二次查就发现"静默已超3.65ms"→判帧结束。

  如果 t=2ms 时又来了新字节：
    OnData 更新 lastDataTicks=t2（重置静默计时）
    t=3.66 查：gap=3.66-2=1.66 < 3.65，不触发（因为又收了数据，不算静默）
    继续等，直到距 t2 静默3.65ms才判帧结束

五、1.83ms 和 3.65ms 的关系（采样定理）

  PollMs=1.83ms 是"查询间隔"——多久查一次
  FrameGapMs=3.65ms 是"判定阈值"——静默多久算帧结束

  为什么 PollMs = FrameGapMs/2：
    要可靠检测一个3.65ms的静默窗口，查询间隔必须≤窗口的一半=1.83ms
    → 保证静默窗口期间至少查一次，不会整个跳过去
    → 最坏检测延迟 = PollMs = 1.83ms（刚查完上一轮、静默刚开始，要等下轮才查到）

  两个值的关系：PollMs是"查多频繁"，FrameGapMs是"查什么条件"。
  不是"等3.65ms后查"，是"每1.83ms查一次3.65ms这个条件成不成立"。

六、完整数据流（修正你的表述）

  串口来字节 → OnData → buf.AddRange + Interlocked.Exchange(ref lastDataTicks, now)
  → FrameGapLoop 每1.83ms查一次：gap = now - lastDataTicks
  → 某次查到 gap ≥ 3.65ms（说明收完最后字节后已静默3.65ms没新数据）
  → OnFrameGap → DrainInLock切完整帧 + 取残帧 → Handle解析温湿度

  "3.65ms后有没有数据"这个理解要改成：
  "每1.83ms查一次：从最后收字节到现在静默了多久，静默≥3.65ms就判帧结束"

七、诚实补充（所有我知道的信息）

1. "静默判帧结束"是 Modbus RTU 规范的定界规则，不是本程序发明的。
   规范说：帧间静默 ≥ 3.5字符时间 = 帧边界。本程序按波特率动态算 3.5*10/BaudRate。
   TCP 版 Modbus 没有这条（TCP 是流式，靠长度字段定界）。

2. 为什么不"收够字节就判帧结束"而要靠静默：
   因为帧长要靠帧内字段算（byteCount），但有时帧头不全/功能码未知/拆包，
   FrameLength 算不出长度（return -1），这时只能靠静默兜底"该收的都收完了"。
   长度定界（帧内）+ 静默定界（帧间）= 双保险。

3. handled 变量的作用（你表述没提但代码有）：
   同一个 lastDataTicks 值只处理一次。OnFrameGap 处理完标记 handled=last，
   下轮查如果 last==handled 就跳过，避免同一批静默重复触发 OnFrameGap。
   直到 OnData 又来新字节更新 lastDataTicks，handled 才会被新值超过。

4. 你的表述"最后帧"可能把"最后收字节时刻"和"最后完整帧"搞混了。
   lastDataTicks 是字节级不是帧级——收半个帧也会更新 lastDataTicks。
   判的是"字节流静默了"，不是"某帧结束后静默了"。

八、记忆口诀

「每1.83ms轮询一次，算静默时长=现在-最后收字节时刻；
 静默≥3.65ms判帧结束，不是等3.65ms后看有没有数据；
 没数据来不触发任何事件，只能主动问=轮询=独立线程；
 PollMs是查多频繁，FrameGapMs是查什么条件，前者=后者/2保不漏判」
