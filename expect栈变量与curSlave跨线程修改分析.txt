一、用户问题
================================================================================
expect 这个是线程栈上的值，每个线程独立的，
会导致 expect 赋值后，SendLoop 改了这个值 curSlave。


二、结论：现象确实会发生，但不影响程序正确性
================================================================================
expect 是 Handle（接收线程）的局部变量，expect = curSlave 是一次性值拷贝。
赋值后 SendLoop（发送线程）改 curSlave，expect 不会跟着变（它是栈上的副本）。
这是事实，但分析表明：无论 expect 拿到旧值还是新值，都不会导致错误结果。


三、涉及的线程与变量
================================================================================

3.1 两个线程
--------------------------------------------------------------------------------
  ① SendLoop（发送线程）：写 curSlave（curSlave = id / curSlave = 0xFF）
  ② Handle（接收线程，由 OnData 回调触发）：读 curSlave（expect = curSlave）

3.2 变量性质
--------------------------------------------------------------------------------
  curSlave：static volatile byte
    - volatile：读取强制从主内存读最新值，写入立即刷主内存
    - 跨线程可见性保证：SendLoop 写后，Handle 读能看到最新值
  expect：byte（局部变量）
    - 在 Handle 方法的线程栈上
    - expect = curSlave 是一次性值拷贝，读完就赋值
    - 赋值后 curSlave 怎么变，expect 都不变（栈上的副本）


四、expect = curSlave 的原子性与可见性
================================================================================

4.1 这一行执行时
--------------------------------------------------------------------------------
  expect = curSlave;
  - curSlave 是 volatile，读时强制从主内存读
  - byte 是 8 位，在所有平台上原子读写
  - 所以 expect 拿到的是"某一时刻 curSlave 的真实值"
  - 要么是 SendLoop 改之前的旧值（如 1），要么是改之后的新值（如 0xFF 或 2）
  - 不会拿到"半改半没改"的中间态

4.2 这一行执行后
--------------------------------------------------------------------------------
  expect 已经是栈上的固定值，不再变化
  即使 SendLoop 此刻改了 curSlave，expect 不受影响
  这是用户描述的现象，确实如此


五、所有可能的时序场景分析
================================================================================

场景 1：正常应答（无超时、无迟到）
--------------------------------------------------------------------------------
  t=0   SendLoop: curSlave = 1（轮询从站1）
  t=0   SendLoop: sp.Write(从站1请求)
  t=20  从站1应答到达 → Handle
  t=20  Handle: expect = curSlave → 读到 1
  t=20  Handle: frame[0](1) == expect(1) → 校验通过 → Set frameReceived
  t=20  SendLoop: WaitOne 返回 true → 正常
  t=35  SendLoop: curSlave = 2（轮询从站2）
  分析：expect=1 是正确的，校验通过是对的，无问题

场景 2：超时后迟到应答（修复后，先 curSlave=0xFF 再 Reset）
--------------------------------------------------------------------------------
  t=0   SendLoop: curSlave = 1
  t=50  SendLoop: 超时
  t=50  SendLoop: curSlave = 0xFF    ← 先置无效
  t=50  SendLoop: frameReceived.Reset()
  t=51  从站1迟到应答到达 → Handle
  t=51  Handle: expect = curSlave → 读到 0xFF
  t=51  Handle: frame[0](1) != expect(0xFF) → 校验失败 → 忽略 → 不 Set
  分析：expect=0xFF，校验失败，不 Set，完全正确

场景 3：用户担心的——expect 拿到旧值，SendLoop 随后改 curSlave
--------------------------------------------------------------------------------
  t=0   SendLoop: curSlave = 1
  t=50  SendLoop: 超时
  t=50  SendLoop: curSlave = 0xFF
  t=50  SendLoop: frameReceived.Reset()
  t=50.1 Handle: expect = curSlave → 读到 0xFF（curSlave 已是 0xFF）
  t=50.2 SendLoop: 下一轮 curSlave = 2  ← SendLoop 改了 curSlave
  t=50.3 Handle: expect 还是 0xFF（栈上副本，不跟着变）
  t=50.4 Handle: frame[0](1) != expect(0xFF) → 校验失败 → 忽略 → 不 Set
  分析：expect=0xFF（旧值），curSlave 已变成 2，但 expect 不跟着变
        校验结果：frame[0](1) != 0xFF → 失败 → 不 Set → 正确（迟到应答被忽略）

场景 4：expect 拿到旧值 1，恰好校验通过
--------------------------------------------------------------------------------
  t=0   SendLoop: curSlave = 1
  t=50  SendLoop: 超时
  t=50  SendLoop: curSlave = 0xFF    ← 但 Handle 在此之前已读到 curSlave=1
  t=50  Handle: expect = curSlave → 读到 1（在 0xFF 写入之前）
  t=50  SendLoop: frameReceived.Reset()
  t=50  Handle: frame[0](1) == expect(1) → 校验通过 → Set frameReceived
  t=50  SendLoop: 下一轮 curSlave = 2
  t=50  SendLoop: WaitOne → ★ 灯被 Set 了（Handle 在 Reset 之后 Set 的）

  ★ 这个场景有问题！但问题不在 expect 缓存旧值，
    而在于"Handle 在 Reset 之后、curSlave=0xFF 之前读到了旧 curSlave"。
    这是上一轮已修复的问题：先 curSlave=0xFF 再 Reset，消除这个窗口。

  修复后的时序：
  t=50  SendLoop: curSlave = 0xFF    ← 先置无效
  t=50  Handle: expect = curSlave → 读到 0xFF（不可能读到 1 了）
  t=50  SendLoop: frameReceived.Reset()
  t=50  Handle: frame[0](1) != 0xFF → 校验失败 → 不 Set
  ★ 窗口消除，expect 不可能拿到旧值 1


六、核心论证：为什么 expect 拿到旧值不影响正确性
================================================================================

6.1 expect 拿到旧值的唯一场景
--------------------------------------------------------------------------------
  Handle 在 SendLoop 改 curSlave 之前执行 expect = curSlave。
  此时 expect = 旧值。
  但"旧值"是"当时 curSlave 的真实值"（volatile 保证），不是缓存假值。

6.2 expect 拿到旧值后，校验结果两种情况
--------------------------------------------------------------------------------
  情况 A：frame[0] == 旧值 → 校验通过 → Set
    - 这说明应答的从站号 == 当时的期望从站号 → 是正确的应答
    - Set 是对的（这个应答确实是给当时正在等的请求的）
    - 如果 SendLoop 已超时（在等 Reset），Set 后 Reset 会关灯（修复后顺序：先0xFF再Reset，
      0xFF 后 Handle 读到 0xFF 不会 Set，所以这种情况在超时分支不会发生）
    - 如果 SendLoop 还在 WaitOne（没超时），Set 正好让 WaitOne 返回 true → 正常成功

  情况 B：frame[0] != 旧值 → 校验失败 → 忽略 → 不 Set
    - 应答的从站号 != 当时的期望从站号 → 是迟到/错配的应答
    - 忽略是对的 → 无影响

6.3 关键：expect 拿到的"旧值"是"当时的真实期望"
--------------------------------------------------------------------------------
  expect = curSlave 读到的不是"过期的错误值"，而是"读取那一刻 curSlave 的真实值"。
  volatile 保证这一点。
  这个值就是"当时 SendLoop 正在等的从站号"。
  用它校验应答，逻辑上是正确的——应答的从站号应该等于当时正在等的从站号。

  SendLoop 之后改了 curSlave（轮下一个从站），那是"未来的期望"，
  Handle 用"当时的期望"校验"当时的应答"，是对的。
  如果用"未来的期望"校验"当时的应答"，反而会错（张冠李戴）。


七、反证：如果 expect 跟着 curSlave 变会怎样
================================================================================
  假设 expect 不是局部变量，而是 curSlave 的引用（跟着变）：
  t=0   SendLoop: curSlave = 1
  t=20  从站1应答到达 → Handle
  t=20  Handle: expect = curSlave → 1
  t=20  Handle: 正在校验 frame[0](1) == expect(1)
  t=20  SendLoop: WaitOne 返回 true，curSlave = 2（轮下一个）
  t=20  Handle: expect 跟着变成 2（假设跟着变）
  t=20  Handle: frame[0](1) != expect(2) → 校验失败 → 忽略！
  ★ 从站1的正确应答被误判为迟到应答！错误！

  所以 expect 必须是局部变量（不跟着变），才能正确校验"当时的应答"。
  这是局部变量的优势，不是缺陷。


八、总结
================================================================================
用户描述的现象确实存在：expect 是 Handle 线程栈上的局部变量，
expect = curSlave 赋值后，SendLoop 改 curSlave，expect 不会跟着变。

但这是正确的设计，不是 bug：
  1. expect 拿到的是"读取那一刻 curSlave 的真实值"（volatile 保证，不是缓存假值）
  2. 这个值就是"当时正在等的从站号"，用它校验"当时的应答"是正确的
  3. 如果 expect 跟着 curSlave 变，反而会错（正确应答被误判为迟到）
  4. 修复后（先 curSlave=0xFF 再 Reset），超时分支的竞态窗口已消除，
     expect 不可能拿到"已失效的旧期望值"

局部变量 expect 的"不跟着变"特性，正是跨线程校验正确性的保障。
