gap≥3.65ms 判帧结束能否保证收完？粘帧拆帧场景详析
====================================================

一、核心一段（先直接回答）
不能 100% 保证。3.65ms 静默是 Modbus 规范的"最佳努力"定界信号，正常从站下可靠（帧内字符间隔 1.04ms < 3.65ms < 帧间静默），但异常情况下会误判：拆包+中间静默>3.65ms（异常从站/总线干扰/调度抖动）时，FrameGapLoop 会在前段就触发 OnFrameGap，前段当残帧丢，整帧因静默拆开而丢失。粘帧（两帧紧挨着、中间静默<3.65ms）不靠静默判，靠 Drain 的 FrameLength 长度字段切。所以"3.65ms判帧结束"是"正常情况够用、异常情况会丢"的兜底机制，不是数学上100%保证。

二、3.65ms 静默为什么"正常情况下可靠"

【Modbus RTU 规范的定界规则】
  帧内：字符间隔 1.04ms（9600，1字符=10位/9600=1.04ms）< 3.65ms → 继续攒帧
  帧间：从站发完一帧会停，静默 ≥ 3.5字符时间 = 3.65ms → 判帧边界

【正常从站的时序保证】
  从站发一帧8字节：字节间隔 1.04ms（连续发，不停顿）
  发完后从站闭嘴：静默 ≥ 3.65ms（规范要求，从站发完要静默至少3.5字符）
  → FrameGapLoop 查到静默≥3.65ms = 这帧发完了 ✓

【3.65ms 的双重角色】
  定界：静默≥3.65ms = 帧边界（帧间分隔）
  容忍：帧内字符间隔 1.04ms < 3.65ms，不会误判帧结束（允许攒帧）
  1.04ms~3.65ms 模糊区：< 3.65ms 都算帧内继续攒

三、粘帧场景（一次收多帧）——不靠静默判，靠长度切

【场景】两帧紧挨着来，中间静默 < 3.65ms
  buf 里：[帧1完整][帧2完整] 粘在一起
  FrameGapLoop：中间静默<3.65ms，不触发OnFrameGap
  → 靠谁切：Drain 的 while 循环 + FrameLength 长度字段
    1.FrameLength算帧1长度=3+byteCount+2
    2.切走帧1，buf剩帧2
    3.while回顶，FrameLength算帧2长度，切走帧2
  → 静默没参与，长度字段切的

【粘帧靠静默会怎样】如果只靠静默不靠长度：
  两帧中间静默<3.65ms → FrameGapLoop不触发 → 永远不判帧结束 → 数据堆buf里不处理
  所以必须有Drain的长度切帧，静默是兜底不是主力。

【粘帧的风险】两帧中间静默<3.65ms 且帧1 CRC错：
  Drain滑动1字节对齐 → 可能搅乱帧1和帧2的边界 → 帧2也切错
  这是长度定界的固有风险，静默定界救不了（静默没触发）。

四、拆帧场景（一帧分多次收）——靠buf攒+等够长度

【场景】5字节应答先来3再来2，中间间隔 1.04ms（正常）
  t=0     来3字节，buf=[3字节]，Drain: FrameLength说要5字节不够，return等更多
  t=1.04  来2字节，buf=[5字节]，Drain: 够5字节，切走 ✓
  FrameGapLoop：中间间隔1.04ms < 3.65ms，不触发OnFrameGap（正确，没误判帧结束）

【拆帧靠静默会怎样】如果中间间隔>3.65ms（异常）：
  t=0      来3字节，buf=[3字节]
  t=3.65   FrameGapLoop查：gap=3.65≥3.65，触发OnFrameGap
           → DrainInLock切完整帧（buf只有3字节不够5，切不动）
           → 取残帧rest=[3字节]，buf.Clear()
           → Handle([3字节])：帧太短丢弃 ✗
  t=5      来2字节，buf=[2字节]（前3字节已被清掉！）
           → 这2字节永远凑不成完整帧，最终也当残帧丢
  → 整帧因中间静默>3.65ms被拆成两段，前段当残帧丢，后段也丢，整帧丢失 ✗

【这就是"不能100%保证"的根因】
  正常从站帧内间隔1.04ms < 3.65ms，不会触发 → 可靠
  异常从站/总线干扰/调度抖动导致帧内静默>3.65ms → 误判帧结束 → 丢帧

五、各种场景汇总表

场景              | 静默特征           | 谁定界      | 结果
------------------|-------------------|------------|------------------
正常单帧          | 帧内1.04<3.65<帧间 | 静默+长度   | ✓正确
粘帧(两帧紧挨)    | 中间<3.65ms        | 长度字段    | ✓正确(静默没参与)
拆帧(帧内1.04ms)  | 帧内1.04<3.65      | buf攒+长度  | ✓正确(静默没误判)
拆帧+异常静默     | 帧内>3.65ms        | 静默误判    | ✗丢帧(前段当残帧丢)
从站不守规范      | 帧间<3.65ms        | 长度字段    | ✓正确(静默没触发但长度切)
CRC错的粘帧       | 中间<3.65ms        | 长度滑动    | ✗可能搅乱边界

六、为什么不能100%保证（本质）

【变长+静默定界的固有矛盾】
  Modbus RTU 帧没有起始符（不像 HDLC 的 0x7E），靠静默定界。
  静默是"时间信号"，长度是"空间信号"。
  时间信号受物理层抖动影响（总线干扰/调度延迟/从站异常），
  一旦帧内出现>3.65ms的异常静默，时间信号就误报"帧结束"。
  这是变长+静默定界协议的固有风险，无法在协议层消除。

【能做什么不能做什么】
  能：正常情况下可靠定界（从站守规范、总线干净）
  能：长度字段做第二保险（Drain切帧不靠静默）
  能：CRC校验兜底（切错了CRC不过会丢，不会解析错数据）
  不能：防止异常静默导致的误判（物理层问题协议层管不了）
  不能：保证拆开的帧能重组（代码没做跨静默的帧拼接）

七、本代码的双重保险机制

  保险1·长度定界（帧内）：Drain 的 FrameLength 算长度，够才切，不够等
    → 处理粘帧（多帧粘一起按长度切）
    → 处理拆帧（不够长度return等更多）

  保险2·静默定界（帧间）：FrameGapLoop 判静默≥3.65ms
    → 处理"长度判不出但静默说帧结束"的残帧
    → 比如帧头不全/功能码未知/拆包残留

  CRC校验：切出来的帧CRC不过就丢/滑动，不会解析错数据
    → 兜底"切错了"的情况，保证不输出错误温湿度

  三层兜底：长度切 → 切不动的静默兜 → 切出来的CRC验
  但都兜不住"帧内异常静默>3.65ms"——这是物理层问题。

八、诚实补充（所有我知道的信息）

1. "3.65ms判帧结束"是 Modbus 规范的规定，不是本程序发明的。
   规范说"超过3.5字符时间的静默=帧边界"，本程序照做。
   规范假设从站守规矩（帧内不静默>3.5字符），不守规矩规范也救不了。

2. 115200bps 下更脆弱：FrameGapMs=0.304ms，帧内一个抖动就超。
   高波特率对总线质量和求更高，9600下3.65ms容错大得多。

3. 工业实践里怎么应对"异常静默丢帧"：
   - 从站重发：主站超时不回，从站（如果支持）会重发同一帧
   - 主站重询：本程序轮询循环，下一轮会再问同一从站，丢一帧不影响（温湿度采样冗余）
   - 所以"偶丢一帧"在轮询系统里可容忍，不是致命问题

4. 如果要"100%不丢"，得改协议：加帧起始符+长度字段+序号（像自定义协议），
   或者用 Modbus TCP（靠长度字段定界，不靠静默）。
   Modbus RTU 选静默定界是为了简单（不用起始符转义），代价是异常静默会误判。

5. 本代码 OnFrameGap 的残帧处理（Handle(rest)）是"再试解析"：
   残帧可能是完整帧（FrameLength判不出但静默说完了），Handle再CRC校验一次。
   过了就解析（救回一帧），不过就丢（和直接丢效果一样）。
   这是对"静默定界可能误判"的补偿，但不能补偿"拆开丢前段"的情况。

6. 你问"一定能判断收完了"——诚实说：正常情况能，异常情况不能。
   工程上没有"一定"，只有"在假设条件下可靠"。
   本程序的假设：从站守Modbus规范、总线无干扰、调度抖动<3.65ms。
   违反假设就丢帧，靠轮询冗余容忍。

九、记忆口诀

「3.65ms静默是最佳努力不是保证，正常从站可靠异常会丢；
 粘帧不靠静默靠长度切，拆帧靠buf攒等够长度；
 拆帧+异常静默>3.65ms是唯一漏洞，前段当残帧丢整帧丢失；
 长度定界+静默定界+CRC校验三层兜底，但兜不住物理层异常静默；
 偶丢一帧靠轮询冗余容忍，要100%不丢得换协议」
