【用户问题原文】
  "SendLoop, FrameGapLoop, WriteLoop, CmdLoop, OnData 这些在不同线程上运行的方法，
   怎么保证不出错，以及怎么知道运行的时候没有出现错误"

【0. 问题拆解】
================================================================================

  这是两个独立但相关的问题：
    Q1（正确性证明）：怎么保证不出错？  → 靠同步机制设计
    Q2（可观测性）：    怎么知道没出错？ → 靠日志/超时/异常捕获/结果反馈

  分别详细回答。

================================================================================
【Q1. 怎么保证不出错 —— 同步机制全景】
================================================================================

  5 个方法的线程归属和共享状态：

  方法          运行线程              触发方式
  ─────────────────────────────────────────────────────
  SendLoop      显式 Thread           while 循环（交互模式被注释，不启动）
  FrameGapLoop  显式 Thread           while 循环 + PreciseSleepMs
  WriteLoop     显式 Thread           while 循环 + TryDequeue
  CmdLoop       显式 Thread           Console.ReadLine 阻塞
  OnData        串口回调线程（底层）   SerialPort.DataReceived 事件触发
  Handle        在 OnData/FrameGapLoop 的线程上调用（非独立线程）

  共享状态与保护方式一览：
  共享状态          写者                读者                保护
  ─────────────────────────────────────────────────────────────────
  buf              OnData/FrameGap/    OnData/FrameGap/    lock(gate)
                   SendLoop/WriteLoop  SendLoop/WriteLoop
  sp(串口)         所有                所有                lock(io)
  running          Main/CmdLoop        所有                volatile
  activeWrite      WriteLoop           OnData→Handle       volatile + 时序
  curSlave         SendLoop            OnData→Handle       volatile
  lastDataTicks    OnData              FrameGapLoop        Interlocked
  writeQueue       CmdLoop/参数模式    WriteLoop           ConcurrentQueue(自带线程安全)
  frameReceived    Handle              SendLoop            AutoResetEvent(自带线程安全)
  wr.Ack           Handle              ExecuteWrite        AutoResetEvent(自带线程安全)
  wr.Completed     WriteLoop           WriteSingleCoil     ManualResetEventSlim(自带线程安全)

  ───────────────────────────────────────────────────────────────────
  保护机制分 4 类，逐一说明：
  ───────────────────────────────────────────────────────────────────

  【保护1：lock 互斥】—— 保护 buf 和 sp
    lock(gate) 保护 buf：
      OnData 第217行、FrameGapLoop→OnFrameGap 第257行、Drain 第336行、
      SendLoop 第191行、ExecuteWrite 第542行，所有 buf 读写都在 lock(gate) 内。
      → 不会两个线程同时改 buf 导致 List 内部状态损坏。

    lock(io) 保护 sp：
      所有 sp.Write / sp.Read / sp.DiscardInBuffer / sp.Close 都在 lock(io) 内。
      → 不会发送和读取同时操作串口驱动导致状态错乱。

  【保护2：锁顺序一致】—— 防死锁
    约定：需要同时持两把锁时，永远 io → gate 顺序。
    OnData:        lock(io)读串口 → lock(gate)操作buf   ✓
    SendLoop超时:  lock(io)Discard → lock(gate)Clear    ✓
    ExecuteWrite:  lock(io)Discard → lock(gate)Clear    ✓
    → 所有双锁路径顺序一致，不会 A 等 B、B 等 A 死锁。

  【保护3：volatile / Interlocked】—— 轻量可见性
    running / activeWrite / curSlave 用 volatile：
      保证一个线程的赋值对其他线程立即可见，不被 CPU 缓存隐藏。
    lastDataTicks 用 Interlocked.Read/Exchange：
      64位 long 在 32位机器上读写非原子，必须用 Interlocked。

  【保护4：线程安全容器 + 信号量】—— 自带同步
    writeQueue 是 ConcurrentQueue：Enqueue/TryDequeue 自带锁，多线程并发安全。
    frameReceived / wr.Ack / wr.Completed 是 Event 原语：Set/WaitOne/Reset 自带锁。

  ───────────────────────────────────────────────────────────────────
  关键不变式（invariants，正确性的数学保证）：
  ───────────────────────────────────────────────────────────────────

  不变式1：同一时刻只有一个 ExecuteWrite 在运行
    保证：WriteLoop 是单线程，while 循环同步调 ExecuteWrite，等它返回才下一轮。
    推论：activeWrite 不会被并发覆盖，Handle 读到的就是当前唯一活跃请求。

  不变式2：activeWrite = wr 发生在 sp.Write 之前
    保证：ExecuteWrite 第546行赋值，第555行发送，顺序固定。
    推论：接收线程收到回显时，activeWrite 已就位。

  不变式3：buf 的所有修改都在 lock(gate) 内
    保证：grep 验证所有 buf.Add/Clear/RemoveRange/ToArray 都在 lock 内。
    推论：buf 不会因并发修改导致 List 内部数组撕裂。

  不变式4：sp 的所有 IO 都在 lock(io) 内
    保证：grep 验证所有 sp.Write/Read/DiscardInBuffer/Close 都在 lock 内。
    推论：串口驱动状态不会因并发调用而错乱。

  不变式5：每个 WriteRequest 的 Ack/Completed 是实例字段，对象间互不干扰
    保证：Ack/Completed 非 static，每 new 一个对象新建一盏灯。
    推论：多请求并发等结果不会串扰。

  ★ 这 5 个不变式都成立 → 程序"不出错"（在单次执行层面）。

【Q1 补充：哪些地方"不出错"是靠时序隐式保证，不够严谨】
================================================================================

  诚实指出 3 处隐式依赖：

  隐式1：activeWrite 内部字段的可见性
    volatile 只保证引用可见，不保证 wr.Slave/wr.Frame/wr.AckOk 字段可见。
    实际靠"wr 入队前已构造完成 + sp.Write 系统调用刷屏障"保证。
    严谨做法：activeWrite=wr 前加 Thread.MemoryBarrier()。

  隐式2：AckOk 的读写无锁
    Handle 第409行写 aw.AckOk=true，ExecuteWrite 第571行读 wr.AckOk。
    无 volatile 无锁。实际靠 Ack.Set/WaitOne 的内存屏障保证可见。
    严谨做法：AckOk 加 volatile 或用 Interlocked。

  隐式3：ExecuteWrite 返回后 activeWrite 未置 null
    下一个写请求来之前，迟到回显会拿旧 wr 比对。整帧比对会拒绝，不会误判，
    但多一次无效处理。非 bug，不够干净。

  ★ 这些隐式依赖在 x86/x64 强内存模型下实际不会出问题，但在 ARM 弱内存模型下有风险。
    本程序运行在 Windows x86/x64，实际安全。

【Q2. 怎么知道运行时没出错 —— 可观测性机制】
================================================================================

  程序通过 5 类机制让运行时错误"可见"：

  【机制1：超时检测】—— 最主要的"知道出错"方式
    SendLoop 第184行：frameReceived.WaitOne(TimeoutMs=50ms)
      超时 → 打印 "[超时] 从站XX 50ms 没应答" → 清状态轮下一个
    ExecuteWrite 第569行：wr.Ack.WaitOne(TimeoutMs=50ms)
      超时 → 打印 "[写超时·从站XX] 第X次 50ms 没回显" → 重试
    WriteSingleCoil 第502行：wr.Completed.Wait(waitMs)
      超时 → 打印 "[写失败·从站XX] 排队执行超时"

    ★ 超时是 RS485 通信最主要的错误信号（从站掉线/总线断开/噪声干扰），
      程序靠超时兜底，不会无限等待。

  【机制2：CRC 校验】—— 数据完整性
    Handle 第351-357行：每帧都校验 CRC
      CRC 错 → 打印 "[CRC错误] 算出 0xXXXX，收到 0xXXXX，丢弃"
    DrainInLock 第319-328行：切帧时校验 CRC
      CRC 错 → 打印 "[对齐] CRC失败，滑动1字节重新对齐"

  【机制3：异常响应解析】—— 从站报告的错误
    Handle 第373-385行：func & 0x80 != 0 是异常响应
      打印 "[异常响应·从站XX] 功能码 0xXX，异常码 0xXX"
      写异常 → 触发重试；读异常 → 跳过该从站

  【机制4：从站身份校验】—— 防错配
    Handle 第365-370行：应答帧第1字节 vs expect
      不匹配 → 打印 "[忽略] 从站 XX 的迟到应答（当前在等从站 XX）"
    0x05 整帧比对 第398-405行：回显帧 vs 发送帧
      不一致 → 打印 "[忽略·0x05] 回显帧与当前请求不一致"

  【机制5：异常捕获】—— CLR/系统级错误
    ExecuteWrite 第558行：try-catch 包 sp.Write
      发送异常 → 打印 "[写异常·从站XX] 第X次 发送失败：{ex.Message}" → 重试
    Main 第123行：参数模式 try-catch
      打印 "[参数模式] 执行异常：{ex.Message}"
    ParseAndSubmit 第657行：同步命令 try-catch
      打印 "[命令] 执行异常：{ex.Message}"

  ───────────────────────────────────────────────────────────────────
  运行时你能看到的错误提示汇总（按严重度）：
  ───────────────────────────────────────────────────────────────────

  提示                                          含义                  处理
  ──────────────────────────────────────────────────────────────────
  [超时] 从站XX 50ms 没应答                     从站没响应            清状态轮下一个
  [写超时·从站XX] 第X次 50ms 没回显             写命令没回显          重试
  [写异常·从站XX] 第X次 发送失败：...           串口发送异常          重试
  [写异常·从站XX] 从站返回异常响应              从站回异常码          重试
  [写失败·从站XX] 重试3次仍未成功               重试耗尽              返回失败
  [写失败·从站XX] 排队执行超时                  队列拥堵              返回失败
  [CRC错误] 算出 0xXXXX，收到 0xXXXX            帧数据损坏           丢弃该帧
  [对齐] CRC失败，滑动1字节重新对齐             帧错位               滑动重新对齐
  [异常响应·从站XX] 功能码 0xXX，异常码 0xXX    从站报告错误         重试或跳过
  [忽略] 从站 XX 的迟到应答                     旧应答错配           丢弃
  [忽略·0x05] 回显帧与当前请求不一致           旧写应答错配         丢弃
  [错误] 帧太短，丢弃                           帧长度异常           丢弃
  [提示] 非预期的帧                             未知功能码           忽略

  ★ 如果程序运行时没有出现以上任何提示，且温湿度/写命令结果正常打印，
    则"认为"没出错。但这是经验判断，不是数学证明。

【Q2 补充：现有可观测性的缺口（诚实指出）】
================================================================================

  缺口1：后台线程顶层未 try-catch
    SendLoop/FrameGapLoop/WriteLoop/CmdLoop 的 while 循环外层没有 try-catch。
    若抛出未预期异常（如 NullReferenceException），该线程静默退出，
    主线程不知道，程序"半死不活"——running 还是 true，但某个功能已停。
    ★ 这是最严重的可观测性缺口。
    建议：每个线程 while 外包 try-catch，打印 "[线程XX崩溃] {ex}" 并设 running=false。

  缺口2：sp.Open() 未 try-catch
    COM4 不存在/被占用 → 抛 IOException → Main 直接崩溃，无友好提示。
    建议：try-catch 打印 "串口打开失败，请检查 COM4 是否存在/被占用"。

  缺口3：OnData 内部异常未捕获
    若 sp.BytesToRead 或 sp.Read 抛异常（如串口突然拔掉），OnData 直接崩，
    DataReceived 事件回调异常会被 SerialPort 吞掉或终止回调线程。
    建议：OnData 顶层 try-catch。

  缺口4：Handle 内部异常未捕获
    若 frame 数组越界（理论上 FrameLength 保证不会，但防御性编程角度），
    Handle 抛异常 → OnData 的 foreach 中断 → 后续帧不处理。
    建议：Handle 顶层 try-catch，单帧异常不影响其他帧。

  缺口5：没有"心跳"日志
    长时间运行时，如果从站全部掉线，程序只是不断打印超时，没有"我已经多久没收到
    任何有效数据了"的汇总告警。运维不易察觉。
    建议：定期打印统计（X秒内成功Y次，超时Z次）。

  缺口6：Verbose=false 时信息很少
    正常运行只有温湿度结果和写命令结果，看不到帧收发细节。
    出问题时开 Verbose=true 才能看到 [发送]/[收到帧]/[解析] 等，需要改代码重编译。
    建议：运行时动态开关（如输入 "verbose on" 切换）。

【Q2 终极问题：怎么"证明"运行时没出错？】
================================================================================

  诚实说：单靠日志只能"发现"错误，不能"证明"无错误。要真正证明，需要：

  方法1：单元测试/集成测试
    - 用串口模拟器（如 com0com 虚拟串口对）+ Modbus 从站模拟器
    - 注入各种异常：超时、CRC 错、错位、异常响应、并发写
    - 验证程序行为符合预期
    - 本程序没有测试代码，这是最大的正确性保障缺口。

  方法2：代码审查/形式化验证
    - 人工证明不变式（本文 Q1 做的工作）
    - 用工具如 Pex/Randoop 自动探索并发场景

  方法3：运行时监控
    - 统计成功率/超时率/CRC错误率
    - 设阈值告警（如超时率 > 10% 报警）
    - 本程序有统计潜力（超时/重试都有打印），但没有汇总

  方法4：压力测试
    - 长时间运行（24小时+）观察内存/线程/CPU/句柄泄漏
    - 高频率写命令压队列
    - 拔插串口/从站掉线恢复

  ★ 现实结论：本程序靠"协议层校验（CRC/帧长/从站号）+ 超时兜底 + 异常捕获"
    能发现大部分通信错误；但靠"线程顶层未 try-catch"是可观测性的硬伤，
    线程静默退出时无法察觉。这是最该补的地方。

【总结】
================================================================================

  Q1 怎么保证不出错：
    靠 4 类同步机制（lock/volatile/Interlocked/线程安全容器+信号量）
    + 5 个不变式（串行执行/先赋值后发送/buf锁/sp锁/对象隔离信号）
    + 一致的锁顺序（io→gate 防死锁）
    隐式依赖 3 处（字段可见性/AckOk无锁/activeWrite未清），x86/x64 下实际安全。

  Q2 怎么知道没出错：
    靠 5 类可观测机制（超时/CRC/异常响应/从站校验/异常捕获）
    运行时看 12 类错误提示，没有提示且结果正常 → 经验上认为没出错
    缺口：后台线程顶层未 try-catch（最严重）、sp.Open未捕获、无心跳汇总、无测试

  一句话：正确性靠设计保证，可观测性靠日志保证；
           设计基本严谨但有隐式依赖，日志基本够用但有线程崩溃盲区。
