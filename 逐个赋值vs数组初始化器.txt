为什么用 req[0]=(byte)(tid>>8) 逐个赋值而非 byte[] req={...} 初始化器
==============================================================

一、核心一段（先直接回答）
两种都能用，选逐个赋值是因为 tid 是 ushort 变量要拆成高字节+低字节，逐个赋值能清晰对应 MBAP 头每个字段并加注释；数组初始化器把 12 个元素挤一行，混合变量表达式和常量，可读性差。RTU 版用 `byte[] req = { id, 0x03, ... }` 是因为 RTU 帧里 id 直接就是 byte 不用拆；TCP 的 MBAP 头里 tid 是 ushort 要拆 2 字节，且 12 个字段逐个赋值更易读。本质是"字段多+有变量拆分时逐个赋值清晰，字段少+全是常量时初始化器简洁"的风格选择，不是技术限制。

二、两种写法对比

【当前写法：逐个赋值】
  byte[] req = new byte[12];
  req[0] = (byte)(tid >> 8);      // TID高字节
  req[1] = (byte)(tid & 0xFF);    // TID低字节
  req[2] = 0; req[3] = 0;         // Protocol ID
  req[4] = 0; req[5] = 6;         // Length
  req[6] = unitId;                // Unit ID
  req[7] = func;                  // Function Code
  req[8] = (byte)(start >> 8);    // 起始地址高
  req[9] = (byte)(start & 0xFF);  // 起始地址低
  req[10] = (byte)(count >> 8);   // 寄存器数高
  req[11] = (byte)(count & 0xFF); // 寄存器数低

【数组初始化器写法（也能用）】
  byte[] req = {
      (byte)(tid >> 8), (byte)(tid & 0xFF),   // TID
      0, 0,                                    // Protocol
      0, 6,                                    // Length
      unitId, func,                            // UnitID + FC
      (byte)(start >> 8), (byte)(start & 0xFF),// 起始地址
      (byte)(count >> 8), (byte)(count & 0xFF) // 寄存器数
  };

【RTU 版的写法（Program.cs）】
  byte[] req = { id, 0x03, 0x00, 0x00, (byte)(RegCount >> 8), (byte)(RegCount & 0xFF) };
  → 6个元素，id 是 byte 不用拆，简洁

三、为什么 TCP 版不用初始化器（4个原因）

【原因1：tid 是 ushort 要拆成 2 字节】
  RTU 的 id 是 byte，直接放数组：{ id, 0x03, ... }
  TCP 的 tid 是 ushort（2字节），要拆高字节+低字节放两个位置：
    (byte)(tid >> 8)   = 高字节
    (byte)(tid & 0xFF) = 低字节
  初始化器里要写 (byte)(tid >> 8), (byte)(tid & 0xFF) 两个表达式，
  不如逐个赋值配注释清晰。

【原因2：12个字段太多，挤一行可读性差】
  RTU 帧 6 字节，初始化器一行搞定，简洁。
  TCP MBAP 12 字节，初始化器一行太长，折行后跟逐个赋值差不多长，
  但逐个赋值每行能加注释说明字段含义。

【原因3：混合变量表达式和常量，初始化器不直观】
  初始化器：{ (byte)(tid>>8), (byte)(tid&0xFF), 0, 0, 0, 6, unitId, func, ... }
  → 变量表达式和常量交替，眼睛要跳着看
  逐个赋值：req[0]=...; req[1]=...; 每行一个，注释对齐
  → 字段含义一目了然

【原因4：逐个赋值能对齐 MBAP 头文档】
  MBAP 头规范：偏移0=TID高, 偏移1=TID低, 偏移2=Proto高...
  req[0]=TID高, req[1]=TID低, req[2]=Proto高...
  → 索引和偏移一一对应，看代码就能对照协议文档
  初始化器没有索引，要数逗号定位

四、>> 8 和 & 0xFF 是什么意思（拆字节原理）

【ushort 拆成两个 byte】
  tid 是 ushort = 16位 = 2字节
  高字节 = (byte)(tid >> 8)   = 右移8位 = 取高8位
  低字节 = (byte)(tid & 0xFF) = 与0xFF = 取低8位

  举例 tid = 0x1234：
    tid >> 8    = 0x12（高字节）
    tid & 0xFF  = 0x34（低字节）
    → req[0]=0x12, req[1]=0x34 → 大端序（高字节先）

【为什么是大端序】
  Modbus TCP 的 MBAP 头用大端序（Big-Endian，高字节先）。
  网络协议通用大端序（叫"网络字节序"）。
  C# 的整数是小端序（x86），所以要手动拆成大端放数组。

【RTU 版为什么不用拆】
  RTU 帧的从站地址 id 是 byte（1字节），不用拆。
  RTU 的寄存器数 RegCount 是 int 但也只取低字节：
    (byte)(RegCount >> 8), (byte)(RegCount & 0xFF)
  RTU 版也用了拆字节，只是帧短所以初始化器够简洁。

五、两种写法什么时候用哪个

场景                          | 推荐写法        | 原因
------------------------------|----------------|------------------
字段少+全是常量/byte变量       | 初始化器 {}     | 简洁，一行搞定
字段多+有ushort/int要拆字节    | 逐个赋值 req[i]=| 清晰，能加注释
字段多+全是常量               | 初始化器折行    | 还行，但注释难加
需要按偏移对照协议文档         | 逐个赋值        | 索引=偏移，对照方便

RTU 版6字节用初始化器，TCP 版12字节用逐个赋值——都是合理选择。

六、诚实补充（所有我知道的信息）

1. 数组初始化器 `byte[] req = { ... }` 里可以用变量表达式，不是只能用常量。
   `byte[] req = { id, 0x03, (byte)(RegCount >> 8) }` 是合法的（id是变量）。
   所以 TCP 版用初始化器技术上也行，只是可读性差。

2. 逐个赋值 vs 初始化器编译结果一样：
   初始化器 `new byte[]{1,2,3}` 编译成 newarr + 每个元素赋值。
   逐个赋值 `new byte[3]; req[0]=1;` 也是 newarr + 赋值。
   性能完全相同，纯风格选择。

3. 还有第三种写法：BitConverter.GetBytes(ushort)
   byte[] tidBytes = BitConverter.GetBytes(tid); // 返回2字节小端
   但 Modbus 要大端，GetBytes 是小端，要 Array.Reverse 或手动交换——更绕。
   所以直接 (tid>>8) 和 (tid&0xFF) 手动拆大端最直接。

4. C# 的 BinaryPrimitives.WriteUInt16BigEndian 是更现代的写法：
   BinaryPrimitives.WriteUInt16BigEndian(req.AsSpan(0), tid);
   一行写一个 ushort 的大端，不用手动拆。但要对 Span 有了解，本程序用手动拆更直观易懂。

5. RTU 版 Program.cs 的 `byte[] req = { id, 0x03, 0x00, 0x00, ... }` 能用初始化器
   是因为 id 是 byte（从站地址1字节），直接放不用拆。
   如果 RTU 也有 TID（没有，RTU 无事务标识），也要拆字节，可能也用逐个赋值。

七、记忆口诀

「byte变量直接放初始化器，ushort要拆高低字节逐个赋值清晰；
 字段少用{}简洁，字段多用req[i]=能注释对照偏移；
 >>8取高字节 &0xFF取低字节，大端序高字节先（网络字节序）；
 两种编译结果一样性能相同，纯可读性风格选择」
