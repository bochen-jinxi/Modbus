Modbus RTU 多从站轮询程序 - 运行流程与线程协调分析
=====================================================

一、核心流程（一段总览）
程序是 C# Modbus RTU 主站，COM4 @9600bps，轮询两个从站(0x01、0x02)，用功能码03读保持寄存器取温湿度。生命周期四步：Main 打开串口清残留、启两个后台线程（发送 tx、帧超时检测 fx）后主线程 Sleep 等 Ctrl+C；发送线程 SendLoop 构造 8 字节请求帧(地址+03+起始+数量+CRC16)、记 curSlave、lock(io) 写串口、frameReceived.WaitOne(50ms) 等应答，超时就 DiscardInBuffer+清 buf+Reset 信号防错位累积；串口来数据触发 OnData（线程池回调）：lock(io) 读出、lock(gate) 追加 buf、Interlocked 记最后接收时刻、Drain 尝试切帧；帧超时检测线程 FrameGapLoop 用 Stopwatch 微秒级轮询，距最后一次收数据 >= 3.5 字符时间(9600 下 3.65ms)就调 OnFrameGap 把残余 buf 当残帧处理。切帧按 FrameLength 动态算长（03/04 应答=3+字节数+2；异常帧=5），CRC 失败滑动 1 字节重对齐，curSlave 过滤迟到应答，最后 frameReceived.Set() 唤醒发送线程发下一帧。

二、发现的两个问题（BUG，先列问题）

【BUG1·致命】Program.cs:189 —— Thread.Sleep(50000) 写在 lock(gate) 内！
  OnFrameGap 一旦执行，持锁 50 秒：期间 OnData 无法入 buf、Drain 无法取帧、
  发送线程超时分支也清不了 buf，整机卡死 50 秒。应移到锁外或删除。

【BUG2·隐蔽】Program.cs:166 —— 帧间隔计算是整数除法：
  gapMs = ((sw.ElapsedTicks - last) / Stopwatch.Frequency) * 1000.0
  先 long 除法（结果几乎总是 0）再乘 1000.0 → gapMs 永远约等于 0
  → FrameGapLoop 永远不触发。应改为：
  gapMs = (sw.ElapsedTicks - last) * 1000.0 / Stopwatch.Frequency（先乘后除）

  后果链：BUG2 让 BUG1 永远不触发（歪打正着掩盖了持锁 50 秒），
  但"3.5 字符判帧结束"完全失效，只能靠 OnData 里 Drain 实时切帧；
  不够一帧的残帧会永久滞留 buf，等下一次 OnData 才有机会被切。

三、线程协调（4 个执行流）
1. Main 线程          ：只启动和退出(running=false)，不碰共享数据。
2. SendLoop 发送线程  ：写串口、写 curSlave、等 frameReceived；超时分支按 io->gate 顺序拿两把锁清状态。
3. OnData 串口事件线程：SerialPort.DataReceived 在线程池回调，lock(io) 读、lock(gate) 写 buf、Interlocked 写时间戳。
4. FrameGapLoop 检测线程：只读 lastDataTicks，到点调 OnFrameGap->Drain。

协调四件套：
- lock(gate)  保护 buf（List<byte> 非线程安全，AddRange/RemoveRange/Clear 都在锁内）
- lock(io)    保护 SerialPort（Write/Read/DiscardInBuffer/Close 互斥；RS485 半双工也不允许同时收发）
- AutoResetEvent frameReceived：一发一等握手信号，Set 唤醒一个等待者；超时分支 Reset 防残留信号误判
- volatile + Interlocked：running、curSlave 用 volatile 保可见性；lastDataTicks 是 64 位 long，
  32 位机上读写非原子，必须 Interlocked.Read / Interlocked.Exchange

锁顺序统一 io->gate（OnData 和超时分支一致），避免 AB-BA 死锁。

四、共享数据的修改（谁写、谁读、怎么保护）
共享变量      | 写者                          | 读者                     | 保护方式
buf           | OnData 追加 / Drain、超时清空 | Drain 切帧               | lock(gate)
sp 串口       | SendLoop.Write / OnData.Read  | 互斥                     | lock(io)
curSlave      | SendLoop 发送前写             | Handle 校验应答归属      | volatile byte（原子读写）
running       | Main(Ctrl+C) 写               | 三个线程循环条件         | volatile bool
lastDataTicks | OnData Exchange 写            | FrameGapLoop Read        | Interlocked（64 位原子）
frameReceived | Handle 在 CRC+从站匹配后 Set  | SendLoop WaitOne         | AutoResetEvent（内核信号）

数据流转（接收方向）：
串口字节 -> OnData(tmp) -> buf 堆积 -> Drain 按 FrameLength 切 -> CRC 校验
-> 从站地址比对 curSlave -> 解析温湿度 -> Set 信号 -> SendLoop 醒 -> 发下一从站请求

五、记忆口诀
CRC16-Modbus：初值 FFFF、多项式 A001。
  口诀：「先异或，八次移；见一移异，见零只移」
  （每字节先与 CRC 异或，再循环 8 次：最低位是 1 就右移后异或 0xA001，是 0 只右移；A001 是 8005 的镜像）

帧长：「03 应答看第三字节，总长 3+N+2；功能码最高位是 1，异常帧固定 5 字节」

3.5 字符：「一字符十位，三点五位静默判帧尾」9600->3.65ms，115200->0.304ms

三十二、"处理粘包帧时新帧会不会考虑？清除帧会不会考虑？"——粘包切帧安全，但OnFrameGap清残帧有锁间窗口竞态会误清新帧

【1.处理粘包时新帧会不会考虑】会。
  Drain在lock(gate)里切帧，OnData入新帧也要lock(gate)，互斥。
  新帧不会丢，等Drain释放gate后入buf，Drain的while循环回顶再lock继续切。✓靠lock互斥保证。

【2.清除帧时会不会考虑新帧】分两处清，一处安全一处有竞态：

  【安全】SendLoop超时清(行123 lock(gate){buf.Clear();})：
    lock内，OnData入新帧被lock阻塞，清完才入，不误清。
    但若OnData已从驱动读走字节(过了io锁)还没入buf(没到gate)，这些字节清不掉，变"迟到应答"——
    靠行124 frameReceived.Reset() + 行286 frame[0]!=curSlave身份校验兜底。✓考虑到。

  【竞态】OnFrameGap清(行188 buf.Clear())：
    lock内，但Drain()(行181)和行183 lock(gate)是两次独立加锁，中间有窗口。
    OnData在这个窗口入的新字节，会被行187 ToArray包进rest当残帧、行188 Clear清掉。
    如果这新字节是下一帧开头，整帧因开头丢失CRC错被丢。✗潜在竞态，代码没特殊处理。

【OnFrameGap竞态时序】
  Drain()释放gate → OnData抢到gate入新字节X → OnFrameGap行183抢到gate，rest=含X，Clear清掉X。
  X若是下一帧开头→整帧CRC错丢弃。

【诚实补充】
  1.OnFrameGap的Drain()+lock(gate)不原子是设计缺陷，正确做法是把切残帧逻辑放进同一个lock
    (C# lock可重入，但Drain的while结构要改)，或用try/finally保证原子。
  2.触发概率：9600下3.65ms窗口短，需新字节恰好在此窗口且OnData抢先；高波特率(115200→0.3ms)概率上升。
  3.这正是第二十八章说的"并发bug藏在交错里"——单看1次回合看不出来，
    要靠反例构造(主动设计"3.65ms静默后新字节恰好到来且OnData抢先"的时序)才抓得着。

口诀：「粘包切帧靠lock互斥，新帧等释放后入buf不丢；超时清靠Reset+身份校验兜底迟到应答；OnFrameGap的Drain和清残帧两次锁不原子，中间窗口新字节会被误当残帧清掉——并发bug藏在锁间窗口里」

三十一、"粘包和拆包对于静默3.65ms怎么解释"——串口借用TCP术语，静默是串口独有定界信号TCP没有

【先厘清】粘包/拆包是TCP术语，串口严格不这么叫(叫"一次收多帧/一帧分多次收")，但现象一样。
  关键区别：TCP是持续流没有静默，靠应用层长度字段定界；
  Modbus RTU跑在串口，多了"静默定界"这层——串口半双工/总线，从站发完会停，静默是天然帧边界信号。

【3.65ms双重角色】
  定界：静默>=3.65ms=帧边界(帧间分隔)
  容忍：帧内字符间隔1..04ms<3.65ms，不会误判帧结束(允许攒帧)
  1.04ms~3.65ms模糊区，<3.65ms都算帧内继续攒

【粘包(一次收多帧)+3.65ms】
  两帧紧挨着来、中间静默<3.65ms。FrameGapLoop不触发，靠Drain的FrameLength长度字段切——
  切走第1帧剩第2帧继续切。粘包靠长度字段切，不靠静默。
  风险：两帧中间静默<3.65ms且第1帧CRC错，Drain滑动1字节可能搅乱两帧。

【拆包(一帧分多次收)+3.65ms】
  5字节应答先来3再来2。第1段入buf，Drain说要5字节不够return等更多；
  帧内间隔1.04ms<3.65ms，FrameGapLoop不会误判；第2段入buf，buf够5字节，Drain切走。
  拆包靠"攒buf+等够长度"处理，3.65ms保证攒的过程中不被误判帧结束。
  风险：拆开的两段中间静默>3.65ms(异常从站/抖动)，FrameGapLoop误判帧结束→残帧被Handle丢弃(第三十章讲的风险)。

【这份代码的双保险】
  粘包：Drain while循环+FrameLength长度字段切
  拆包：buf攒+buf.Count<len return等够
  静默兜底：OnFrameGap处理"长度判不出但静默说帧结束"的残帧
  Modbus RTU = 长度字段定界(帧内) + 静默定界(帧间)

【诚实补充】
  1.3.65ms不是魔法数字，是Modbus规范3.5字符时间按波特率算(行62)，
    波特率越高阈值越小(115200→0.304ms)对抖动越敏感。
  2.TimeoutMs=12ms(行39)是发送线程等应答的超时，跟FrameGapMs=3.65ms(帧内定界)是两个不同超时别混——
    前者管"等不等得到应答"，后者管"收到的字节流怎么切帧"。

口诀：「粘包靠长度字段切(Drain while循环)，拆包靠buf攒等够长度；3.65ms定帧间边界+容忍帧内1.04ms间隔；静默是串口独有的定界信号，TCP没有；长度定界(帧内)+静默定界(帧间)双保险」

三十、"OnFrameGap里Drain已切帧，为啥还要Handle(rest)处理残帧？不能直接丢？"——静默是协议定界权威信号，残帧很可能就是完整帧

【Drain切什么/切不动什么】
  Drain切"完整帧"(长度够+CRC对)，切不动的是"残帧"：
  - 不够3字节帧头(行235 buf.Count>=3不满足)return
  - FrameLength判不出(行223非0x03/0x04/异常功能码)return -1
  - 不够整帧长(行239)return等更多
  - CRC错滑动1字节(行252)滑完可能剩残帧

【OnFrameGap的时机=帧超时(3.65ms静默)】
  静默是Modbus协议层权威信号"这批数据就是一帧的全部"。
  所以buf里切不动的残帧，很可能就是一帧完整内容，
  只是FrameLength当时判不出。Handle(rest)用"协议静默信号"兜底"长度猜测"。

【为什么不能直接丢弃】
  1.残帧可能是完整帧，FrameLength判不出：帧超时时buf只有2字节(应答被拆段)，
    Drain行235 buf.Count>=3不满足return，丢弃就丢应答。
  2.非标准功能码：FrameLength行223对不认的功能码return -1，Drain切不动，
    但帧超时说明这是合法帧，丢弃就丢。
  3.CRC滑动残留：Drain行252滑动1字节对齐，滑完剩残帧，
    Handle再CRC校验一次，过了就解析，不过安全丢弃——比直接丢多一次机会。

【Handle(rest)不会崩】
  Handle内部行267 frame.Length<4帧太短丢弃、行275 CRC错丢弃，都有兜底。
  最坏打印错误丢弃(和直接丢效果一样)，最好多救回一帧。

【本质】
  Modbus RTU没有帧起始符，靠静默超时定界。
  FrameLength是"猜长度"，帧超时是"协议说这就是一帧"。
  丢弃=只信猜不信协议，会丢应答。

【诚实补充(风险)】
  1.若一帧被从站拆两段、中间静默>3.65ms(异常从站/总线干扰)，
    FrameGapLoop会在前段触发OnFrameGap，rest=前段被Handle丢弃，后段再来又丢——
    整帧因静默拆开而丢失。变长+静默定界的固有风险，代码没特殊处理(也很难处理)。
    正常从站帧内间隔1.04ms<3.65ms不会触发。
  2.OnFrameGap的Drain()和后面lock(gate)是两次独立加锁，中间OnData可能又入buf。
    但buf.Clear()只清当时内容，新字节留下下轮处理，可接受。
  3."可以直接丢弃"——可以，代价是丢应答。代码选"再试解析"是更保守策略，靠Handle内部校验保安全。

口诀：「Drain切完整帧，切不动的是残帧；帧超时=协议说这是一帧，Handle(rest)用静默信号兜底长度猜测；直接丢=只信猜不信协议，会丢应答」

二十九、"发→等→收→解→醒指什么操作"——逐行映射Program.cs（已通读364行）

【发】SendLoop 行97-114，发送线程：
  行102 id=Slaves[idx] 取当前从站地址
  行104-105 构造请求[id,0x03,0x00,0x00,N高,N低]+Crc16追加成完整帧
  行106 curSlave=id 写volatile，告诉接收线程"在等谁"(防应答错配)
  行108-113 lock(io)持串口锁 sp.Write发到RS485总线
  行114 打印发送日志

【等】SendLoop 行116-125，发送线程：
  行116 frameReceived.WaitOne(TimeoutMs=12ms) 在AutoResetEvent上阻塞，CPU让出
  超时(false)→行122 lock(io)DiscardInBuffer清驱动缓冲 + 行123 lock(gate)buf.Clear()清残帧
         + 行124 frameReceived.Reset()清残留Set信号——防迟到应答错配下一轮
  收到(true)→往下走

【收】OnData 行134-155 接收线程 + FrameGapLoop 行159-176 检测线程，两线程协作：
  OnData(事件触发)：行137-143 lock(io)sp.Read读字节到tmp；行145-149 lock(gate)buf.AddRange入全局缓冲；
                    行152 Interlocked.Exchange(ref lastDataTicks)记最后收字节时刻；行154 Drain试切
  FrameGapLoop(后台轮询)：行164 Interlocked.Read读lastDataTicks；行167算gapMs；
                    行168 gapMs>=FrameGapMs(3.65ms)判帧结束→行171 OnFrameGap

【解】Drain 行228-260 + Handle 行263-325：
  Drain：行237 FrameLength算帧长(3+byteCount+2)；行239不够整帧return等更多；
         行244 CrcOk校验，通过行246 RemoveRange取走，失败行252滑动1字节重新对齐
  Handle：行273-279再校验CRC；行286 frame[0]!=curSlave校验应答者身份，不是当前在等的就忽略(防错配)；
         行301-320按byteCount=frame[2]解析N个寄存器，行315-317温度=t/10.0℃湿度=h/10.0%RH

【醒】Handle行319/296 + SendLoop行116：
  行319 frameReceived.Set()置位AutoResetEvent(异常响应行296也Set)
  →唤醒SendLoop行116 WaitOne返回true
  →行127 idx=(idx+1)%Slaves.Length轮下一站
  →回行100 while顶进下一回合(发→等→收→解→醒)

【诚实补充】
  1."收"是两线程协作：OnData收字节入buf + FrameGapLoop判帧结束。单看OnData不够，帧结束靠静默超时。
  2."解"在两处触发：OnData末尾Drain(边收边解早切) + OnFrameGap里Drain(帧齐了切干净晚切)。
  3."醒"用AutoResetEvent：Set一次只唤醒一个WaitOne并自动复位，保证多从站轮询不误唤醒。
  4.单回合内三线程已并发(SendLoop+OnData+FrameGapLoop)，"单回合"≠"单线程"，单回合内就有交错。
  5.行129 Thread.SpinWait(IntervalMs)是BUG——SpinWait参数是迭代次数不是毫秒，会无间隔疯狂连发，应改回Thread.Sleep(IntervalMs)。

口诀：「发=构造+CRC+持io写串口；等=WaitOne阻塞让CPU；收=OnData入buf+FrameGap判静默；解=Drain切帧+Handle校验身份解析；醒=Set信号唤醒轮下一站」

二十八、"多线程打乱时间顺序，所以1次请求就够分析基础数据流转？"——推理方向反了，没全局顺序恰恰是1次不够的原因

【纠前提】"多线程会打乱时间顺序"不准确(第二十四章讲过)：
  不是"打乱了"，是多线程本来就没有全局时间顺序。
  各线程有自己的时间线，线程间事件是偏序(partial order)，
  只有 lock/volatile/Interlocked 建立 happens-before 才在某些事件间确定先后。
  lock 是建序，不是乱上添乱。

【纠推理方向】
  正因为没有全局时间顺序(交错无限)，1次只采样了"一种交错"，
  并发bug藏在其他交错里——所以1次不够，不是1次够。
  "多线程没全局时间顺序"是"1次不够"的原因，被用成了"1次够"的理由，方向反了。

【1次能/不能】
  能：建单回合因果骨架(发→等→收→解→醒)，这是"基础数据流转"的骨架
  不能：看回合衔接(残留→下一轮)、循环闭合(idx回起点)、累积(buf堆积)、
        极端竞态(迟到应答恰在下一站WaitOne时到达)——这些才是并发bug藏身地

【潜台词纠偏】
  "1次请求期间多线程已在并发跑，所以1次就能看到多线程交错"——
  对，1次期间确实能看到一种交错。但并发bug不在"一种交错"里，在"所有可能交错"里。
  1次只掷出骰子一个面，要说"骰子公平"得掷很多次。

【结论】
  1次建骨架是对的(基础)，但"1次就够"是错的。
  骨架是脚手架，bug狩猎在衔接/闭合/累积/反例。
  多线程无全局时间顺序这件事，恰恰逼着你不能只看1次。

口诀：「多线程不是打乱时间顺序，是本来就没有全局顺序；正因为没有，1次只采样一种交错，并发bug藏其他交错里——没全局顺序是1次不够的原因，不是1次够的理由」

二十七、"1次建骨架2次看衔接，是先假设只发1次再假设只发2次？"——理解偏了，是推演N回合不是限制发N次

【纠正】"假设只能发N次"像给程序加约束只跑N圈，那是测试场景设计。
  代码分析是"在脑子里/纸面上推演N次回合的因果链"，不用真跑、不用真限制。
  程序实际无限循环，你是从最简场景逐步扩大观察窗口建立直觉，不是约束程序行为。

【准确表述】
  1次：推演单回合因果(发→等→收→解→醒)，建骨架建直觉
  2次：推演两回合衔接(残留→下一轮、curSlave切换、idx变)，看回合之间
  3次：推演三回合闭合(idx 01→02→01回到起点)，验循环复位
  N次：看累积(buf堆积、计数溢出、长期漂移)
  反例：主动构造极端竞态(不靠次数)

【数学归纳法类比】
  1次=证 n=1 成立(骨架)，2次=证 n→n+1 衔接成立。
  但并发比归纳难：归纳法衔接确定，并发衔接有时序交错，
  一种交错对不代表所有交错对，所以还要反例构造补刀。

【为什么1次2次不够要看3次】
  循环闭合在第3次才出现(01→02→01，第3次回01)，
  2次只走半圈，看不到"回到起点状态是否正确复位"。

【诚实补充】
  "1次2次3次"阶梯是我包装的方法论框架，不是教科书标准术语。
  业界标准说法是"逐步求精/分层推理 + 状态机分析 + 反例构造"。
  包装成次数是为了好记，本质是"从最简场景逐步扩大观察窗口"。

口诀：「不是限制程序发N次，是推演N回合的因果；1次建骨架2次看衔接3次验闭合，归纳法思路但并发要反例补刀」

二十六、"那假设只发2次请求？"——2次看衔接，但仍不够，换方法不堆次数

【2次比1次多看到什么】"回合衔接"层2的问题开始显现：
  第1次残留如何影响第2次——残帧接在第2次数据前、信号残留让第2次误判、
  curSlave从01变02的切换、idx从0变1。比如"01超时→buf残留→02数据接在残帧后→Drain滑动对齐"，
  1次看不到，2次能看到。

【但2次仍不够】
  · 稳态未达：累积问题要N次后才显现(buf堆积、超时计数累积、信号反复Set/Reset边界)
  · 循环回归未验：idx循环01→02→01，第3次回到01才是"循环闭合"，2次只走半圈，
    没验证"回到起点时状态是否正确复位"
  · 极端竞态要主动构造：不是"发2次"能碰上的——"01迟到应答恰在轮到02的WaitOne时到达"
    这种时序要主动设计，不是跑2次自然发生
  · 从站缺席/全超时：2次都超时要专门分析

【关键】不是"加次数"，是"换方法"。次数堆叠=穷举执行路径，但并发路径无限(每次交错都不同)，
堆不过来。正确方法是不变量+状态机+反例构造(第23章)。反例构造是"主动设计能破坏不变量的时序"，
不是"多跑几次看运气"。

【分析阶梯(递进，2次是其中一级)】
  1次：因果骨架(发→等→收→解→醒)
  2次：回合衔接(残留→下一轮)        ← 你现在这一级
  3次：循环闭合(idx回到起点，状态复位验证)
  N次/稳态：累积效应(buf堆积、计数器溢出、长期漂移)
  反例构造：极端竞态(不靠次数，靠主动设计)

【用Program.cs示范2次能看到/看不到的】
  能看到：01发→等→收→Set→idx=1→02发→等→收→Set→idx=0(一次完整轮询两站)；
          01超时→Clear→Reset→02发(衔接：超时后状态清空)；
          01残帧→02数据接后→Drain滑动(衔接：残帧跨回合)
  看不到：idx回到0后第3次01是否正确(循环闭合)；
          01连续超时5次的诊断提示(累积)；
          01迟到应答恰在02的WaitOne时到达(极端竞态，要主动构造)；
          buf长期堆积(稳态)

【诚实补充】"发2次"作为分析练习是好的——比1次更接近真实，但别陷入"次数堆叠"思路。
终极方法还是不变量+状态机+反例，次数只是帮助建立直觉的脚手架。

口诀：「1次建骨架，2次看衔接，3次验闭合，N次看累积；极端竞态不靠次数，主动构造才抓得着」
     「次数是脚手架不是终点，并发路径无穷堆不过来；2次只是衔接的最小单元，不是够用的边界」

二十五、"分析数据流转要假设只发一次请求？"——对一半，单次建骨架，多次抓累积

【你的直觉】假设只发一次请求开始分析——对，这叫"单次回合分析"或"隔离变量"：
请求-应答系统是周期性重复的，一次交互的因果链搞清楚，整个循环就清楚了大部分。
这是科学方法的"隔离变量"：先最小单元，再组合。

【但只做单次不够】单次能搞清楚"发→等→收→解→醒"的因果骨架，
搞不清楚的(必须靠"多次"才暴露)：
  a. 错位累积：第N次请求的迟到应答错配到第N+1次 → curSlave比对防这个
  b. 残帧累积：上一次没切完的残帧留到下一次 → Drain滑动对齐/超时Clear
  c. 信号残留：上一轮Set没被消费，下一轮WaitOne误判成功 → Reset防这个
  d. 超时与迟到竞态：单次里不发生，多次循环里才发生
  e. 轮询状态推进：idx在多次中循环 (idx+1)%Slaves.Length
并发bug大多在"回合衔接处"，单次分析看不见。

【精确分析单元】不是"只发一次"，而是"一次完整回合 + 回合间的衔接"：
  一个回合 = 发请求 → 等应答(或超时) → 收数据 → 解析 → 唤醒
  回合衔接 = 上一回合的残留(残帧/信号/idx/curSlave)如何影响下一回合
这才是请求-应答循环系统的完整分析单元。

【用Program.cs示范】
单次回合(假设只发一次01)：
  t0 SendLoop: curSlave=01 → lock(io)写 → WaitOne
  t1 OnData: lock(io)读 → lock(gate)AddRange → Drain切帧 → Handle匹配 → Set
  t2 SendLoop: WaitOne返回 → idx++ → Sleep → 准备发02
  因果链清楚 ✓
多次回合才暴露的问题：
  · 01应答迟到，轮到02时才到 → frame[0]!=curSlave忽略(单次看不到)
  · 01超时后buf没清干净，02数据接在01残帧后 → Drain滑动对齐(单次看不到)
  · 01超时后frameReceived残留Set → 02的WaitOne误判 → Reset(单次看不到)
  · idx循环01→02→01(单次看不到循环)

【三层视角】
  层1 单次回合：因果骨架(发→等→收→解→醒)
  层2 回合衔接：残留/状态如何传递(残帧/信号/idx/curSlave)
  层3 异常路径：超时/迟到/错位/CRC失败/从站缺席
  只做层1会漏掉大部分并发bug(都在层2层3)。

【方法论升华】"假设只发一次"=时间维度上的"切片分析"，把无限循环切成一个周期，
类比傅里叶把周期信号拆成一个周期+重复。但并发系统的"非线性"在于：
周期之间有状态耦合(残帧/信号)，不能简单重复，所以要加"周期衔接分析"。

口诀：「单次回合建骨架，多次回合抓累积；错位残留和竞态，单次分析看不见」
     「先切一个回合看因果，再接回合之间看残留；并发bug都在衔接处，单次只能看骨架」

二十四、"是lock把运行时间线打乱了？"——反了，无锁才真乱，lock是建序

【纠正方向】lock 不打乱时间线，恰恰相反：多线程本来就没有全局时间顺序，
lock 是在"本来就乱"的并发里"人为钉下确定的先后关系"（happens-before）。
说"lock打乱"是把因果搞反了——没有lock的多线程才是真乱，而且乱到出错。

【为什么"本来就没全局时间线"】两个线程在不同核上同时跑，谁先执行某行、谁后执行，
由CPU调度/缓存/乱序执行决定，程序层面根本无法预测。这才是真正的"乱"，
且这种乱导致数据竞争（buf被改烂）。lock的存在让"本来不确定的"变成"临界点上有序的"。

【lock怎么建序】
  入口acquire屏障：拿到锁前的内存操作对其他线程可见
  出口release屏障：锁内的写对下一个拿锁的线程可见
  互斥：同一把锁同一时刻只一个线程在锁内 → 锁内代码相对"同锁线程"串行 → 建立"先A后B"
  即 A出锁 happens-before B进锁。秩序就此钉下。

【代价与收益】lock会让等锁的线程推迟(挂起)，但这是局部代价(只锁内几行、微秒级)，
换来临界区串行+内存可见=数据不烂。推迟≠打乱，推迟是"多等一个灯"。

【红绿灯类比】
  无lock = 十字路口没灯：车各方向乱穿，谁先过全凭运气，还会撞车(数据竞争)
  有lock = 加了红绿灯：轮流过，"打乱"了"谁先到谁先过"的自然顺序，
  但换来"不撞车+有序通过"。lock不是把有序变无序，是把无序变有序。

【"时间线"三种含义的澄清】
  指"每线程各自的程序序" → lock不打乱，每线程仍按代码顺序走
  指"多线程交错的全局顺序" → 本来就不存在/不确定，lock在其中钉下确定点
  指"某线程被推迟"        → 是的，等锁的线程被推迟，但这是局部代价不是打乱

【本代码实证】
  无lock(gate)：OnData.AddRange 和 Drain.RemoveRange 交错，buf内容不可预测——这才是乱
  有lock(gate)：两者串行，要么先加后切、要么先切后加，两种都正确——临界点有序了

口诀：「无锁才真乱(乱到出错)，有锁是建序(局部串行+可见)；lock是红绿灯不是搅拌机」

二十三、代码没运行怎么 review 找 bug？——并发代码静态审查法（含本代码实测）

【核心观念】并发代码不能"按时间顺序读"（多核下根本没有全局时间顺序），
要换成"按不变量/契约/状态机/反例"读。这是成熟方法论，比顺着读有效。

【七法清单】
1. 不变量审查：列出"永远该成立"的断言，逐个改写点验证。
   本代码不变量：buf是"完整帧+残帧"连续流；curSlave=当前在等的站；
   frameReceived被Set当且仅当收到curSlave的有效应答；running=false后线程全退。
2. 锁契约四查：①同变量所有读写是否同把锁 ②锁顺序全局是否一致 ③锁内有无长操作/阻塞 ④锁内有无回调重入。

4. happens-before推演：对关键数据问"B读时A的写一定发生了吗"，靠lock/事件/Interlocked的内存屏障回答。

二十二、时间相关机制如何保证"运行的时间顺序"？

【核心】多线程不追求"全局时间顺序"，而是三层模型：
  层1 各自节拍（Sleep/SpinWait/Stopwatch）——每个线程自己定时，自顾自
  层2 因果握手（lock/AutoResetEvent/Interlocked）——关键事件建立"先于"关系
  层3 超时兜底（WaitOne(timeout)/FrameGapMs）——等不到也别卡死
绝对时间顺序在多核并发下根本不存在——两个核同时跑，谁先谁后是物理问题，程序管不了。
程序要的不是"按时间排序"，是"结果正确"：buf不烂、应答不错配、不卡死。

【各机制管哪层"时间问题"】
Thread.Sleep(ms)        层1 自身节拍·挂起定时。挂起≥ms毫秒(精度~15.6ms)，不占CPU。
                        SendLoop用Sleep(15)控请求间隔；Main用Sleep(200)等退出。
                        "至少"ms，多一点无所谓——要的是"别太快刷爆总线"。
Thread.SpinWait(n)      层1 自身节拍·忙等定时。参数n是迭代次数(不是毫秒！)，烧CPU换精度。
                        PreciseSleepMs里配Stopwatch做微秒级忙等，因为Sleep测不出3.65ms。
Stopwatch               层1 量时间(不是等时间)。QPC微秒级，给FrameGapLoop判帧尾提供精确时钟。
lock                    层2 因果顺序(不是时间顺序)。出锁release/进锁acquire建happens-before：
                        A锁内写buf出锁后，B进锁一定看到A写的值。不保证"何时"拿到，只保证"拿到后状态对"。
AutoResetEvent.WaitOne  层2+层3 等待+超时二合一。等到Set立即返回true；等不到最多等timeout返回false。
                        SendLoop发完WaitOne(50ms)：因果等(应答到了才继续)+超时兜底(50ms没到当丢了)。
                        Set/WaitOne建强因果：Handle里Set()在解析完之后，SendLoop醒来时数据已就绪。
volatile/Interlocked    层2 跨线程可见性·内存屏障。OnData写lastDataTicks后FrameGapLoop下次读一定看到新值，
                        否则检测线程读到旧时刻、判帧尾时机错乱。curSlave volatile同理。

【一个完整时序串起来看】(无全局时钟，全靠三层协作)
t0       SendLoop: curSlave=01(volatile写) → lock(io)写串口 → WaitOne(50ms)[挂起]
t0+18ms  从站应答字节到 → 串口事件 → OnData在池线程跑
t0+18ms  OnData: lock(io)读字节 → lock(gate)AddRange → Interlocked写lastDataTicks → Drain
t0+18ms  Drain: lock(gate)切帧 → CRC → Handle:读curSlave(volatile)匹配 → 解析 → Set()
t0+18ms  SendLoop: WaitOne返回true → idx++ → Sleep(15ms) → 发02
全程没有"对时"，靠：volatile保curSlave可见、lock保buf不烂、Set/WaitOne握手、Sleep控节拍。

【诚实补充·这套机制的代价】
1. SpinWait烧CPU：115200下PollMs=0.15ms，FrameGapLoop基本全程烧满一个核。
2. Sleep精度差：15ms间隔实际15~31ms，总线利用率有抖动。
3. 超时是"最佳努力"：50ms超时vs实际18ms应答有32ms余量，应答慢到50ms就误判丢包。
4. 没有"全局时间戳排序事件"——要做历史回放/事件溯源，需另加时间戳记录层。

口诀：「各自节拍·因果握手·超时兜底；多线程不排时间排因果，不靠全局时钟靠局部握手」

二十一、澄清："A持有锁，B能执行到lock之后的代码？"——不能！（对上一章歧义的修正）

【你的质疑】对。每个线程自己的执行顺序（程序序）是铁律：
  lock之前的代码 → lock入口(排队) → 锁内 → lock之后的代码。
  A持锁时 B 卡在入口，B 程序里排在 lock 之后的那些行，B 现在一行也到不了。
  上一章"lock之后的代码B照常执行"表述有歧义，以本章为准。

【我真正想纠正的错误想象】"卡的是点，不是面"：
  错误想象：A 在方法里 → 整个方法对 B 关闭，B 连方法都进不来。
  正确模型：B 可以和 A 同在同一个方法里！B 能执行方法开头到 lock 之前的所有行，
  只在 lock 这一个"闸门点"停下。方法不是闸门，lock 那一对大括号才是。

河道模型：代码=河道，线程=船，lock=船闸。
  A 在闸内时，B 可以已经开到闸前水域（同一条河、同一方法里），
  但闸后的河道（lock之后的代码）B 现在到不了——
  不是整条河对B关闭，只是闸这一个点。B 就停在闸前排队，不占动力（挂起不费CPU）。

用 Drain 的真实代码标出 B 的"停止线"：
  void Drain() {
      while (true) {                    // B 能到这儿（与A同方法共存）
          byte[] frame = null;
          lock (gate)                   // ★ B 的停止线：A持gate时 B 卡死在这行
          {                             // ---- 临界区：B 进不去 ----
              ...切帧...
          }
          if (frame == null) return;    // lock之后：B 必须拿到锁+出锁后才到得了
          Handle(frame);
      }
  }

若一个方法有多把不同的锁，B 逐闸排队，互不影响：
  锁外代码1            // B 随便跑
  lock (io)   { ... } // 闸门1：只在 io 被持时卡
  锁外代码2            // 过了闸门1才能到
  lock (gate) { ... } // 闸门2：只在 gate 被持时卡
  锁外代码3            // 过了闸门2才能到

口诀：「程序序是铁律，船到闸前排队；闸挡一步不挡河，闸后水先到不了」

二十、你的理解确认："线程遇 lock 不能跳过，必须等"——对，补三个精确点

【你的表述】不同线程调同一个方法，遇到 lock 时其他线程不能跳过 lock 直接执行后面的代码。
【判定】正确。lock 不是栏杆（不能绕着走），是闸门（排队过）：
线程B 到达 lock 语句而锁正被A持有时，B 就阻塞在 lock 入口那一行——
既进不了锁内，也绕不过锁执行后面的代码，直到 A 出锁、B 拿到锁后才继续。

精确点1：B 是"挂起排队"不是"空转等"——不占 CPU。
  CLR 把 B 放进该锁对象的等待队列，A 出锁瞬间唤醒一个。排队不烧钱。

精确点2：卡住的位置是"lock 入口"，不是整个方法。
  方法里 lock 之前、之后的代码（不在锁内的行）B 照常执行；
  只有 lock(gate){ ... } 这一对大括号是闸门。所以"锁内只放最短代码"的铁律
  就是在缩短排队长度——闸门越窄，全队过得越快。

精确点3：互斥不看"同一个方法"，看"同一个锁对象"。
  本程序 OnData 和 Drain 是两个不同方法，但都 lock(gate)，照样互斥；
  哪怕十处代码八种方法，锁同一对象就排同一条队。呼应：锁管桥（对象）不管谱（方法）。

补充：真想"拿不到就不等、去干别的"，有合法跳过姿势 Monitor.TryEnter：
  if (Monitor.TryEnter(gate, 10)) { try { /*拿到锁，干活*/ } finally { Monitor.Exit(gate); } }
  else { /*10ms没拿到，走别的路，不排队*/ }
  普通 lock 等价于"无限期排队的 TryEnter"。本程序收发场景必须等（数据不能丢），所以用普通 lock。

时间线示例（OnData 持 gate 时 FrameGapLoop 到来）：
  t0     A 进 lock(gate)，开始 AddRange（约2μs）
  t0+1μs B 到 lock(gate) 入口 → 锁被占 → B 挂起进等待队列（CPU 让出）
  t0+2μs A 出锁 → 唤醒 B → B 拿锁进临界区 → 出锁后继续 Handle(rest)

口诀：「lock 是闸门不是栏杆：不能绕，只能排；排队挂起不费电；闸门越窄过得越快」

十九、两个理解纠偏：lock 只是串行？新线程只是重复动作？

【问题1】lock 的作用只是让锁内代码串行执行？——对一半，三点精确化：

① 不是"全部串行"，是"按锁分组串行"：同一把锁才互斥，不同的锁可并行。
   本程序两把锁各管一摊：lock(io) 出现在 SendLoop.Write / OnData.Read / 超时Discard / Main.Close
   四处，它们互斥；lock(gate) 出现在 OnData.AddRange / Drain / 超时Clear / OnFrameGap，它们互斥。
   但 SendLoop 持 io 写串口的同时，OnData 可以持 gate 动 buf——两组互不排队。
   所以准确说：lock 让"抢同一把锁的线程"串行，不是让全程序串行。

② lock 保的是"资源"，不是"代码"：锁对象=独木桥，代码=过桥动作，共享数据=桥那头的货。
   三段长得完全不同的代码（追加/切帧/清空）只要锁同一个 gate 就互斥；
   反过来同一段代码若用两把不同的锁进来也互不干扰。理解 lock 要盯着"它守哪个变量"，
   而不是"它框住哪几行"。

③ 附送一个隐藏技能：内存可见性。lock 不只防"同时改"，还防"改了看不见"——
   进锁 acquire、出锁 release，锁内写的共享变量对下一个拿锁的线程保证可见
   （否则 CPU 各自缓存，你改的我读不到）。这也是 curSlave 用 volatile 的同款问题，
   只是 volatile 保可见性不保互斥，lock 两个都保。

【问题2】新线程只是重复完成定义好的代码动作？——"重复"错了，是"并发"。

精确模型：代码=乐谱（只有一份，存在代码段），线程=乐手（各自有谱架=独立的栈、
进度=指令位置、节奏=调度时间片）。一份乐谱可以多个乐手同时吹——
本程序的 Drain() 就可能被 OnData(池线程) 和 FrameGapLoop 在同一瞬间同时进入，
两个线程各自带着独立的局部变量跑同一份代码，互不覆盖（栈隔离）。
这正是 buf 必须 lock(gate) 的原因：两人同时弹同一架钢琴必乱。

三个纠正：
- 线程不是"重复做"（时间先后），是"同时做"（时间重叠）——分身术，不是复印机。
- 本程序几个线程跑的是完全不同的代码段（SendLoop/FrameGapLoop/OnData），是分工不是重复。
- 线程的价值在"同时等待"：等Ctrl+C、等应答、等静默互不相干，一个流等一件事。

口诀：「锁管桥不管谱，同桥才排队；线程是乐手不是复印，同谱各自吹，同琴要加锁」

十五、"双击exe打不开" 根因与修复（含黑匣子机制）

【根因】不是崩溃在业务代码，是 XAML 运行时校验：
ToggleButton 的 Style 写了 BasedOn="{StaticResource {x:Type Button}}"，
而 WPF 铁律：BasedOn 的样式 TargetType 必须是当前类型的基类。
Button 和 ToggleButton 是兄弟（都继承 ButtonBase），兄弟样式不能 BasedOn，
运行时 Style.Seal() 抛 InvalidOperationException → 包成 XamlParseException（行112）→ 双击秒退。
编译零错误是因为该校验只在运行时做，XAML 编译器不查。
【修复】ToggleButton 样式去掉 BasedOn，共用 Setter 各自写全。已验证：
进程存活、窗口标题"尘博 SCADA 监控站 · Modbus RTU"、Responding=True、无 crash.log。
【黑匣子（新增，治本）】App.xaml 去掉 StartupUri，App.xaml.cs 手动启动：
- 构造函数包 try/catch，启动异常写 bin 目录 crash.log + 弹窗；
- DispatcherUnhandledException + AppDomain.UnhandledException 全局兜底，
  以后任何双击闪退都会在 crash.log 留下完整堆栈，双击不再"死无对证"。
口诀：「Style 继承只能 BasedOn 亲爹（基类），兄弟样式各自写全」

十三、"扫描没有发现0x02" 根因实锤（截图证据）

【结论】不是线路、不是参数、不是超时——是 Modbus Slave 模拟器配置错了。
截图证据链（互相印证）：

   SCADA 就能解析出 02 站的温湿度并上波形；
4. 回 SCADA 重新"扫描总线"：应发现 0x01 和 0x02 两个站；再启动轮询，超时消失。

【回顾排查路径】超时日志 → 无迟到/无CRC失败 → 扫描只有01 → 截图实锤模拟器 ID 配错。

十、"日志输出从站2超时无应答" 问题分析与处理

【问题】SCADA 日志反复出现 "[超时] 从站02 50ms 无应答"，但从站01正常。

3. 接线/终端电阻问题：但从站1正常基本可排除。

- 顶栏新增"轮询从站"输入框（默认 01,02，逗号分隔十六进制），只接1号站就填 01，超时刷屏即消失；

- 诊断提示：同一从站连续超时满 5 次，日志自动输出建议——
  "从站XX 连续5次超时：可能不存在/未上电/地址不对，可从轮询列表移除；若日志有'迟到应答'则调大超时"。

  → MainWindow 转发 Wave.AddPoint → InvalidateVisual 滚动。约7.5点/秒/通道。

诚实补充：
1. 引擎里 129 行用的是 Thread.Sleep(IntervalMs)——你控制台版改成 SpinWait(15) 是迭代次数≠毫秒，
   会导致无间隔疯狂连发，引擎没带这个 BUG（167行先乘后除、189行无持锁Sleep，均已修复态）。
2. 自绘波形 vs 专业库：OxyPlot/ScottPlot 功能强（缩放/游标/导出）但要引包；
   当前 2 通道×600点自绘零依赖足够，要分析功能再换 ScottPlot.WPF。
3. 没接真串口也能跑：点启动会捕获异常显示"打开失败"红字日志，不会崩。

八、lock 到底有什么用？对 4 个线程的影响

【本轮代码变化（先报）】
- 已修复：166/167 行整数除法 → 改为先乘后除 (ticks)*1000.0/Frequency ✓
- 已修复：189 行 lock(gate) 内 Sleep(50000) 已删除 ✓
- 新问题：129 行 Thread.Sleep(IntervalMs) 被改成 Thread.SpinWait(IntervalMs)！
  SpinWait 的参数是"自旋迭代次数"不是毫秒——SpinWait(15) 只转约几十纳秒就返回，
  等于两次请求的间隔从 15ms 变成约 0，发送线程会疯狂连发、刷爆 RS485 总线、CPU 升高。
  修复：改回 Thread.Sleep(IntervalMs)，或用文件里已有的 PreciseSleepMs(IntervalMs)（它才是按毫秒忙等的）。

【问题】lock 不影响排队的长度和时间，那它的用处是啥？
先纠正前提：lock 其实"会造成排队"（不然互斥无从谈起），但正常情况下锁内操作只有微秒级，
排队代价约等于 0。它不改变"业务工作量"（要收多少字节、发多少帧不变），
它换来的东西是——数据正确性：被保护的多步操作变成不可分割的整体，
别的线程要么看到改之前、要么看到改之后，永远看不到"改了一半"的中间态。

生活类比：lock 是单间厕所的门锁。它不决定今天多少人上厕所、每人蹲多久
（排队总量由业务决定），它只保证一次进一个人。没锁＝两人同时进一个隔间＝撞车。

用本代码讲"没 lock 会怎么烂"（以 buf 为例）：
  buf.AddRange(tmp) 内部是多步：查容量→不够就申请新数组→拷贝旧数据→写入→改 _size；
  buf.RemoveRange(0,len) 内部也是多步：后面元素往前搬→改 _size。
  若 OnData 扩容搬到一半时 Drain 同时 RemoveRange：_size 被两个线程交叉改写、
  底层数组被换、拷贝错位——结果丢字节/重复字节/内容错乱，甚至 IndexOutOfRange。
  有 lock 后：要么先加完再删、要么先删完再加，两种结果都正确，中间态无人看见。

lock 机制一句话：lock(obj) ≈ Monitor.Enter/Exit，同一个 obj 同一时刻只进一个线程，
其余在 obj 上排队，出来的瞬间放一个进去。所以"锁对象=独木桥，共享数据=桥那头的货"。

为什么用两把锁（io 和 gate）而不是一把大锁：
  按资源分锁，粒度才小、排队才短。发请求(碰io)和切帧(碰gate)可以并行互不排队，
  只有碰同一资源才需要等。一把大锁也能保证正确，但所有线程都串行，白瞎了多核。

死锁与锁顺序：两把锁嵌套时，全程序必须同一顺序获取（本代码统一 io→gate）。
  若线程A 持io等gate、线程B 持gate等io——环形等待，两人永远卡住（死锁）。

【lock 对 4 个线程的具体影响】
线程          | 它持锁时挡住了谁              | 它自己被谁挡            | 正常等待量级
SendLoop      | 持io写串口时挡住 OnData 的读   | OnData 持io读时它写不了 | 亚毫秒
OnData        | 持gate入buf时挡住 Drain/清理   | SendLoop 持io写时它读不了 | 微秒级
FrameGapLoop  | 持gate切帧时挡住 OnData 入buf  | OnData 持gate时它等      | 微秒~毫秒
Main          | 几乎不碰锁（退出时lock(io)关串口）| 无                     | 可忽略
注意：原来的 189 行 BUG 就是把"FrameGapLoop 持 gate 挡 OnData"从微秒放大到 50 秒——
锁内 Sleep(50000)，全员陪坐牢。这正说明铁律：锁内只放非保护不可的最短代码。
小瑕疵：148 行 Console.WriteLine 在 lock(gate) 内，控制台打印是毫秒级，建议挪到锁外。

口诀：
  「lock 是独木桥：不减队伍，只管一次过一人，桥上不撞车」
  「排队长短看锁内，锁内睡大觉，全员陪坐牢」
  「两把锁同向走(io→gate)；你等我、我等你，必死锁」

七、为什么发送和检测要各自开新线程（原理问答）

核心一段：一个线程同一时刻只能干一件事——要么在跑，要么在等。这个程序同一时刻有 4 件"互相不能等"的事：
主线程等 Ctrl+C、发送方阻塞等应答、串口字节随时来、有人盯着表判 3.65ms 静默。互相不能等就得各占一个执行流，
所以线程数 = 并发执行流数。代码里只 new 了 2 个 Thread（发送、检测），是因为接收流由 SerialPort.DataReceived 事件
免费白送——它的回调本来就跑在 .NET 线程池线程上，不用自己开。

1）发送为什么开线程（SendLoop）
- 发送循环里有两个"卡住自己"的动作：frameReceived.WaitOne(50ms) 阻塞等应答 + Thread.Sleep(15ms) 轮询间隔。
  阻塞的本质是"当前线程挂起"——谁调 WaitOne 谁被挂起。如果放主线程，主线程就永远困在收发循环里，
  没法同时监控 Ctrl+C 退出；业务上"等应答"这个挂起也不该拖累别人，所以派一个专职线程去卡它自己。
- 等待期间 CPU 是闲的，但串口字节随时可能到，收和发必须并发——接收靠 DataReceived 事件（池线程），
  发送自然也得是自己的线程，两边节奏互不干扰。

2）检测为什么开线程（FrameGapLoop）
- 帧结束的标志是"没有数据了"（静默3.65ms）——而 DataReceived 只在"有数据到"时触发，
  "没来数据"这件事本身永远不会产生任何回调！只能有人主动、持续地去问"距最后一字节过去多久了"，
  主动询问=循环，循环就得占一个线程。
- 精度逼着它独立：9600 下 3.65ms、115200 下 0.304ms，而 Thread.Sleep/Timer 精度只有约15.6ms
  （Windows 默认时钟节拍），根本测不出来。所以代码用 Stopwatch(QPC微秒级)+SpinWait 忙等——
  忙等会持续烧满一个 CPU 核，这种活必须丢给专用线程，不能跟收发抢。

3）诚实补充：能不能不开 / 有没有更省的做法
- 发送+检测不能合并：发送线程大半时间堵在 WaitOne/Sleep 里，检测要求每约1.8ms看一眼，
  一个堵着的线程没法同时做毫秒级轮询。
- Timer/Task.Delay 替代不了检测：精度都卡在 15ms 级，3.65ms 都测不准，更别说 0.3ms。
- 更省 CPU 的检测写法（代码没用）：检测线程用 Monitor.Wait(剩余时间) 挂起，OnData 每来一字节 Pulse 唤醒，
  拿"被唤醒"代替"轮询"，精度不减还不烧核。当前代码用 SpinWait 是拿 CPU 换实现简单。
- 另一种极简架构（代码没用）：一个线程都不开，主循环同步 sp.Write 后 sp.Read 阻塞读够字节数、
  靠 ReadTimeout 抛异常兜底。简单主站常这么干，但做不到边收边解析、粘包滑动对齐、多从站错配过滤，
  灵活性差。当前代码选"事件+轮询+阻塞等"混合模型，是为了这些能力付出的线程成本。

口诀：「等会卡自己，盯表要专人；主线程当老板不当工人；接收线程是事件白送的。」
